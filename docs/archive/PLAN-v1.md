# План работ — «Обмен с внешней системой»

Основание: `04-system-integration.md` (ТЗ v2.1 от 03.11.2026).

## 1. Суть задания

Ядро — надёжная интеграция с ненадёжным внешним исполнителем. Требования сводятся к четырём гарантиям:

1. **Задание не теряется.** Его принимают локально, сохраняют и отправляют потом, в том числе после перезапуска и после восстановления связи (D01, D-NF01).
2. **Внешнее исполнение происходит не более одного раза (at-most-once)**, включая случай потери ответа. Проверяется по счётчику исполнений в эмуляторе (D03, D-NF02, D07).
3. **Входящие результаты обрабатываются корректно.** Дубликат не даёт нового эффекта, устаревший результат не откатывает актуальное состояние, некорректное сообщение уходит на разбор (D03, D04, D-NF03).
4. **Неопределённость видна оператору.** Расхождения не исправляются автоматически без правила, решение оператора фиксируется (D05, D06).

Остальное (роли, аудит, UI, нагрузка, часовой пояс) — общие требования серии заданий. Они закрываются явными допущениями (раздел 6).

## 2. Архитектурные решения

### Стек
Java 21 + Spring Boot, PostgreSQL, Flyway, React + TypeScript + Vite, Docker Compose.

### Компоненты
- `app`: API, бизнес-логика, фоновые обработчики (dispatcher, reconciler).
- `emulator`: отдельное Spring-приложение со своей схемой БД и служебным API.
- `web`: SPA.
- `postgres`.

### Схема БД и миграции
Flyway в ТЗ не требуется, это выбор исполнителя. Требования: воспроизводимое применение схемы (NF09) и «схема и изменения БД» в составе результата (раздел 10).

- Схема лежит в версионируемых SQL-миграциях с явными ограничениями целостности: `UNIQUE`, `CHECK`, FK, индексы.
- Миграции применяются автоматически при старте и в Testcontainers-тестах.
- У эмулятора свой набор миграций.
- Демо-данные загружаются отдельной командой, вне миграций.
- `ddl-auto` не используется.

### Отправка: transactional outbox
- Создание задания и запись в `outbox` выполняются в одной транзакции.
- Dispatcher забирает записи через `SELECT … FOR UPDATE SKIP LOCKED` и захватывает их на время (lease).
- Если приложение упало во время отправки, lease истекает, и запись подхватывается снова.

### Идентификация бизнес-операции
- `operationId` (UUID) создаётся один раз при принятии задания и **не меняется при повторах**.
- Payload после принятия неизменяем.
- Эмулятор хранит операции с уникальным `operationId`. Повторный запрос возвращает существующий статус и не исполняется заново.
- Тот же `operationId` с другим payload отклоняется ответом `409`, а в приложении создаётся проблема.

### Два независимых состояния (D01)
- **Доставка:** `PENDING → SENDING → ACKNOWLEDGED`, а также `RETRY_WAIT`, `UNKNOWN` (ответ потерян, исход неясен), `FAILED` (исчерпаны попытки или постоянная ошибка).
- **Бизнес-результат:** `AWAITING → IN_PROGRESS → SUCCEEDED | REJECTED`.

Подтверждение получения (ACK) не означает выполнения.

### Повторы (D04)
- Экспоненциальная задержка с jitter, потолок интервала и лимит попыток (ориентир: 8 попыток в пределах ~30 минут).
- Таймаут и 5xx — временная ошибка. 4xx — постоянная: сразу создаётся проблема.
- Исчерпание попыток тоже создаёт проблему, и дальше повтор запускает только оператор.
- Холостого цикла нет: dispatcher берёт только записи с `next_attempt_at <= now()`.

### Входящие результаты: pull лентой
Альтернатива (callback + outbox) описана в разделе 12.

- Эмулятор ведёт ленту результатов: каждая запись имеет монотонный номер `feedSeq`.
- Приложение раз в 1–2 секунды запрашивает `GET /results?after=N&limit=100`.
- Курсор `N` хранится в нашей БД (`feed_cursor`). Обработка пачки результатов и сдвиг курсора идут **в одной транзакции**, поэтому перезапуск в любой момент ничего не теряет и не применяет дважды.
- Если эмулятор недоступен, опрос продолжается с паузами (backoff), без холостого цикла.
- Каждая полученная запись сохраняется в таблицу `inbox` с уникальным `messageId`. Повтор сообщения получает отметку `DUPLICATE` и не даёт эффекта.
- **Результат подтверждает получение.** Корректный результат для операции в `UNKNOWN` или `RETRY_WAIT` переводит доставку в `ACKNOWLEDGED` с пометкой «подтверждено результатом», отменяет запланированный повтор и закрывает проблему `UNKNOWN` с записью в историю.
- Правило применимости: у результата есть монотонный `sequence` в рамках операции.
  - Применяется, только если `sequence` больше текущего.
  - Терминальное состояние не откатывается к промежуточному.
  - Тот же `sequence` с другим содержимым — расхождение и проблема.
- Не прошёл схему, неизвестный `operationId` — статус `INVALID` и проблема. Курсор при этом сдвигается: некорректная запись не блокирует ленту.

### Сверка (D05)
Запускается периодически и вручную. Запрашивает у эмулятора `GET /operations/{id}` и сравнивает с локальным состоянием.

| Исход | Значение | Обработка |
|---|---|---|
| `MATCH` | Состояния совпадают | — |
| `EXTERNAL_AHEAD` | Снаружи есть результат, локально нет | Применяется автоматически с пометкой «источник: сверка». Это единственное автоматическое правило |
| `EXTERNAL_MISSING` | Эмулятор операцию не знает | Допустима повторная отправка: она безопасна благодаря идемпотентности |
| `CONFLICT` | Разные терминальные результаты | Только решение оператора («принять внешний» или «оставить локальный») с обязательным комментарием и записью в аудит |

`UNKNOWN` после потери ответа сразу показывается оператору и снимается сверкой или повтором.

### Права (NF02)
- Spring Security, сессия, демо-пользователи с BCrypt.
- Сущность **«служба»**: у пользователя и у задания есть служба.
  - Инициатор видит и меняет только свои задания.
  - Оператор видит задания своей службы и выполняет действия только по ним.
- Фильтр области доступа на уровне сервиса или репозитория. На чужое задание отвечаем `404`.
- Операторские эндпоинты закрыты ролью.
- API обмена и служебный API эмулятора защищены отдельными токенами.

### Повторы и гонки в API (NF03, NF04)
- `Idempotency-Key` на изменяющих запросах. Хранится таблица `(user, key, hash запроса, ответ)`; механизм действует и при прямом обращении к API.
- Optimistic locking через `version`: при конфликте `409` с понятным сообщением.

### Аудит и история (NF05, D-NF03)
- `audit_log`: автор, время, объект, действие, diff.
- `exchange_attempt`: исходящие попытки.
- `inbox`: входящие сообщения.
- `problem`: проблемы, их решения и связь с заданием.

Вместе они дают цепочку: задание → попытки → внешний результат → решение оператора.

### Журнал (NF10)
Структурированные логи с `taskId` и `operationId`. Пароли и токены не логируются.

## 3. Эмулятор

**Состояние:** `operations(operation_id PK, payload_hash, status, exec_count, result, sequence)`.

**Режимы сбоев.** Управляются через служебный API и CLI-скрипты. Правила детерминированные: «следующие N запросов» или конкретный `operationId` / тег задания.

| Режим | Поведение |
|---|---|
| `UNAVAILABLE` | 503 / отказ соединения |
| `LOSE_RESPONSE` | Исполнить, затем вернуть 500 или оборвать соединение |
| `DUPLICATE_RESULT` | Записать результат в ленту дважды (тот же `messageId`) |
| `DELAYED_RESULT` | Придержать результат и доставить его после более нового (out-of-order) |
| `BUSINESS_REJECT` | Исполнение с бизнес-отказом |
| `CORRUPT_MESSAGE` | Некорректная запись в ленте |

**Независимая проверка (D07):** `GET /emulator/operations/{id}` возвращает `exec_count` и фактическое состояние. После любого сценария должно быть `exec_count == 1`.

В обычном режиме (и при нагрузочном прогоне) нет искусственных задержек и отказов.

## 5. Тесты и данные

### Автотесты (NF10)
- **Unit:** переходы состояний, правило применимости, классификация ошибок, расчёт задержки повтора, расчёт просрочки.
- **Интеграционные (Testcontainers, PostgreSQL):**
  - outbox переживает «падение»;
  - параллельный dispatcher не отправляет одно и то же дважды;
  - потеря ответа даёт `UNKNOWN`, затем повтор, итог `exec_count = 1`;
  - дубликат и устаревший результат не дают эффекта;
  - некорректное сообщение становится проблемой;
  - параллельное изменение даёт `409`;
  - доступ к чужому заданию и операторским эндпоинтам через прямой API запрещён;
  - повтор с тем же `Idempotency-Key` не создаёт второе задание.
- **Сценарные end-to-end:** против поднятого эмулятора, по `scenarios.md`.

### Демо-данные
2 службы, 2 инициатора, оператор (одной из служб, чтобы было видно ограничение по области доступа) и 8 заданий:
1. успех;
2. бизнес-отказ;
3. ожидание из-за недоступности;
4. потеря ответа, затем сверка;
5. дубликат результата;
6. задержанный результат;
7. конфликт, ждущий решения оператора;
8. некорректное сообщение.

Задания создаются **прогоном сценариев через API и эмулятор**, а не SQL-вставкой, чтобы история обмена была настоящей (NF01).

### Нагрузка (NF08)
- Отдельная команда генерирует 5000 записей.
- Прогон k6: 30 секунд прогрева, 2 минуты, 20 клиентов.
- Операции поровну: список с фильтром и страницей 20, карточка, создание, изменение.
- Лимиты в Compose: суммарно 2 CPU и 4 ГиБ на app + db + emulator.

## 6. Допущения (зафиксировать в README)

- **Область доступа:** инициатор видит только свои задания, оператор — задания своей службы. Служба задаётся начальной загрузкой, интерфейса управления службами нет.
- **Сроки (NF07):**
  - у задания есть `deadline`;
  - «просрочено» = нет терминального бизнес-результата на момент `deadline`, граница включительная;
  - хранение в UTC, отображение и ввод в `Europe/Moscow`;
  - расчёт только на сервере.
- **Изменение записи (NF08):** смена внутренних полей заявки (ответственный, приоритет, комментарий) с проверкой `version`. Содержимое заявки (груз, вес, адрес, срок) после отправки неизменяемо.
- **Фильтр реестра:** по бизнес-статусу или приоритету, с индексами.
- **Ресурсы:** heap JVM ~768 МБ на приложение, ограниченные пулы соединений.
- **Разрешённые действия оператора:**
  - повтор доставки только из `FAILED` или `UNKNOWN`;
  - сверка;
  - решение по конфликту;
  - закрытие проблемы с некорректным сообщением.

  Каждое действие идемпотентно и попадает в аудит.
- **Отмена задания** вне объёма и указывается в ограничениях.

Если к концу 3-го дня сбойные сценарии на бэкенде не работают, сокращается UI, а не надёжность.

### Что можно сократить
- UI управления эмулятором: хватит CLI-скриптов (~2 ч).
- Сущность «служба» (~1–2 ч).
- Периодическая сверка: оставить запуск вручную (~1 ч).
- Визуальная полировка UI. Доступность при этом остаётся.

### Что сокращать нельзя
- Идемпотентность и `exec_count = 1`.
- Outbox и восстановление после перезапуска.
- Видимый оператору `UNKNOWN`.
- Проверка прав на уровне API.
- Автотесты на реальной БД.
- Нагрузочный отчёт с числом ошибок.
- Воспроизводимый запуск по README.

## 9. Частые причины провала проверки

- Новый `operationId` при повторе или отсутствие дедупликации в эмуляторе: тогда `exec_count = 2`.
- Подтверждение получения (ACK) отображается как «выполнено».
- Потеря ответа превращается в `FAILED` или `SUCCESS` вместо `UNKNOWN`.
- Сверка молча перезаписывает конфликт.
- Доступ к чужому заданию по прямому ID через API.
- Холостой цикл повторов.
- Секреты в логах.
- Нагрузочный отчёт без ошибок или прогон без лимитов ресурсов.

### Уровни тестирования

| Уровень | Что проверяет | Как запускается |
|---|---|---|
| Unit | Правила без БД и сети: переходы статусов, применимость результатов, паузы между повторами, просрочка | `./gradlew test` |

| Сценарные | Приложение и реальный эмулятор: по тесту на каждый режим сбоя, проверка статуса в приложении и `exec_count = 1` в эмуляторе | `make test-scenarios` на поднятом стенде |

| Нагрузка | p95 на 5000 записях, 20 клиентов, под лимитами ресурсов | `make seed-load && make load-test` |

Ключевой сценарий — **потеря ответа после исполнения**:
1. Эмулятор исполнил задание, ответ потерян.
2. В приложении задание в `UNKNOWN`.
3. Повтор с тем же `operationId`.
4. Эмулятор отвечает «уже исполнено».
5. Итог: `exec_count = 1`, задание в корректном итоговом статусе.

**Ручная проверка** — чек-лист в README: «включите режим X → создайте задание → откройте карточку → ожидаемый результат Y → проверка в эмуляторе командой Z».

### Развёртывание

Промышленное развёртывание не требуется (ТЗ, раздел 5). Результат — воспроизводимый локальный запуск:

```bash
cp .env.example .env
docker compose up -d --build   # сборка, запуск, применение миграций
make seed                      # демо-пользователи и задания (прогон сценариев)
# http://localhost:3000
```

### Эмулятор

**Отдельный процесс и контейнер в общем `docker-compose.yml`.** Код лежит в том же репозитории, модуль `/emulator`.

```
docker-compose.yml
 ├─ postgres   одна инстанция, две базы: app и emulator (разные пользователи)
 ├─ app        Spring Boot: API + dispatcher + reconciler
 ├─ emulator   Spring Boot: отдельное приложение
 └─ web        nginx со сборкой React
```

**Почему отдельный процесс:**
- состояние и счётчик исполнений проверяются независимо от приложения (D07);
- недоступность можно воспроизвести по-настоящему: `docker compose stop emulator`;
- обмен идёт по реальному HTTP с таймаутами и обрывами.

**Почему общий Postgres:** бюджет 2 CPU / 4 ГиБ. Изоляцию дают отдельная база и отдельный пользователь: приложение не имеет доступа к базе эмулятора.

### Конфигурация

Переменные окружения в `.env` (шаблон `.env.example` в репозитории) и профили Spring. Секреты не хранятся в коде и не попадают в логи.

**Приложение (`app`):**

| Параметр | Пример / назначение |
|---|---|
| `DB_URL`, `DB_USER`, `DB_PASSWORD` | база `app` |
| `EMULATOR_URL` | `http://emulator:8081` |
| `EMULATOR_TOKEN` | токен вызовов эмулятора |
| `RESULTS_POLL_INTERVAL` | `1s`: интервал опроса ленты результатов |
| `RETRY_MAX_ATTEMPTS`, `RETRY_BASE_DELAY`, `RETRY_MAX_DELAY` | `8`, `5s`, `10m` |
| `DISPATCH_LEASE_TIMEOUT` | `60s`: когда отправка считается зависшей |
| `HTTP_TIMEOUT` | `5s` |
| `RECONCILE_INTERVAL` | `5m` |
| `APP_TIMEZONE` | `Europe/Moscow` |

**Эмулятор (`emulator`):**

| Параметр | Пример / назначение |
|---|---|
| `DB_URL`, `DB_USER`, `DB_PASSWORD` | база `emulator` |
| `API_TOKEN` | токен, который должно предъявлять приложение |
| `ADMIN_TOKEN` | доступ к служебному API |
| `EXECUTION_DELAY` | `0` по умолчанию, без искусственных задержек |

**Режимы сбоев** включаются во время работы, без перезапуска: через служебный API эмулятора или CLI-скрипт.

```bash
./emu fault set UNAVAILABLE --count 5
./emu fault set LOSE_RESPONSE --task-tag demo-lost
./emu fault clear
./emu operation <operationId>   # фактическое состояние и exec_count
```

**Профили Spring:**
- `default` — демо;
- `test` — короткие интервалы повторов для быстрых тестов;
- `load` — сокращённое логирование для нагрузочного прогона.

**Лимиты ресурсов** (`cpus`, `mem_limit`) заданы в `docker-compose.yml` и описаны в README: суммарно 2 CPU и 4 ГиБ на app + postgres + emulator (NF08).

## 11. Журнал решений

| № | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Стек | Java + Spring, React + TypeScript, PostgreSQL | Ориентир ТЗ, стек знаком |
| 2 | Область доступа оператора | Вводится «служба»: оператор видит задания своей службы | NF02 требует ограничения по области, а не только по роли |
| 3 | Результат пришёл, пока доставка в `UNKNOWN` | Корректный результат подтверждает получение: `ACKNOWLEDGED`, повтор отменяется, проблема закрывается с записью в историю | Результат доказывает, что исполнитель получил задание; иначе оператор видит противоречивую картину |
| 4 | Получение результатов | Pull лентой с курсором в нашей БД + сверка (при старте, периодически, вручную) | Переживает перезапуск по построению, меньше кода, без нового сервиса. Kafka отклонена: не снимает идемпотентность, дедупликацию и сверку, а занимает 0,5–1 ГБ из бюджета 4 ГиБ |
| 5 | Повтор после потери ответа (таймаут) | Автоповтор с тем же `operationId` по обычному расписанию + проблема `UNKNOWN` видна оператору. Ответ «уже исполнено» или полученный результат снимает её автоматически, след остаётся в истории. После исчерпания попыток — ждём оператора | Повтор безопасен благодаря идемпотентности; ручная работа только там, где автоматике не хватило попыток |
| 6 | Предметная область | Заявка на доставку груза: груз, вес, адрес, срок. Вымышленная служба доставки возвращает номер отправления и стоимость либо отказ с причиной | Понятно без объяснений, естественный срок для NF07, наглядные расхождения при сверке |
| 7 | Жизненный цикл и «изменение» | Заявка создаётся черновиком (всё редактируется). «Отправить» фиксирует содержимое, создаёт `operationId` и запись в outbox. После отправки меняются только внутренние поля: ответственный, приоритет, комментарий. Для NF08 «изменение» = смена внутренних полей, допустима в любом состоянии | Отправленный payload неизменяем (идемпотентность); у нагрузки есть настоящая бизнес-операция без массовых отказов |

## 12. Отложенная альтернатива: callback + outbox

Не реализуется сейчас. Сохранено на случай, если понадобится push-модель.

**Как работает:**
- Эмулятор после исполнения пишет в свою таблицу `callback_outbox` запись «отправить результат X».
- Отдельный процесс эмулятора отправляет `POST /api/integration/results` в приложение и повторяет с экспоненциальной задержкой, пока не получит `2xx`. Попытки ограничены.
- Запрос подписывается HMAC-SHA256 с общим секретом (`CALLBACK_HMAC_SECRET`); приложение отклоняет запросы с неверной подписью.
- Приложение сохраняет сообщение в `inbox` (уникальный `messageId`) и отвечает `2xx` только после коммита.
- Сверка в приложении остаётся страховкой: опрашивает задания, которые дольше порога висят в `ACKNOWLEDGED` без результата.

**Дополнительная конфигурация:**
- приложение: `CALLBACK_HMAC_SECRET`;
- эмулятор: `CALLBACK_URL`, `CALLBACK_HMAC_SECRET`, `CALLBACK_MAX_ATTEMPTS`.

**Плюсы:**
- ближе к реальным вебхукам;
- результат приходит сразу, без интервала опроса.

**Минусы:**
- около +3–4 часов;
- больше движущихся частей: outbox в эмуляторе, подпись, входящий endpoint;
- при недоступности приложения доставка зависит от повторов на стороне эмулятора.

**Переход с pull:** таблица `inbox`, правила применимости и сверка не меняются. Меняется только транспорт: вместо опроса ленты — входящий endpoint.
