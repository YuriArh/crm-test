# carrier-emulator — проектные решения

`carrier-emulator` — **максимально простой тестовый стенд**, изображающий внешнего перевозчика. Он нужен, чтобы проверить работу `dispatch` с интеграцией (D01–D03, D07, D-NF02), а не как самостоятельный продукт. Сложной бизнес-логики нет.

Документ фиксирует итог проектного опроса от 12.11.2026. Сторона `dispatch` описана в `docs/dispatch-design.md` (§5 «Обмен с перевозчиком», §6 «Сверка»); эмулятор поддерживает то, что там требуется.

## 1. Границы

- Отдельное приложение, **общих Java-классов с `dispatch` нет**. Единственная договорённость — `contracts/carrier-api.yaml` (OpenAPI 3.1, пишется вручную, генерации кода нет; DTO на каждой стороне свои).
- Аутентификации нет: обмен идёт внутри docker-сети. Это допущение записывается в README.
- Своей веб-страницы нет: управление сбоями и просмотр состояния — служебный JSON API и команды `make` (ТЗ это допускает).

## 2. Стек и запуск

- Spring Boot 4 / Java 25, модуль Gradle `carrier-emulator`, пакет `com.acme.carrier`, порт `8081`.
- Доступ к данным — только `JdbcClient` (простые таблицы и условные `UPDATE`; Spring Data не нужен).
- **Своя БД:** база `carrier` с отдельным пользователем в общем контейнере PostgreSQL (создаётся init-скриптом контейнера). Отдельный контейнер не нужен: он съел бы ~200–300 МБ из бюджета NF08 и не дал бы большей изоляции данных.
- Схема — собственные миграции Flyway эмулятора.
- Ресурсы в compose: ~0.4 CPU / 768 МБ (общий бюджет NF08 — 2 CPU / 4 ГиБ на `dispatch` + PostgreSQL + эмулятор).

## 3. Рабочий API (контракт с `dispatch`)

Точный формат — `contracts/carrier-api.yaml`; ниже — суть.

| Запрос | Ответ |
|---|---|
| `POST /operations` `{operationId, cargoDescription, weightKg, deliveryAddress, deadline}` | первый раз — `202 {operationId, status: "ACCEPTED"}`; повтор с тем же содержимым — тот же `202`, без нового исполнения; тот же `operationId` с другим содержимым — `409 {code: "PAYLOAD_MISMATCH"}`; неверное тело — `400` |
| `GET /operations/{operationId}` | состояние операции и итог (для сверки); незнакомая операция — `404` (в `dispatch` это `EXTERNAL_MISSING`) |
| `GET /results?after=N&limit=…` | записи ленты с `feedSeq > N` по возрастанию, `limit` ≤ 100 |

- **Почему `POST`, а не `PUT /operations/{id}`:** отправка задания — действие, а не сохранение документа; так выглядит типичный внешний API и наш собственный `POST /api/requests` с ключом идемпотентности. Идемпотентность обеспечивает `operationId` в теле.
- Содержимое сравнивается по хэшу, эмулятор хранит его у себя.
- Ошибки — простой JSON `{code, message}`, не Problem Details: эмулятор изображает «чужую» систему.
- `deadline` принимается и хранится, но в правилах исполнения не используется.

**Запись ленты** (формат из `dispatch-design.md` §5):

```json
{
  "feedSeq": 1042,
  "messageId": "…",
  "operationId": "…",
  "sequence": 2,
  "status": "SUCCEEDED",
  "trackingNumber": "TRK-58213A0C",
  "price": 1450.00,
  "reason": null,
  "occurredAt": "2026-11-12T09:15:03Z"
}
```

`status`: `IN_PROGRESS` (`sequence = 1`), `SUCCEEDED` или `REJECTED` (`sequence = 2`).

## 4. Исполнение

- Приём (`POST /operations`) только сохраняет операцию в статусе `ACCEPTED` и отвечает «получено». Получение ≠ исполнение (D01).
- **Исполнитель:** один `@Scheduled` раз в ~1 с берёт принятые операции. По каждой в одной транзакции:
  - переход `ACCEPTED → EXECUTED` условным `UPDATE … WHERE status = 'ACCEPTED'`;
  - запись в ленту `IN_PROGRESS` (`sequence = 1`) и итога (`sequence = 2`).
- **Порядок ленты:** `feed_seq` — `bigserial`. В ленту пишет только этот единственный поток, поэтому записи коммитятся строго по порядку и в `feedSeq` нет «дыр», которые `dispatch` мог бы перескочить курсором.
- **Правило исхода** (детерминированное, чтобы демо-данные и тесты воспроизводились):

  | Условие | Исход |
  |---|---|
  | вес > 10 000 кг | `REJECTED`, «Превышен допустимый вес» |
  | адрес содержит `тест-отказ` | `REJECTED`, «Адрес не обслуживается» |
  | иначе | `SUCCEEDED`: `trackingNumber = TRK-` + 8 символов, производных от `operationId`; `price = 300 + 25 × вес`, округление до копеек |

## 5. Не более одного исполнения (D03, D-NF02, D07)

- Уникальный ключ `operation_id` в БД эмулятора и условный `UPDATE ACCEPTED → EXECUTED`: повтор отправки, в том числе после потери ответа, не приводит ко второму исполнению.
- Два счётчика на операцию:
  - `received_count` — сколько раз операцию присылали (включая повторы);
  - `execution_count` — сколько раз она реально исполнена: всегда 0 или 1.
- Оба видны в служебном API отдельно от `dispatch` (D07).

## 6. Режимы сбоев (D07)

Каждый режим — выключатель «вкл/выкл» **в памяти** эмулятора. Без счётчиков «следующих K операций» и без хранения в БД; после перезапуска эмулятора все режимы выключены. Сценарий проверки: включить → создать заявку → выключить.

| Режим | Поведение |
|---|---|
| `UNAVAILABLE` | все рабочие запросы (приём, лента, сверка) получают `503` |
| `LOSE_RESPONSE` | операция принимается и фиксируется, затем ответ задерживается на 10 с — дольше таймаута `dispatch` (5 с). `dispatch` видит `UNKNOWN`, хотя приём уже состоялся |
| `DUPLICATE` | каждая запись результата публикуется в ленту дважды с тем же `messageId` |
| `DELAYED` | итог публикуется через 60 с, а запись `IN_PROGRESS` — **после** итога. `dispatch` должен пометить её `STALE` и не откатить состояние |

Задержки (10 с, 60 с) настраиваются в конфигурации. В обычном режиме (и в нагрузочном прогоне NF08) искусственных задержек и отказов нет.

## 7. Служебный API и команды

| Запрос | Что делает |
|---|---|
| `GET /admin/faults` | текущие режимы |
| `PUT /admin/faults` | включить/выключить режимы |
| `GET /admin/operations[?operationId=…]` | операции: статус, итог, `received_count`, `execution_count` |

- Обёртки в Makefile: `make fault-unavailable`, `make fault-lose-response`, `make fault-duplicate`, `make fault-delayed`, `make fault-off`, `make carrier-ops`.
- Отдельного сброса нет — `make reset`.

## 8. Данные

| Таблица | Содержимое |
|---|---|
| `operation` | `operation_id` (PK), содержимое, хэш содержимого, статус (`ACCEPTED` / `EXECUTED`), итог (`status`, `tracking_number`, `price`, `reason`), `received_count`, `execution_count`, `created_at`, `executed_at` |
| `feed_entry` | `feed_seq` (`bigserial`), `message_id` (UUIDv7), `operation_id`, `sequence`, статус и поля результата, `occurred_at` |

Записи не удаляются: объём мал, лента нужна для сверки и разбора. Правила схемы — как в `dispatch` (CLAUDE.md, раздел о миграциях).

## 9. Тесты

- **Модульные:** правило исхода, номер отправления, цена.
- **Интеграционные** (Testcontainers): приём и повтор, `409` на другое содержимое, исполнение ровно один раз, лента и курсор, режимы сбоев. **Каждый ответ сверяется с `contracts/carrier-api.yaml`** (`swagger-request-validator-mockmvc`; если он несовместим с Boot 4 / Jackson 3 — небольшая собственная проверка по JSON Schema). Это единственное, что держит YAML честным: e2e сравнивает код с кодом и проходит только счастливый путь.
- **E2E** (живой стенд): счётчики и режимы через служебный API. Сквозной сценарий с `dispatch` — когда в нём появятся отправка и опрос ленты.
