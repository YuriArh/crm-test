# Устройство `dispatch` — принятые решения

`dispatch` — основное приложение: принимает заявки на доставку, передаёт их внешнему перевозчику (`carrier-emulator`), отслеживает доставку и бизнес-результат, сверяет состояние и показывает проблемы оператору.

Документ фиксирует итог проектного опроса от 12.11.2026. Требования ТЗ указаны в скобках (D01–D07, NF01–NF10, D-NF01–03). Альтернатива с callback вместо опроса ленты описана в `docs/archive/PLAN-v1.md`, раздел 12.

## 1. Основа

- **Стек:** Java 25, Spring Boot 4.1, PostgreSQL 18.
- **Схема БД** — только Flyway-миграции с явными ограничениями (`UNIQUE`, `CHECK`, FK, индексы). Соответствие схемы и кода проверяют интеграционные тесты на реальной БД.
- **Время:** моменты хранятся и обрабатываются в UTC. Единая бизнес-зона — `Europe/Moscow` (`APP_TIMEZONE`). «Сейчас» берётся только из бина `Clock` (NF07).
- **Пакеты по возможностям:**

  | Пакет | Что внутри |
  |---|---|
  | `request` | заявки |
  | `exchange` | очередь, отправка, опрос ленты, обработчик результатов |
  | `carrier` | HTTP-клиент перевозчика |
  | `auth` | пользователи, службы, права |
  | `problem` | проблемы и действия по ним |
  | `reconciliation` | сверка |

- **Доступ к данным:** без ORM (JPA/Hibernate не используется).
  - Обычные сущности (заявка, проблема, пользователь) — через Spring Data JDBC: репозитории, `@Version` для optimistic locking, пагинация. Сущности — изменяемые классы с доменными методами (`changeComment`, `changeAssignee`), потому что Spring Data должен выставлять `version`; DTO и модели чтения — Java records. Нет кэша сущностей, ленивых загрузок и неявных `UPDATE`.
  - Ядро обмена — явный SQL через `JdbcClient`: очередь (`FOR UPDATE SKIP LOCKED`), блокировка строки операции, `INSERT … ON CONFLICT` для дедупликации, условные переходы статусов, запрос реестра.
  - **Почему:** это ядро всё равно PostgreSQL-специфичный SQL. Кэш сущностей Hibernate не видит нативных `UPDATE`, и воркер мог бы затереть свежее состояние устаревшим (D03).
- **Правила для кода:**
  - агрегаты маленькие: заявка и операция — разные агрегаты, связь по id;
  - переход статуса операции — только условным `UPDATE … WHERE status IN (…)` с проверкой числа изменённых строк, а не «прочитал → изменил → сохранил»;
  - новизна сущности определяется по `version == null`.
- **Идентификаторы:** первичные ключи — UUIDv7, генерируются в приложении. Номер заявки для людей — из sequence, формат `DR-000123`.
- **API:**
  - REST + JSON под `/api`, без HATEOAS;
  - ошибки в формате Problem Details (RFC 9457) с машинным кодом, ошибки валидации — по полям;
  - конфликт версии — `409 VERSION_CONFLICT`, недопустимое действие в текущем состоянии — `409 INVALID_STATE`;
  - коды ошибок: `VALIDATION_FAILED` (400, `errors[]` по полям), `IDEMPOTENCY_KEY_REQUIRED` (400), `IDEMPOTENCY_KEY_REUSED` (422), `UNAUTHENTICATED` (401), `BAD_CREDENTIALS` (401), `FORBIDDEN` (403), `NOT_FOUND` (404), `VERSION_CONFLICT` (409, с полем `current`), `INVALID_STATE` (409), `INVALID_ASSIGNEE` (422), `INTERNAL_ERROR` (500);
  - 401 и 403 из цепочки безопасности тоже отдаются как Problem Details, без перенаправлений.

## 2. Пользователи и права (NF02)

**Вход:**
- сессия на cookie (Spring Security), пароли под BCrypt;
- эндпоинты: `GET /api/auth/csrf` (выдаёт токен и cookie), `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`; список операторов своей службы для выбора ответственного — `GET /api/users/operators` (только оператор);
- при входе меняется id сессии (защита от фиксации сессии), контекст сохраняется в сессию явно, CSRF-токен обновляется;
- неизвестный пользователь, неверный пароль и отключённая учётная запись дают одинаковый ответ `401 BAD_CREDENTIALS`;
- CSRF: cookie `XSRF-TOKEN` (читается SPA), заголовок `X-XSRF-TOKEN` на каждом изменяющем запросе; при выходе cookie очищается, токен нужно получить заново;
- сессия хранится в памяти: после перезапуска нужно войти заново, данные при этом сохраняются.

**Данные:**
- службы и демо-пользователи создаются Flyway-миграцией: две службы, два инициатора и оператор одной из служб;
- демо-заявки создаёт команда `make seed` через API, чтобы история обмена была настоящей.

**Права:**

| | Инициатор | Оператор |
|---|---|---|
| Видит заявки | только свои | своей службы |
| Создаёт заявки | да | нет |
| Комментарий | в своих заявках | да |
| Ответственный | нет | назначает оператора своей службы |
| Техническая история обмена | нет | да |
| Проблемы и действия по обмену | нет | да |

- Чужая заявка — `404`, запрещённое действие — `403`.
- Область доступа применяется сервером всегда, из параметров запроса её не изменить.

## 3. Заявка

**Жизненный цикл.** Черновика нет. «Создать» сохраняет заявку и в той же транзакции создаёт операцию в очереди на отправку (D01, D-NF01).

**Защита от повторного создания** (NF04), с этапа 1:
- заголовок `Idempotency-Key` обязателен, без него ответ `400`;
- сервер хранит «пользователь + ключ → хэш запроса + ответ»;
- повтор с тем же ключом и телом возвращает сохранённый первый ответ (ту же заявку) с заголовком `Idempotent-Replayed: true`;
- тот же ключ с другим телом — `422`;
- ключи раздельны по пользователям; при ошибке действия (например, срок в прошлом) ключ не расходуется — транзакция откатывается целиком;
- вес нормализуется: `12.50` и `12.5` кг — один и тот же запрос.

**Поля:**

| Группа | Поля | Изменяемость |
|---|---|---|
| Содержимое | описание груза (до 200 символов), вес в кг (0,1–20 000), адрес доставки, срок доставки (дата) | неизменяемо с момента создания |
| Внутренние | ответственный, комментарий | меняются в любом состоянии, с проверкой `version` (NF03) |
| Системные | номер, служба, автор, время создания, статус доставки, бизнес-статус, `version` | меняет только система |

**Срок и просрочка** (NF07):
- срок — дата в бизнес-зоне, включительно («до 15.11» = до конца 15.11 по Москве);
- при создании срок не раньше сегодняшней даты по Москве;
- **просрочена**, если бизнес-статус не итоговый (`AWAITING` или `IN_PROGRESS`), а сегодняшняя дата по Москве позже срока;
- `SUCCEEDED` и `REJECTED` не бывают просроченными;
- признак считается на сервере, в API отдаётся поле `overdue`, по нему можно фильтровать.

**Ответственный:** только оператор той же службы. При создании пустой. Смена записывается в журнал, история заявки сохраняется (NF05).

**Правка заявки:** `PATCH /api/requests/{id}` с телом `{version, comment?, assigneeId?}`.
- Пропущенное поле не меняется, явный `null` очищает значение. Тело разбирается из дерева JSON, а не через привязку к `Optional`: Jackson превращает в пустой `Optional` и пропущенное поле, и `null`, а здесь это разные действия.
- Незнакомые поля, в том числе поля содержимого, отклоняются (`400 VALIDATION_FAILED`).
- `version`, которую видел клиент, должна совпадать с текущей, иначе `409 VERSION_CONFLICT` с актуальным состоянием в поле `current` (NF03).
- Если присланные значения совпадают с текущими, это пустая операция: `200` без увеличения `version`, без проверки версии и прав. Повторный клик не даёт конфликта, а клиент, который всегда отправляет форму целиком, не получает `403` за поле, которое не менял. Права и `version` проверяются только для полей, которые действительно меняются.
- Длина комментария (до 2000) считается по тексту после обрезки пробелов и в символах, как `varchar` в PostgreSQL.

## 4. Модель данных

Миграции лежат в `dispatch/src/main/resources/db/migration`:

| Файл | Что создаёт |
|---|---|
| `V1__services_and_users.sql` | `service`, `app_user` |
| `V2__delivery_requests.sql` | `delivery_request`, `dispatch_operation`, `exchange_attempt`, sequence номеров заявок |
| `V3__result_inbox.sql` | `inbox`, `feed_cursor` (с начальной строкой) |
| `V4__idempotency_keys.sql` | `idempotency_key` |
| `V5__demo_users.sql` | демо-службы и демо-пользователи |

**Общие правила схемы:**
- первичные ключи `uuid` генерирует приложение (UUIDv7), значений по умолчанию у id нет;
- статусы хранятся как `text` + `CHECK (… IN (…))`, а не как типы enum PostgreSQL: их проще менять;
- моменты времени — `timestamptz`, срок — `date`. `created_at` и `updated_at` ставит приложение из `Clock`, триггеров и `now()` по умолчанию нет.

**Таблицы:**

| Таблица | Содержимое и ключевые ограничения |
|---|---|
| `service` | `code` (уникальный: `NORTH`, `SOUTH`), `name` |
| `app_user` | логин (уникален без учёта регистра), имя, хэш пароля BCrypt, `role` (`INITIATOR` / `OPERATOR`), служба, `enabled`. Дополнительно `UNIQUE (id, service_id)` — цель составных внешних ключей |
| `delivery_request` | номер из sequence, служба, автор, ответственный; содержимое (груз до 200 символов, вес 0,1–20 000 кг, адрес, срок); комментарий; **бизнес-результат**: `business_status`, `tracking_number`, `price`, `rejection_reason`, `result_at`; `created_at`, `updated_at`, `version` |
| `dispatch_operation` | ключ — `request_id` (1:1 с заявкой); `operation_id` (уникальный), `payload_hash`, `delivery_status`, `attempts`, `next_attempt_at`, `locked_until`, `last_error`, `acknowledged_at` + `acknowledged_via` (`RESPONSE` / `RESULT` / `RECONCILIATION`), `last_applied_seq`. Колонки `version` нет: меняется только условными `UPDATE` |
| `exchange_attempt` | попытка отправки: номер (уникален в рамках операции), время начала и конца, исход, HTTP-код, ошибка, длительность |
| `inbox` | одна строка на сообщение: `message_id` (уникальный, если есть), `feed_seq`, `operation_id` (без FK: может быть незнакомым), `sequence`, статус результата, исходная запись (`jsonb`), источник (`FEED` / `RECONCILIATION`), `processing_status` (`APPLIED` / `STALE` / `CONFLICT` / `INVALID`), причина. Повтор сообщения не создаёт новую строку, а увеличивает `duplicate_count` (`INSERT … ON CONFLICT`) |
| `feed_cursor` | одна строка `carrier`: номер последней обработанной записи ленты |
| `idempotency_key` | ключ `(user_id, idem_key)`, операция, хэш запроса, сохранённый ответ, id созданного объекта. Пишется в той же транзакции, что и само действие: параллельный дубль ждёт на первичном ключе и затем получает сохранённый ответ |

**Целостность на уровне БД (NF03):**
- составные внешние ключи `(owner_id, service_id)` и `(assignee_id, service_id)` → `app_user (id, service_id)`: автор и ответственный всегда из службы заявки. Роль «оператор» у ответственного проверяет код;
- `SUCCEEDED` невозможен без номера отправления, стоимости и времени результата; `REJECTED` — без причины;
- `SENDING` невозможен без `locked_until`; `acknowledged_at` и `acknowledged_via` заполняются только вместе.

**`version` у заявки** увеличивает каждый, кто её меняет, включая воркер, применяющий результат. Правка пользователя, сделанная по старой версии, получит `409`, а не затрёт результат молча. Результат меняется 1–2 раза за жизнь заявки, поэтому такие конфликты редки.

Заявка и операция лежат в разных таблицах: частые изменения операции (попытки, захват воркером) не трогают `version` заявки.

**Индексы:**
- реестр: `delivery_request (service_id, business_status, created_at desc)` и `(owner_id, created_at desc)`, плюс `(assignee_id)`;
- очередь: частичный индекс `dispatch_operation (next_attempt_at)` для статусов `PENDING`, `RETRY_WAIT`, `UNKNOWN`;
- восстановление после падения: частичный индекс `(locked_until)` для `SENDING`;
- фильтр реестра: `dispatch_operation (delivery_status)`;
- `inbox (operation_id, received_at)` для истории заявки.

**Этап 2** добавит отдельными миграциями `problem` (с частичным уникальным индексом «одна открытая проблема каждого вида на заявку») и `audit_log`.

## 5. Обмен с перевозчиком

### Идентификация операции (D02, D03)
- `operationId` (UUID) создаётся вместе с заявкой и никогда не меняется. Все повторы отправки используют его.
- Хранится хэш содержимого. Если перевозчик ответил, что этот `operationId` уже был с другими данными, создаётся проблема `PAYLOAD_CONFLICT`.
- Отправка: `POST /operations` с `operationId` в теле; перевозчик отвечает `202` и на первый приём, и на повтор (без второго исполнения), `409 PAYLOAD_MISMATCH` — если `operationId` уже был с другим содержимым. Контракт — `contracts/carrier-api.yaml`, сторона эмулятора — `docs/carrier-emulator-design.md`.

### Статусы

| Доставка | Значение |
|---|---|
| `PENDING` | ждёт отправки |
| `SENDING` | воркер отправляет сейчас |
| `RETRY_WAIT` | временная ошибка, ждём следующей попытки |
| `UNKNOWN` | таймаут или обрыв после отправки, исход неизвестен; ждём повтора |
| `ACKNOWLEDGED` | перевозчик подтвердил получение |
| `FAILED` | постоянная ошибка или попытки кончились; решает оператор |

| Бизнес-результат | Значение |
|---|---|
| `AWAITING` | результатов ещё нет |
| `IN_PROGRESS` | перевозчик взял заявку в работу |
| `SUCCEEDED` | итог: номер отправления и стоимость |
| `REJECTED` | итог: отказ с причиной |

Подтверждение получения не означает выполнения (D01).

### Отправка (D04, D-NF01)
- Воркер `@Scheduled(fixedDelay)` захватывает пачку операций через `FOR UPDATE SKIP LOCKED`, поэтому корректен и при нескольких экземплярах.
- **HTTP-клиент:** Spring `RestClient`, таймаут соединения 2 с, ответа 5 с (задаются в конфигурации).
- **Классификация исходов:**

  | Исход | Статус доставки |
  |---|---|
  | таймаут или обрыв после отправки | `UNKNOWN` |
  | отказ соединения, 5xx | `RETRY_WAIT` |
  | `409 PAYLOAD_MISMATCH` | `FAILED` + проблема `PAYLOAD_CONFLICT` |
  | прочие 4xx | `FAILED` |
  | подтверждение | `ACKNOWLEDGED` |

- **Восстановление после падения:** операция в `SENDING`, у которой истёк захват (60 с), переходит в `UNKNOWN` и отправляется снова.
- **Повторы:** пауза от 5 с, удваивается до потолка 5 минут, разброс ±20 %, не больше 8 попыток (около 20 минут), затем `FAILED`. Повтор оператором сбрасывает счётчик, `operationId` прежний.
- **При `UNKNOWN`** повтор автоматический, с тем же `operationId`: это безопасно, потому что перевозчик не исполняет одну операцию дважды (D-NF02). Статус виден сразу в карточке и реестре.

### Получение результатов: опрос ленты
- Раз в 1 с `GET /results?after=N`, пачками до 100. Если пачка полная, следующий запрос идёт сразу.
- Курсор `N` хранится в `feed_cursor` и сдвигается в той же транзакции, что и обработка пачки, поэтому перезапуск ничего не теряет и не применяет дважды.
- При недоступности перевозчика пауза растёт 1 с → 2 с → … → 30 с, после успеха возвращается к 1 с. В журнал пишется только смена состояния «недоступен / доступен».

**Запись ленты:**

```json
{
  "feedSeq": 1042,
  "messageId": "…",
  "operationId": "…",
  "sequence": 2,
  "status": "SUCCEEDED",
  "trackingNumber": "TRK-58213",
  "price": 1450.00,
  "reason": null,
  "occurredAt": "2026-11-12T09:15:03Z"
}
```

### Обработка результатов (D03, D-NF02, D-NF03)
- **Транспорт отделён от обработки.** Опрос ленты только получает записи и передаёт их в единый обработчик `ResultInbox.accept(message)`. Переход на callback меняет только транспорт.
- **Блокировка:** обработчик блокирует строку операции (`SELECT … FOR UPDATE`) на время применения результата. Так код корректен и при параллельной доставке сообщений.
- **Правила:**

  | Ситуация | Действие |
  |---|---|
  | `messageId` уже был | `DUPLICATE`, без эффекта |
  | `sequence` не больше применённого | `STALE`, без эффекта |
  | тот же `sequence`, другое содержимое | `CONFLICT`, проблема `RESULT_CONFLICT` |
  | неверный формат или незнакомый `operationId` | `INVALID`, проблема `INVALID_MESSAGE`; курсор идёт дальше |
  | иначе | `APPLIED`, бизнес-статус обновляется |

- Итоговый статус (`SUCCEEDED` или `REJECTED`) автоматически не меняется никогда.
- **Результат подтверждает доставку:** корректный результат для операции в `UNKNOWN`, `RETRY_WAIT` или `FAILED` переводит её в `ACKNOWLEDGED`. Запланированный повтор отменяется, проблема доставки закрывается, в истории остаётся пометка «подтверждено результатом».

## 6. Сверка (D05)

- **Запуск:** при старте, раз в 5 минут и вручную оператором по заявке.
- **Кого сверяем:** операции в `UNKNOWN`, а также в `ACKNOWLEDGED` без итогового результата дольше 2 минут. По каждой — `GET /operations/{operationId}`.
- **Исходы:**

  | Исход | Значение | Действие |
  |---|---|---|
  | `MATCH` | состояния совпадают | — |
  | `EXTERNAL_AHEAD` | у перевозчика есть результат, у нас нет | применить через `ResultInbox` с пометкой «источник: сверка». Единственное автоматическое правило |
  | `EXTERNAL_MISSING` | перевозчик операцию не знает | поставить повторную отправку |
  | `CONFLICT` | разные итоговые результаты | ничего не менять, проблема `RECONCILIATION_CONFLICT` |

- Каждый запуск и его исход записываются в историю заявки.

## 7. Проблемы и действия оператора (D05, D06, D-NF03)

**Виды проблем:**

| Вид | Когда возникает | Как закрывается |
|---|---|---|
| `DELIVERY_UNKNOWN` | доставка в `UNKNOWN` | автоматически: результат или подтверждение |
| `DELIVERY_FAILED` | доставка в `FAILED` | автоматически при результате или повтором оператора |
| `INVALID_MESSAGE` | некорректная запись ленты | оператор: «разобрано» + комментарий |
| `RESULT_CONFLICT` | тот же `sequence`, другое содержимое | решение оператора |
| `RECONCILIATION_CONFLICT` | сверка нашла разные итоги | решение оператора |
| `PAYLOAD_CONFLICT` | `operationId` уже был с другими данными | решение оператора |

- Статусы проблемы: `OPEN` → `RESOLVED`. Хранится, кто закрыл (система или оператор), когда, решение и комментарий.
- У заявки не больше одной открытой проблемы каждого вида (ограничение в БД).
- Список проблем видит только оператор, по своей службе. Фильтры по виду и статусу, по умолчанию открытые, новые сверху.

**Действия оператора:**

| Действие | Когда доступно | Что делает |
|---|---|---|
| Повторить отправку | доставка `FAILED` или `UNKNOWN` | сброс счётчика, отправка «сейчас», `operationId` прежний |
| Сверить сейчас | любая заявка | сверка по одной заявке, исход сразу в ответе |
| Решить конфликт | открыта проблема `*_CONFLICT` | «принять результат перевозчика» или «оставить наш», комментарий обязателен |
| Отметить «разобрано» | открыта проблема `INVALID_MESSAGE` | закрыть проблему, комментарий обязателен |

- Недоступное действие — `409 INVALID_STATE`.
- Каждое действие принимает `Idempotency-Key`.
- Решение записывается в историю.

## 8. История и журнал

**История (NF05, D-NF03):**
- `audit_log` — действия людей: кто, когда, объект, действие, было → стало;
- история обмена — `exchange_attempt`, `inbox`, исходы сверки;
- в карточке заявки всё сводится в одну ленту событий;
- инициатор видит свои действия и смену статусов, техническую часть видит только оператор службы;
- история не удаляется и не меняется.

**Технический журнал (NF10):**
- JSON в Docker (структурированное логирование Spring Boot), текст при локальной разработке;
- в каждой строке id запроса, пользователь, `operationId`;
- обязательно пишутся: входы и отказы во входе, попытки отправки и их исходы, переходы статусов доставки, применённые, отсеянные и некорректные сообщения, исходы сверки, действия оператора;
- пароли, cookie сессии, токены и `Authorization` не пишутся никогда, это проверяется тестом.

## 9. Реестр заявок (основа NF08)

- `GET /api/requests?businessStatus=&deliveryStatus=&overdue=&page=0&size=20&sort=createdAt,desc`.
- Размер страницы до 100, по умолчанию новые сверху.
- Нагрузочный тест фильтрует по `businessStatus`.
- Операции профиля NF08:

  | Операция профиля | Запрос |
  |---|---|
  | список | `GET /api/requests?businessStatus=…` |
  | карточка | `GET /api/requests/{id}` |
  | создание | `POST /api/requests` (сразу уходит перевозчику) |
  | изменение | `PATCH /api/requests/{id}`: ответственный или комментарий |

## 10. Допущения для README

- Содержимое заявки неизменяемо с момента создания. Отмены заявки нет.
- Сессия хранится в памяти: после перезапуска нужно войти заново.
- Оператор не создаёт заявки.
- Единственное автоматическое правило сверки — `EXTERNAL_AHEAD`. Все остальные расхождения решает оператор.
