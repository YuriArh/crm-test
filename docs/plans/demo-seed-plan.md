# План: демо-данные со сбоями и ручная проверка расхождений

Основание: спека `docs/specs/demo-seed.md` (v2, согласована 17.11.2026, вариант (b)). Ветка `demo-seed` от `main`.
Один шаг — один коммит.

## 0. Исходное состояние и как проверяется

- `scripts/seed.sh` создаёт 7 заявок (4 «Север», 3 «Юг»), правит три из них, печатает итоги. Помощники: `login`,
  `call`, `create` (пустой id при `IDEMPOTENCY_KEY_REUSED`), `final_card` (30 с), `patch`. `trap` убирает только
  временный каталог. К эмулятору сид не обращается.
- `Makefile`: `seed: wait` → `./scripts/seed.sh $(E2E_BASE_URL)`. `CARRIER_BASE_URL` в цели не передаётся.
- Код `dispatch`, эмулятора, контракты, миграции и web не меняются (спека §5).

**Тесты.** Сид — сценарий стенда, а не продуктовый код (спека §4): модульных, интеграционных и e2e тестов у него
нет, поведение, которое он показывает, покрыто тестами спек (a), (b), (w). Правило «сначала красный тест» здесь
заменяется проверкой шага на стенде, записанной в каждом шаге **до** кода: что запустить и что увидеть. Сначала
убеждаемся, что на текущем сиде ожидание не выполняется (красное), затем пишем код до выполнения (зелёное).

Проверки каждого шага, кроме docs:
- `bash -n scripts/seed.sh`;
- ShellCheck в Docker, как Redocly для контрактов:
  `docker run --rm -v "$PWD:/mnt" -w /mnt koalaman/shellcheck:v0.10.0 scripts/seed.sh` — без предупреждений;
- прогон на стенде, указанный в шаге. «Чистый стенд» — `make reset && make up` (сид рассчитан на пустую базу).

## Шаг 2. Эмулятор в сиде: выключение режимов при входе и выходе

**Ожидание (красное сейчас):** `make fault-unavailable && make seed` — сид падает на ожидании итога (`got no result in
30 s`), режим остаётся включённым (`make faults`).

**Код:**
- `CARRIER="${CARRIER_BASE_URL:-http://localhost:8081}"`; `Makefile`: `CARRIER_BASE_URL=$(CARRIER_BASE_URL) ./scripts/seed.sh …`
  (переменная в `Makefile` уже есть и учитывает `CARRIER_PORT`, её же берут `make e2e` и `make fault-*`).
- `set_faults '<json>'` — `PUT $CARRIER/admin/faults` объектом целиком (все пять полей; переданные — `true`);
  `faults_off`; ошибка эмулятора → сообщение и выход.
- Вход: прочитать `GET /admin/faults`, если что-то включено — напечатать что, затем `faults_off`.
- Выход: `trap` на `EXIT` (а `INT`/`TERM` → `exit`, чтобы сработал `EXIT`) делает `faults_off` и удаляет
  временный каталог. Ошибка выключения при выходе печатается, но код выхода не подменяет.

**Проверка:** `make fault-unavailable && make seed` на чистом стенде — сид печатает «включены: unavailable»,
выключает, создаёт 7 заявок как раньше; `make faults` — всё выключено. `make fault-duplicate`, `make seed`, `Ctrl+C`
в первые секунды — режимы выключены.

## Шаг 3. Ожидание и «заявка уже была»

**Ожидание (красное сейчас):** нечего наблюдать снаружи: это помощники следующих шагов; поведение обычных 7 заявок не
меняется.

**Код:**
- `RUN_STARTED` — `serverTime` из `GET /api/system/info` в начале.
- `create` возвращает id и признак «новая»: новая — `201`/`200` с `createdAt ≥ RUN_STARTED`; «была» — `200` с более
  ранним `createdAt` или `IDEMPOTENCY_KEY_REUSED` (тогда id нет).
- `wait_card <user> <id> <jq-условие> <секунд> <что ждём>` — опрос карточки раз в 1 с; по истечении — сообщение с
  номером заявки, ожиданием и последним состоянием (`businessStatus`, `deliveryStatus`, `exchange.attempts`, виды
  проблем) и выход с ошибкой. `final_card` — через него (условие «итог», 30 с, как сейчас).
- Перед сценариями — ожидание итога всех 7 обычных заявок (спека §2.2 п. 1).

**Проверка:** чистый стенд, `make seed` — вывод и данные как до шага; повторный `make seed` — «already created»,
ничего нового. Сломанное условие (временно `wait_card … 'false' 3`) — ошибка с последним состоянием, режимы выключены.

## Шаг 4. Сценарии `seed-north-5…7`

**Ожидание (красное сейчас):** после `make seed` на чистом стенде 7 заявок; ни у одной нет закрытой проблемы
«Неизвестно, получена ли заявка», `make inbox` без `duplicate_count`, у операций `receivedCount = 1`.

**Код:** `scenario <ключ> <режимы> <условие точки> <груз> …`: режимы → создание (если заявка была — режимы выключить,
напечатать состояние, дальше) → `wait_card` до точки (90 с) → `faults_off` → `wait_card` до итога (90 с).
- `seed-north-5`: `unavailable`, точка `.exchange.attempts >= 2`;
- `seed-north-6`: `loseResponse` + `delayed`, точка `.deliveryStatus == "UNKNOWN" or any(.problems[]; .kind == "DELIVERY_UNKNOWN")`;
- `seed-north-7`: `duplicate`, точка `.deliveryStatus == "ACKNOWLEDGED"`.
Грузы, адреса и сроки — обычные, с исходом «Выполнена» (не «тест-отказ», вес меньше 10 000 кг).

**Проверка:** чистый стенд, `make seed`:
- `seed-north-5`: «Выполнена», «Попыток отправки» ≥ 3, проблем нет; в логе эмулятора `Fault unavailable`;
- `seed-north-6`: «Выполнена», в «Закрытых проблемах» «Неизвестно, получена ли заявка · Закрыта системой»;
  `make carrier-ops` — `receivedCount = 2`, `executionCount = 1`;
- `seed-north-7`: «Выполнена»; `make inbox` — у итога `duplicate_count ≥ 1`;
- `make faults` — всё выключено. Повторный `make seed` — три сценария пропущены, новых `Fault …` в логе нет.

## Шаг 5. Сценарий `seed-north-8` и «Сверить сейчас»

**Ожидание (красное сейчас):** `/problems` под `north.operator` пуст; в «Сверках» ни одной ручной проверки.

**Код:** `seed-north-8`: `malformed`, точка `.businessStatus == "IN_PROGRESS"` → `faults_off` → `POST
/api/requests/{id}/reconcile` под `north.operator` с `Idempotency-Key: seed-north-8-reconcile` (ответ `200`, печать
`outcome`; `outcome` не `EXTERNAL_AHEAD` — предупреждение с `details`, не ошибка: заявку могла забрать фоновая
сверка, если запуск шёл дольше 2 минут) → `wait_card` до итога. Если заявка была — сверка не вызывается.

**Проверка:** чистый стенд, `make seed`, экраны под `north.operator`:
- карточка `seed-north-8`: «Выполнена»; под панелью обмена «Сверки», первая строка «Итог получен сверкой · вручную ·
  Оператор (Север)»; открыта «Некорректное сообщение перевозчика»;
- `/problems`: одна открытая, счётчик шапки 1; реестр с «Есть открытые проблемы» — только `seed-north-8`, значок 1;
- `make carrier-ops` — у всех `executionCount = 1`.

## Шаг 6. Итоговая таблица

**Ожидание (красное сейчас):** вывод сида без статуса доставки и проблем.

**Код:** таблица по всем заявкам сида (спека §2.4): номер, автор, бизнес-статус, номер отправления или причина,
статус доставки, открытые проблемы (виды; для «Севера» — из карточки оператора, для «Юга» — «—»). Пропущенные заявки
(id неизвестен после `IDEMPOTENCY_KEY_REUSED`) — строкой «создана раньше». Затем напоминание про `make carrier-ops`.

**Проверка:** чистый стенд, `make seed` — 11 строк, у `seed-north-8` открытая `INVALID_MESSAGE`; повторный запуск в
тот же день — те же 11 строк.

## Риски

| Риск | Что делаем |
|---|---|
| Окно `UNKNOWN` у `seed-north-6` (~5 с) проскочило между опросами | условие точки принимает и проблему `DELIVERY_UNKNOWN` (спека §2.1) |
| Пауза чтения ленты после `unavailable` (до 30 с) задерживает итоги следующих сценариев | сценарии строго по одному, ожидание итога до 90 с, следующий режим — только после итога |
| `make seed` на непустом стенде, где тестировщик уже включал режимы или создавал заявки | режимы выключаются при входе; сценарии существующих заявок пропускаются; таблица показывает фактическое состояние |
| Сид упал посреди сценария с включённым режимом | `trap EXIT` выключает режимы; проверка `Ctrl+C` в шагах 2 и 8 |
| Ручные проверки 8.1–8.4 на стенде расходятся с ожиданиями спеки | шаг 7 правит документ; если расходится с поведением продукта — стоп и обсуждение, без правок кода в этой работе |
