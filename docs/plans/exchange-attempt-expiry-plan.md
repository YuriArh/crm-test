# План: срок жизни попытки обмена

Основание: `docs/dispatch-design.md` §5, пункт «Срок жизни попытки», и §8 (решение принято 15.11.2026, вариант 1
из разбора). Отдельной спеки нет: изменение внутреннее, контракт и интерфейс не меняются.
Ветка: `attempt-expiry` от `main`. Делается **до** спеки restart-check: её сценарий 1 опирается на это исправление.

## 0. Проблема и исходное состояние

- Попытка (`exchange_attempt`) открывается при захвате операции (`SendWorker.claim`, `started_at` = момент
  захвата) и закрывается воркером после ответа (`ExchangeAttemptDao.finish`, только если `finished_at IS NULL`).
- Если воркер умер посреди вызова, попытку закрывает только `finishInterrupted`. Его вызывают лишь для
  операций, которые `SendQueueDao.recoverExpired` нашёл в `SENDING` с истёкшим захватом.
- Если до истечения захвата операцию увёл из `SENDING` кто-то другой (сейчас результат из ленты:
  `ResultInbox` → `ACKNOWLEDGED`, захват снят), попытка остаётся с `finished_at IS NULL` навсегда.
  На этапе 2 таких путей станет больше: повтор оператором, сверка, решение конфликта.
- Решение: у попытки собственный срок, равный захвату (`app.exchange.lease`, 60 с). Попытка закрывается по
  своему возрасту, статус операции не важен.

## Шаг 1. Закрытие попыток по сроку (один коммит)

**Что делаем**
- Миграция `V6__exchange_attempt_open_index.sql`: частичный индекс
  `exchange_attempt_open_idx ON exchange_attempt (started_at) WHERE finished_at IS NULL`. Проход восстановления
  идёт раз в секунду, а незакрытых попыток единицы, поэтому полный просмотр таблицы на каждом проходе недопустим (NF08).
- `ExchangeAttemptDao`: `finishInterrupted(Collection<UUID>, Instant)` заменяется на
  `int finishExpired(Instant now, Instant startedBefore)`:
  `UPDATE exchange_attempt SET finished_at = :now, outcome = 'UNKNOWN', error = 'Send was interrupted (lease expired)'
  WHERE finished_at IS NULL AND started_at < :startedBefore`.
  Условие строгое (`<`), так же как `locked_until < :now` в `recoverExpired`: попытка и её захват истекают в один
  и тот же проход. `duration_ms` и `http_status` остаются пустыми: ответа не было, а длительность неизвестна.
- `SendWorker.recover()`: в той же транзакции сначала `queue.recoverExpired(now)` (как сейчас), затем
  `attempts.finishExpired(now, now.minus(lease))`. Журнал (NF10):
  - восстановленные операции: как сейчас, `WARN` с числом;
  - закрытые попытки: `WARN` «Closed N exchange attempt(s) left open past the lease». В журнал попадает и
    случай, когда операция уже ушла из `SENDING`; по нему видно, что воркер падал.
- `finish` не меняется: условие `finished_at IS NULL` уже не даёт опоздавшему воркеру перезаписать исход.
  Максимальная длительность вызова (соединение 2 с + ответ 5 с) намного меньше срока, поэтому живую попытку
  правило не закрывает. Это верно только при захвате прямо перед вызовом, см. шаг 2. Комментарий в `ExchangeProperties.lease` дополнить: срок захвата одновременно является
  сроком жизни попытки и должен быть больше `connect-timeout + read-timeout`.

**Тесты**
- Интеграционные, `SendWorkerTests` (настоящая БД, `FakeCarrier`, `MutableClock`):
  1. *Падение, затем результат из ленты.* Операция в `SENDING` с живым захватом и открытой попыткой (воркер
     только что упал). Результат приходит через `ResultInbox.accept` в транзакции, так же как его вызывает опрос
     ленты. Сам `FeedPoller` здесь не используется: его пауза при недоступности переходит между тестами.
     Операция становится `ACKNOWLEDGED` через `RESULT`. Часы на 61 с вперёд, `worker.runOnce()`. Ожидаем: попытка 1 закрыта
     (`UNKNOWN`, «Send was interrupted (lease expired)»), операция осталась `ACKNOWLEDGED`, `attempts = 1`,
     перевозчик повторной отправки не получил.
  2. *Падение, затем истёк захват.* Это существующий тест `sendInterruptedByACrashIsRecoveredAsUnknownAndResent`:
     должен остаться зелёным без изменений сценария. Дополнительно проверить текст ошибки закрытой попытки.
  3. *Живая попытка не трогается.* Операция уже `ACKNOWLEDGED`, попытка открыта 59 с назад, затем ровно 60 с
     назад: после `runOnce()` она по-прежнему открыта. Через 61 с закрыта.
  4. *Опоздавший воркер не перезаписывает исход.* Попытка закрыта по сроку, затем `finish` с исходом
     `ACKNOWLEDGED`: в строке остаются `UNKNOWN` и прежние `finished_at` и `error`.
- `SchemaMigrationTests`: ожидаемый список версий `1…6`; индекс существует и он частичный
  (`pg_indexes.indexdef` содержит `WHERE (finished_at IS NULL)`).
- Unit-тестов нет: правило целиком в SQL-условии, а проверять его имеет смысл только на настоящей БД.
- E2E нет: живой стенд нельзя уронить посреди отправки, не останавливая `dispatch`, а `make e2e` контейнеры не
  трогает. На стенде случай покажет restart-check (сценарий 1). Существующие `ExchangeE2ETest` и
  `ExchangeFaultsE2ETest` прогоняются как проверка регрессии.

**Готово, когда:** `./gradlew build` зелёный, затем `make reset && make up && make e2e` зелёный. `reset` нужен,
только если на локальной БД уже есть неприменённая версия V6; иначе достаточно `make up`.

## Шаг 2. Захват по одной операции прямо перед отправкой (по итогам ревью шага 1)

**Проблема.** `claim()` захватывает до 20 операций разом: всем ставит `locked_until = T + 60 с` и открывает
попытки с `started_at = T`. Потом `send()` отправляет их по одной, до 7 с на вызов. Пачка может длиться ~140 с, и
при нескольких экземплярах другой экземпляр через 60 с сочтёт живые операции конца пачки брошенными. Он закроет их
попытки как прерванные (настоящий исход потеряется) и заберёт операции на повторную отправку. Захват операций был
устроен так и до шага 1, шаг 1 распространил это на попытки. Решение принято 15.11.2026: канонический паттерн
очереди, последовательный воркер захватывает по одной (`docs/dispatch-design.md` §5, «Отправка»).

**Что делаем**
- `SendQueueDao.claimDue(now, leaseUntil, limit)` → `claimNext(now, leaseUntil)`: тот же условный `UPDATE … FROM`
  с `FOR UPDATE SKIP LOCKED LIMIT 1`, возвращает `Optional<Claimed>`. Сортировка внешнего запроса больше не нужна.
- `SendWorker.runOnce()`: `recover()`, затем цикл до `sendsPerPass` раз: в одной транзакции `claimNext` и
  `attempts.start`, затем вызов вне транзакции, затем запись исхода. Если `claimNext` ничего не вернул, проход
  заканчивается. Возвращает число отправленных, как сейчас.
- Длительность попытки считается от того же момента, что записан в `started_at` (момент захвата). Сейчас в
  `send()` берётся отдельный `calendar.now()`, и `started_at`, `finished_at` и `duration_ms` могут расходиться.
- `ExchangeProperties.sendBatchSize` переименовать в `sendsPerPass` (`app.exchange.sends-per-pass`, по
  умолчанию 20): пачки больше нет, старое имя вводило бы в заблуждение. Найти и поправить все использования.
- Мелкие замечания ревью:
  - `WARN` о восстановленных операциях: число и первые 10 `operationId`, а не весь список;
  - `CLAUDE.md`: «Flyway V1–V5» → «V1–V6»;
  - тесты: импорты вместо полных имён `java.time.*`, время через `SqlTime.toSql`.

**Тесты**
- Интеграционные, `SendWorkerTests`:
  1. *Опоздавший воркер* (заменяет тест с прямым вызовом `finish`). Настоящая отправка с хуком
     `FakeCarrier.duringSubmit`, срабатывающим один раз: внутри вызова часы сдвигаются на 61 с и запускается
     `worker.runOnce()`, как если бы это был второй экземпляр. Он закрывает попытку 1 по сроку, переводит операцию
     в `UNKNOWN` и отправляет попытку 2. Потом первый вызов возвращает `202`. Ожидаем: попытки
     `1:UNKNOWN` («Send was interrupted») и `2:ACKNOWLEDGED:202`, исход первого вызова ничего не перезаписал.
  2. *Захват прямо перед вызовом.* Три готовые операции, хук `duringSubmit` на каждом вызове сдвигает часы на 7 с.
     Ожидаем: у каждой попытки `started_at` — момент начала её вызова (T, T+7, T+14), у каждой операции
     `locked_until` при захвате равен `started_at + 60 с`, `duration_ms` соответствует `finished_at − started_at`.
  3. *Предел прохода.* Готовых операций больше `sendsPerPass`: за проход отправлено ровно `sendsPerPass`, остальные
     в следующем. Готовых нет: проход ничего не захватывает.
  4. Существующие `batchIsSentInDueOrder` (переименовать: порядок отправки по сроку) и
     `parallelWorkersNeverSendOneOperationTwice` должны остаться зелёными: по одной, но в порядке
     `next_attempt_at` и без двойной отправки при параллельных воркерах.
- Unit и E2E: как в шаге 1. Существующие обменные e2e прогоняются как проверка регрессии.

**Готово, когда:** `./gradlew build` зелёный, затем `make up && make e2e` зелёный.

Шаги 1 и 2 коммитятся вместе: шаг 1 без шага 2 даёт ложные «прерванные» попытки при нескольких экземплярах.

## 1. Вне объёма

- Отображение попыток в истории карточки: этап 2, п. 5–6 (`docs/PLAN.md`).
- Неизменяемый журнал попыток (вариант 4 из разбора): ТЗ его не требует, решение записано в design §8.
- Пульс воркера (heartbeat): вызов длится не больше 7 с, отдельный механизм не нужен.
- Спека и команды restart-check: следующий шаг после этого плана.
