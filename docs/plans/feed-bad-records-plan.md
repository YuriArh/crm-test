# План: плохие записи ленты не останавливают получение результатов

Основание: спека `docs/specs/feed-bad-records.md` (опрос Q1–Q31). Ветка `feed-bad-records` от `main`.
Работа по TDD: в каждом шаге сначала пишутся тесты шага и запускаются, чтобы увидеть, что они падают **по нужной
причине** (красные), затем код до зелёного, затем рефакторинг. Рабочего кода без падающего теста нет. Один шаг — один
коммит; после каждого шага проходит гейт шага.

Порядок шагов: сначала устройство (два шага приёма и разбора), потом строгая проверка. Устройство само по себе
гарантирует, что лента не встаёт; проверка после него только уточняет причины отказа.

## 0. Исходное состояние

- `FeedPoller.process` в одной транзакции блокирует закладку, вызывает `ResultInbox.accept` на каждую запись и
  сдвигает закладку. `ResultInbox.accept` (`Propagation.MANDATORY`) разбирает запись `ResultMessage.parse`,
  пишет строку `inbox` (`payload jsonb`) и применяет результат.
- В рабочем дереве лежат незакоммиченные временные тесты ревью: `ReviewFeedFindingsTests` (пункты 1, 2, 7) и
  `ReviewSendFindingsTests` (пункт 3, не этой работы). Первый разбирается по шагам 2–4 и удаляется; второй в ветку
  не коммитится и ждёт своей спеки.
- Тестовые помощники: `FakeCarrier` (лента отдаёт записи без `feedSeq` всегда — удобно для проверки конверта),
  `TestFeed`, `TestRequests`, `MutableClock`, `TestRows`. Результат «из ленты» в тестах сейчас подаётся вызовом
  `inbox.accept(...)` в транзакции (`ResultInboxTests`, `SendWorkerTests`).

## Шаг 2. Конверт пачки и пауза без метода сброса

**Что делаем**
- Чистая функция проверки конверта (`exchange/feed/FeedEnvelope`): по закладке и пачке возвращает «годна» или
  причину нарушения (элемент не объект; нет целого `feedSeq` или он вне `1 … Long.MAX_VALUE`, проверка
  `canConvertToLong` до чтения; первый номер не больше закладки; номера не возрастают). Пропуски допустимы.
- `FeedPoller`: перед транзакцией пачки проверить конверт. Нарушение — ничего не писать, пауза по той же схеме, что
  при недоступности (1 → 30 с), `ERROR` «Feed protocol violated after <cursor>: <причина>» (журнал отличает его от
  «unavailable»). Ветка «no readable feedSeq; the cursor cannot move» с коммитом без сдвига закладки удаляется.
- `FeedPoller.resetPause()` удаляется из рабочего кода.
- Тесты, которые вызывают паузу (недоступность, нарушение протокола), сами снимают её в конце: часы за пределы паузы
  и успешный проход (`resume()` сбрасывает её штатно). `@BeforeEach` больше ничего у поллера не сбрасывает.

**Тесты (сначала красные)**
- Unit `FeedEnvelopeTest`: годная пачка; пропуски номеров; элемент не объект; нет `feedSeq`; `feedSeq` строкой;
  `feedSeq` больше `Long.MAX_VALUE`; первый номер равен закладке и меньше её; номера равны и убывают; пустая пачка.
- Интеграционные `FeedPollerTests`:
  - пачка с записью без `feedSeq` (из `ReviewFeedFindingsTests.finding2…`, ожидания перевёрнуты): ничего не
    сохранено в `inbox`, закладка на месте, следующий `runOnce()` до конца паузы ничего не читает, после сдвига часов
    за паузу — снова проверяет;
  - пачка с убывающими номерами: то же;
  - существующие тесты недоступности переписаны без `resetPause()`; весь класс зелёный в любом порядке запуска.
- E2E: нет новых (испорченный конверт эмулятор не выдаёт); существующие — как регрессия.

**Готово, когда:** `./gradlew build` зелёный, `make up && make e2e` зелёный; `resetPause` нет в `src/main`.

## Шаг 3. Два шага: приём и разбор

**Что делаем**
- Миграция `V7__inbox_two_step.sql` по спеке §7 (тип `payload`, колонки `attempts` / `next_attempt_at` /
  `last_error`, статусы, ограничения `inbox_attempts_non_negative`, `inbox_received_has_next_attempt`,
  `inbox_feed_has_feed_seq`, индексы `inbox_feed_seq_unique`, `inbox_due_idx`). `attempts` добавляется по правилу
  nullable → заполнение `0` → `SET NOT NULL`.
- Приём (`ResultInbox.receive`, внутри транзакции вызывающего, как сейчас `accept`): на каждую запись — повтор
  `messageId` → `duplicate_count + 1`; иначе вставка `RECEIVED` с исходным текстом, `feed_seq`, «чистым»
  `messageId` (спека §3.3, иначе `NULL`), `next_attempt_at = now`. Содержимое записи не разбирается.
- Разбор (`exchange/inbox/InboxProcessor.processDue()`): пока есть подошедшие записи — в своей транзакции захватить
  одну (`FOR UPDATE SKIP LOCKED LIMIT 1`, порядок `received_at, feed_seq`), разобрать и решить, как сейчас
  (`ResultMessage`, `ResultRules`, `lockTarget`, `applyToRequest`, `applyToOperation`), записать итог и разобранные
  поля. При исключении — откат и новая транзакция по спеке §4.3:
  - `DataIntegrityViolationException` → `INVALID`, причина «rejected by the database: …»;
  - иначе `attempts + 1`, `last_error`, `next_attempt_at` по политике повторов, после последней — `FAILED`;
  - если и эта запись не удалась — проход разбора останавливается (`ERROR`), попытка не засчитана.
- Политика повторов: `RetryPolicy` получает параметр разброса (0.2 для отправки, как сейчас; 0 для разбора), второй
  экземпляр — из `app.exchange.inbox-max-attempts` / `inbox-initial-backoff` / `inbox-max-backoff` (5, 1 с, 1 мин).
- Причины и журнал: значения из записи экранируются (`\uXXXX`) и обрезаются до 200 символов (спека §4.5);
  `INVALID` — `WARN`, `FAILED` — `ERROR`, временная ошибка — `WARN` с номером попытки.
- `FeedPoller.runOnce()`: приём всех доступных пачек (как сейчас, транзакция пачки с блокировкой закладки), затем
  `InboxProcessor.processDue()`. `ResultInbox.accept` удаляется.
- Тестовая поддержка: шпион `@MockitoSpyBean InboxDao` объявляется в общей конфигурации `@IntegrationTest`
  (контекст остаётся один), сбрасывается после каждого теста; помощник `TestResults.deliver(entry)` (приём в
  транзакции + разбор) заменяет прямые вызовы `inbox.accept(...)` в `ResultInboxTests` и `SendWorkerTests`.

**Тесты (сначала красные)**
- Unit `RetryPolicyTest`: без разброса паузы ровно 1, 2, 4, 8 с, потолок 1 мин, `canRetry` ложно после 5-й;
  с разбросом — как сейчас.
- Интеграционные `FeedPollerTests` (из `ReviewFeedFindingsTests.finding1…`, ожидания перевёрнуты):
  - цена `10000000000000.00` перед нормальной записью другой заявки: нормальная применена, закладка на последнем
    номере, плохая не `RECEIVED` (здесь она `INVALID` от базы; после шага 4 — от проверки);
  - `\u0000` в `reason`: то же; исходный текст в `payload` сохранён и читается обратно с `\u0000`;
  - огромный `sequence` перед нормальной записью: нормальная применена (статус плохой проверяется в шаге 4);
  - `\u0000` в `messageId`: приём не падает, `message_id` пустой, запись `INVALID`;
  - повтор `messageId` на другой позиции: новой строки нет, `duplicate_count = 1`.
- Интеграционные, новый `InboxProcessorTests`:
  - только приём (без разбора), затем разбор следующим проходом: результат применён один раз, `version + 1` один раз;
  - шпион бросает `DataIntegrityViolationException` в `applyToRequest`: запись `INVALID` с причиной, заявка не
    изменена, следующая запись применена;
  - шпион бросает `RuntimeException` 2 раза: после первого прохода `attempts = 1`, `next_attempt_at = now + 1 с`;
    раньше срока запись не берётся; после сдвига часов — `attempts = 2`, пауза 2 с; третий проход — `APPLIED`;
  - шпион бросает 5 раз: после 5-го — `FAILED`, причина «processing failed 5 times: …», `next_attempt_at` пустой,
    остальные записи разобраны;
  - шпион бросает и при применении, и при записи повтора (как недоступная база): проход остановлен, `attempts` не
    изменился, запись осталась `RECEIVED`; следующий проход разбирает её;
  - два параллельных `processDue()` на 20 записях: каждая разобрана ровно один раз (число `APPLIED` = 20, у заявок
    `version` выросла на 1).
- Интеграционные `ResultInboxTests`, `SendWorkerTests`: все существующие сценарии (дубль, `STALE`, `CONFLICT`,
  незнакомая операция, подтверждение доставки результатом) — через `TestResults.deliver`, ожидания прежние.
- `SchemaMigrationTests`: список версий `1…7`; каждое новое ограничение отвергает неверную строку
  (`attempts < 0`; `RECEIVED` без `next_attempt_at`; `APPLIED` с `next_attempt_at`; `FEED` без `feed_seq`;
  повтор `feed_seq` у `FEED`); перевод `jsonb` → `text`: Flyway с целью `6` в отдельной схеме того же контейнера,
  вставка строки, миграция до `7`, текст совпадает с исходным JSON.
- E2E: новых нет; все существующие обменные e2e (`ExchangeE2ETest`, `ExchangeFaultsE2ETest`) проходят — каждый
  результат на стенде теперь идёт через приём и разбор.

**Готово, когда:** `./gradlew build` зелёный, `make up && make e2e` зелёный.

## Шаг 4. Строгая проверка и пределы

**Что делаем**
- `contracts/carrier-api.yaml`: пределы спеки §6 в схемах `OperationResult` / `ResultEntry` (`minimum`/`maximum`,
  `multipleOf: 0.01` для цены, `minLength`/`maxLength`, `pattern` без управляющих символов, `format: int32/int64`).
  `make contracts-lint`.
- `ResultMessage.parse`: проверка ровно этих пределов; числа — на диапазон до преобразования; ни на каком входе не
  бросает исключений. Порядок причин сохраняется (первая найденная).
- Миграция `V8__result_field_lengths.sql`: `delivery_request_tracking_number_length` (≤ 64),
  `delivery_request_rejection_reason_length` (≤ 1000).
- `ReviewFeedFindingsTests` удаляется: все его сценарии к этому шагу перенесены.

**Тесты (сначала красные)**
- Unit `ResultMessageTest`: для каждого поля значение на границе (годно) и за ней (`INVALID` с причиной):
  `messageId` 100/101 символ; `sequence` 2147483647 / 2147483648 / 4294967297; `feedSeq` за `Long.MAX_VALUE`;
  цена 9999999999.99 / 10000000000.00 / 1.234 / −0.01; `trackingNumber` 64/65; `reason` 1000/1001; `\u0000`,
  `\u001F`, `\u007F` в каждой строке; ни один вход из набора не бросает исключение.
- Интеграционные `FeedPollerTests`: огромный `sequence` и цена сверх предела — `INVALID` **с причиной проверки**
  (а не базы), лента идёт дальше.
- `SchemaMigrationTests`: список версий `1…8`; `tracking_number` в 65 символов и `rejection_reason` в 1001
  отвергаются.
- Эмулятор: существующие тесты с `Contract.matchesContract()` зелёные с новыми пределами (его записи укладываются).
- E2E: новых нет; существующие — как регрессия.

**Готово, когда:** `./gradlew build` зелёный, `make contracts-lint` зелёный, `make up && make e2e` зелёный.

## Шаг 5. Режим сбоя эмулятора `malformed`

**Что делаем**
- `docs/specs/carrier-faults.md`: новый режим по спеке §9 (§2 таблица «когда применяется», §3.5, §6 контракт,
  §7 команды, §8 ожидаемое поведение, §9 тесты, §11 демо).
- `contracts/carrier-api.yaml`: обязательное поле `Faults.malformed`; описание `PUT /admin/faults` — режим
  сознательно нарушает контракт ленты. `make contracts-lint`.
- Эмулятор: выключатель в `FaultModes` / `Faults`; при чтении ленты (`GET /results`) при включённом режиме цена
  каждой записи `SUCCEEDED` в ответе заменяется на `10000000000000.00`, `WARN` «Fault malformed: …» с `messageId` и
  `operationId`. База, исполнитель, `GET /operations/{id}`, `GET /admin/operations` не меняются; миграций нет.
  `unavailable` по-прежнему отвечает раньше всего.
- `Makefile`: `make fault-malformed`; остальные `fault-*` и `fault-off` передают пять полей.
- E2E-клиент эмулятора: выключение всех режимов включает `malformed`.

**Тесты (сначала красные)**
- Интеграционные эмулятора:
  - `PUT /admin/faults` без `malformed` → `400`; с пятью полями — состояние возвращается;
  - режим включён: у `SUCCEEDED` в `GET /results` цена испорчена, `IN_PROGRESS` и `REJECTED` без изменений;
    проверка ответа по контракту даёт ошибку ровно в цене испорченной записи (валидатор контракта вызывается
    напрямую и проверяется список ошибок); при выключенном — ответ соответствует контракту;
  - база (`feed_entry.price`), `GET /operations/{id}` и `GET /admin/operations` показывают настоящую цену;
  - с `duplicate` испорчены обе копии; с `unavailable` — `503`;
  - журнал содержит `Fault malformed` с `operationId`.
- E2E:
  - `CarrierFaultsE2ETest`: режим включён — цена итога в ленте `10000000000000.00`, `GET /operations/{id}` —
    настоящая; выключен — настоящая и в ленте;
  - `ExchangeFaultsE2ETest`: включить `malformed`, создать заявку А с уникальным описанием, дождаться в карточке
    `IN_PROGRESS`; выключить, создать заявку Б, дождаться `SUCCEEDED`; карточка А по-прежнему `IN_PROGRESS`.
    До кода эмулятора оба e2e красные, потому что режима нет (`400` на `PUT /admin/faults`). То, что без шагов 2–4
    лента встала бы, уже доказали интеграционные тесты шага 3.

**Готово, когда:** `./gradlew build` зелёный, `make contracts-lint` зелёный, `make up && make e2e` зелёный.
