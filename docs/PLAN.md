# План работ — «Обмен с внешней системой»

Основание: `04-system-integration.md` (ТЗ v2.1).

Подход: сначала **базовый работающий функционал** (бэкенд → эмулятор → фронтенд → сквозной сценарий). Только после этого — остальные требования ТЗ: надёжность, права, аудит, нагрузка, тесты, документация.

Предыдущая подробная версия плана: `docs/archive/PLAN-v1.md`. Подробные решения по `dispatch`: `docs/dispatch-design.md`.

## Исходные решения

- Стек: Java 25 + Spring Boot, PostgreSQL, React + TypeScript + Vite, Docker Compose.
- Предметная область: заявка на доставку груза (груз, вес, адрес, срок). Вымышленная служба доставки возвращает номер отправления и стоимость либо отказ.
- Жизненный цикл: «Создать» (заявка сохраняется и сразу ставится в очередь) → исполнение → результат. Черновика нет, содержимое неизменяемо.
- Результаты приложение забирает у эмулятора опросом ленты (pull).
- Репозиторий: Gradle multi-project для Java (`dispatch`, `carrier-emulator`), `web/` — отдельный npm-проект, Docker Compose и Makefile поверх. Turborepo и Nx не используются.
- Именование: основное приложение — `dispatch` (принимает заявки, передаёт их перевозчику, отслеживает доставку и результат, сверяет), эмулятор — `carrier-emulator` (изображает внешнего перевозчика).
- Фронтенд и API доступны с одного origin: в разработке через proxy Vite, в Docker через nginx (сессионные cookie без CORS).
- `dispatch` и `carrier-emulator` не делят Java-классы; контракт описан в `contracts/` (OpenAPI).

## Структура репозитория

```
dispatch/          Spring Boot: API и фоновые обработчики
carrier-emulator/  эмулятор внешнего перевозчика (отдельное приложение, своя БД)
contracts/         OpenAPI-контракты
web/               React + TS + Vite (позже)
docs/              план и документация
docker-compose.yml, Makefile, settings.gradle.kts, build.gradle.kts
```

# Этап 1. Базовый функционал

## 1. Бэкенд

- Каркас Spring Boot, подключение к PostgreSQL, миграции схемы.
- Демо-пользователи и простой вход (два инициатора, оператор).
- Заявки:
  - создание: сохраняет заявку и в той же транзакции ставит её в очередь на отправку; обязательный `Idempotency-Key`;
  - изменение ответственного и комментария с проверкой `version`;
  - список заявок с фильтром и страницами;
  - карточка заявки.
- Фоновая отправка заявок в эмулятор.
- Фоновый опрос ленты эмулятора и применение результатов через единый обработчик.
- У заявки два статуса: доставка и бизнес-результат.

**Готово, когда:** через curl можно создать заявку и увидеть, как она уходит перевозчику и получает результат.

## 2. Эмулятор

- Отдельное Spring Boot приложение со своей базой.
- Принимает заявку, исполняет (выдаёт номер отправления и стоимость или отказ), сохраняет у себя.
- Отдаёт результаты приложению по запросу.
- Показывает своё состояние: список операций и сколько раз каждая исполнена.

**Готово, когда:** приложение отправляет заявку, эмулятор её исполняет, приложение получает результат.

## 3. Фронтенд

- Вход.
- Реестр заявок с фильтром.
- Форма создания заявки.
- Карточка заявки: оба статуса, результат, ответственный и комментарий.

**Готово, когда:** весь сценарий проходится в браузере.

## 4. Сквозной сценарий

- `docker compose up` поднимает БД, бэкенд, эмулятор и фронтенд.
- Небольшой набор демо-данных.
- Ручная проверка: вход → создать заявку → увидеть результат.

**Контрольная точка этапа 1:** основной сценарий работает от начала до конца на реальных данных.

## Заложить сразу, чтобы не переделывать

Это мелочи, которые потом дорого добавлять:
- у каждой заявки есть `operationId`, который создаётся вместе с ней и не меняется;
- отправка идёт через таблицу-очередь в БД (`dispatch_operation`), а не прямым вызовом из запроса пользователя;
- у заявки поле `version` для защиты от одновременных изменений;
- статусы доставки и результата хранятся раздельно;
- `Idempotency-Key` на создании: без него двойной клик даёт две реальные доставки;
- получение результатов отделено от их обработки (`ResultInbox`), обработчик блокирует строку операции.

# Этап 2. Остальные требования ТЗ

Делается после этапа 1, примерно в этом порядке:

1. **Надёжность обмена:**
   - ограниченные повторы с паузами;
   - исполнение не более одного раза в эмуляторе;
   - отсеивание дубликатов и устаревших результатов;
   - восстановление после перезапуска.
2. **Режимы сбоев эмулятора:** недоступность, потеря ответа, дубликат, задержанный результат.
3. **Проблемы и сверка:** неоднозначные ситуации видны оператору, действия оператора (повтор, решение по расхождению).
4. **Права доступа:** роли и область доступа, защита от обхода через API.
5. **История и аудит действий.** Сейчас смена ответственного и комментария меняет только заявку и `version` и никуда не записывается: в `audit_log` должны попадать кто, когда, было → стало (NF05; замечание обзора кода этапа 1).
6. **Интерфейс:** история обмена, проблемы, сверка; адаптивность 390–1440, клавиатура, пустые состояния и ошибки.
7. **Автотесты:** бизнес-правила, права, повторы, гонки; часть на реальной БД.
8. **Нагрузка:** генератор 5000 записей, прогон, лимиты ресурсов, отчёт.
9. **Документация:** README, устройство, модель данных, API, допущения.
