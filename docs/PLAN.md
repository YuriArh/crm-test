# План работ — «Обмен с внешней системой»

Основание: `04-system-integration.md` (ТЗ v2.1).

Подход: сначала **базовый работающий функционал** (бэкенд → эмулятор → фронтенд → сквозной сценарий). Только после этого — остальные требования ТЗ: надёжность, права, аудит, нагрузка, тесты, документация.

Предыдущая подробная версия плана: `docs/archive/PLAN-v1.md`. Подробные решения по `dispatch`: `docs/dispatch-design.md`.

## Исходные решения

- Стек: Java 25 + Spring Boot, PostgreSQL, React + TypeScript + Vite, Docker Compose.
- Предметная область: заявка на доставку груза (груз, вес, адрес, срок). Вымышленная служба доставки возвращает номер отправления и стоимость либо отказ.
- Жизненный цикл: «Создать» (заявка сохраняется и сразу ставится в очередь) → исполнение → результат. Черновика нет, содержимое неизменяемо.
- Результаты приложение забирает у эмулятора опросом ленты (pull).
- Репозиторий: Gradle multi-project для Java (`dispatch`, `carrier-emulator`), `web/` — отдельный npm-проект, Docker Compose и Makefile поверх. Turborepo и Nx не используются.
- Именование: основное приложение — `dispatch` (принимает заявки, передаёт их перевозчику, отслеживает доставку и результат, сверяет), эмулятор — `carrier-emulator` (изображает внешнего перевозчика).
- Фронтенд и API доступны с одного origin: в разработке через proxy Vite, в Docker через nginx (сессионные cookie без CORS).
- `dispatch` и `carrier-emulator` не делят Java-классы; контракт описан в `contracts/` (OpenAPI).

## Структура репозитория

```
dispatch/          Spring Boot: API и фоновые обработчики
carrier-emulator/  эмулятор внешнего перевозчика (отдельное приложение, своя БД)
contracts/         OpenAPI-контракты
web/               React + TS + Vite (позже)
docs/              план и документация
docker-compose.yml, Makefile, settings.gradle.kts, build.gradle.kts
```

# Этап 1. Базовый функционал

## 1. Бэкенд

- Каркас Spring Boot, подключение к PostgreSQL, миграции схемы.
- Демо-пользователи и простой вход (два инициатора, оператор).
- Заявки:
  - создание: сохраняет заявку и в той же транзакции ставит её в очередь на отправку; обязательный `Idempotency-Key`;
  - изменение ответственного и комментария с проверкой `version`;
  - список заявок с фильтром и страницами;
  - карточка заявки.
- Фоновая отправка заявок в эмулятор.
- Фоновый опрос ленты эмулятора и применение результатов через единый обработчик.
- У заявки два статуса: доставка и бизнес-результат.

**Готово, когда:** через curl можно создать заявку и увидеть, как она уходит перевозчику и получает результат.

## 2. Эмулятор

- Отдельное Spring Boot приложение со своей базой.
- Принимает заявку, исполняет (выдаёт номер отправления и стоимость или отказ), сохраняет у себя.
- Отдаёт результаты приложению по запросу.
- Показывает своё состояние: список операций и сколько раз каждая исполнена.

**Готово, когда:** приложение отправляет заявку, эмулятор её исполняет, приложение получает результат.

## 3. Фронтенд

- Вход.
- Реестр заявок с фильтром.
- Форма создания заявки.
- Карточка заявки: оба статуса, результат, ответственный и комментарий.

**Готово, когда:** весь сценарий проходится в браузере.

## 4. Сквозной сценарий

- `docker compose up` поднимает БД, бэкенд, эмулятор и фронтенд.
- Небольшой набор демо-данных.
- Ручная проверка: вход → создать заявку → увидеть результат.

**Контрольная точка этапа 1:** основной сценарий работает от начала до конца на реальных данных.

## Заложить сразу, чтобы не переделывать

Это мелочи, которые потом дорого добавлять:
- у каждой заявки есть `operationId`, который создаётся вместе с ней и не меняется;
- отправка идёт через таблицу-очередь в БД (`dispatch_operation`), а не прямым вызовом из запроса пользователя;
- у заявки поле `version` для защиты от одновременных изменений;
- статусы доставки и результата хранятся раздельно;
- `Idempotency-Key` на создании: без него двойной клик даёт две реальные доставки;
- получение результатов отделено от их обработки (`ResultInbox`), обработчик блокирует строку операции.

# Этап 2. Остальные требования ТЗ

Делается после этапа 1, примерно в этом порядке:

1. **Надёжность обмена:**
   - ограниченные повторы с паузами;
   - исполнение не более одного раза в эмуляторе;
   - отсеивание дубликатов и устаревших результатов;
   - восстановление после перезапуска.
2. **Режимы сбоев эмулятора:** недоступность, потеря ответа, дубликат, задержанный результат. Спека: `docs/specs/carrier-faults.md`.
   - **Падение и перезапуск во время обмена** (D04, D-NF01, NF03; решение 15.11.2026). Отдельных сценариев рестарта нет. Требование — инвариант: в какой бы момент `dispatch` или БД ни упали и сколько бы ни лежали, после старта каждая принятая заявка доходит до итога, ничего не теряется и не исполняется дважды. Конкретные окна (посреди отправки, до чтения ленты, истёкший захват) покрыты интеграционными тестами (`SendWorkerTests`, `FeedPollerTests`); на стенде показываем, как в жизни.
   - Команды: `make dispatch-kill` (`docker compose kill dispatch`, SIGKILL как настоящее падение), `make dispatch-start` (`docker compose start dispatch` и ожидание health); для эмулятора `make carrier-kill` / `make carrier-start`; для БД `make db-kill` / `make db-start`. Момент падения и длительность простоя выбирает проверяющий. В гейт не входят.
   - README, одна общая процедура:
     1. создать заявки, можно несколько и с любыми режимами сбоев (`make fault-*`);
     2. в любой момент `make dispatch-kill`, подождать сколько угодно, `make dispatch-start`, войти заново (сессия хранится в памяти);
     3. ожидаемо: каждая заявка дошла до итога (карточка, реестр), у эмулятора по каждой операции `executionCount = 1` (`make carrier-ops`), заявки, созданные до падения, на месте.

     Отдельно: при `unavailable` дольше ~10 минут попытки кончаются и заявка уходит в `FAILED` (решает оператор). После выключения сбоя заявка ждёт свою «Следующую попытку». Для БД то же через `make db-kill` / `make db-start`: сессия `dispatch` сохраняется, PostgreSQL общий, поэтому эмулятор тоже теряет базу и восстанавливается сам; пока БД лежит, интерфейс показывает ошибки загрузки.
   - Реализация (одним коммитом): четыре цели в `Makefile`, раздел в README. Проверка: вручную на стенде по процедуре README, затем гейт (`./gradlew build`, `make up && make e2e`) как проверка регрессии.
3. **Проблемы и сверка:** неоднозначные ситуации видны оператору, действия оператора (повтор, решение по расхождению). Учесть (из проверки спеки сбоев):
   - некорректная запись ленты (`INVALID_MESSAGE`) на стенде получается режимом сбоя `malformed` (`make fault-malformed`, `docs/specs/feed-bad-records.md`). Разные итоги по одной операции (`RESULT_CONFLICT`) и `RECONCILIATION_CONFLICT` честный эмулятор по-прежнему не выдаёт: способ получить их для демо и e2e решается вместе с этим пунктом. Вставка произвольной записи (`POST /admin/feed`) отклонена: ради неё пришлось бы менять схему эмулятора;
   - сценарий `EXTERNAL_AHEAD` (сверка получила итог раньше ленты) на стенде сам не возникнет: задержка `delayed` 15 с, а порог сверки 2 мин. Сделать порог сверки настраиваемым или поднять задержку для этого сценария;
   - `make seed`: провести часть демо-заявок через режимы сбоев (например `loseResponse` и `unavailable`), чтобы в карточках была история с `UNKNOWN` и повторами (раздел 7 ТЗ).
4. **Права доступа:** роли и область доступа, защита от обхода через API.
5. **История заявки** (ТЗ NF05, D06, D-NF03, §6; решение 18.11.2026). Спека: `docs/specs/request-history.md`,
   план: `docs/plans/request-history-plan.md`. **Реализовано.**
   - В ТЗ это одно требование, а не два. NF05 описывает, какой должна быть запись истории (автор, время, объект,
     содержание изменения; видна уполномоченным; переживает смену ответственного, состояния и перезапуск). D06 и
     D-NF03 описывают, что в историю входит (обмен, внешний результат, решение оператора) и где её видно (в
     интерфейсе). Слова «аудит» в ТЗ нет. Раньше план делил историю на «аудит действий» (п. 5) и «хронологию
     обмена» (п. 6) по источнику данных; теперь это один пункт.
   - Так же устроено в индустрии: история записи в её карточке (Jira History/Activity, Salesforce Field History,
     ServiceNow Activity stream, Zendesk ticket audits). Правки полей хранятся отдельно, обмен — в своих таблицах
     (Message Store из EIP), интерфейс сливает их в одну ленту. Журнал безопасности всей системы (GitHub audit log,
     Salesforce Setup Audit Trail) ТЗ не требует: входы и отказы в доступе пишет технический журнал (NF10), это
     допущение README.
   - Чтения существующих таблиц мало. Без следа сейчас остаются правка комментария и ответственного (`PATCH`
     затирает прежнее значение) и «Повторить отправку» (автор есть только в служебном `idempotency_key`). Для них
     нужна запись события с автором и «было → стало» в той же транзакции, что и действие.
   - Видимость — как у самой заявки, с ограничением по полям: оператор службы видит всё, инициатор — свою заявку
     без технической части.
6. **Интерфейс:** история обмена, проблемы, сверка; адаптивность 390–1440, клавиатура, пустые состояния и ошибки.
   - Проблемы — `docs/specs/web-problems.md` часть A (реализована); сверка — там же часть B.
   - История заявки в карточке — п. 5.
7. **Автотесты:** бизнес-правила, права, повторы, гонки; часть на реальной БД.
8. **Нагрузка:** генератор 5000 записей, прогон, лимиты ресурсов, отчёт (решение 18.11.2026; реализовано).
   - Спека `docs/specs/load-test.md`, план `docs/plans/load-test-plan.md`, результат `docs/load-report.md`.
   - k6 в Docker на отдельном стенде `exchange-load`, скрипты на TypeScript в `load/`; набор создаётся через API
     (`make load-seed`), замер и отчёт — `make load-test`.
9. **Документация:** README, устройство, модель данных, API, допущения.
