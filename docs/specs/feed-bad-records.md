# Спека: плохие записи ленты не останавливают получение результатов

Статус: согласовано (16.11.2026), план — `docs/plans/feed-bad-records-plan.md`. Основание: ТЗ D04 («некорректное сообщение требует разбора; бесконечного быстрого
цикла повторов быть не должно»), D-NF03, D03, NF03, NF10; ревью кода `dispatch` (16.11.2026, пункты 1, 2, 7);
итог проектного опроса Q1–Q31. Дизайн `dispatch` — `docs/dispatch-design.md`; эта спека меняет его §4 (таблица
`inbox`) и §5 (получение и обработка результатов). Режимы сбоев эмулятора — `docs/specs/carrier-faults.md`, эта
спека добавляет пятый режим.

## 1. Зачем

Сейчас `dispatch` читает из ленты перевозчика пачку до 100 записей и в **одной транзакции** разбирает каждую запись,
применяет её к заявке и сдвигает закладку (`feed_cursor`). Если база отвергает одну запись, откатывается вся пачка,
закладка остаётся на месте, и через 1 с всё повторяется. Лента стоит навсегда, результаты не приходят ни по одной
заявке. Это нарушает D04 и правило §5 дизайна «одна некорректная запись становится `INVALID` и не блокирует ленту».

Подтверждено тестами на реальной PostgreSQL (`ReviewFeedFindingsTests`, временные):

| Запись | Что происходит |
|---|---|
| цена `10000000000000.00` | проверка пропускает, база: `numeric field overflow` (SQLSTATE `22003`) |
| `\u0000` в `reason` | проверка пропускает, `jsonb`: `unsupported Unicode escape sequence` (`22P05`) |
| `sequence` = 4294967297 | `ResultMessage.parse` бросает исключение (Jackson 3 `asInt()`), хотя обещает не бросать |
| запись без `feedSeq` | каждый проход коммитит ещё одну строку `INVALID`, закладка не двигается |

Причина не в конкретных полях, а в устройстве: живучесть ленты держится на том, что проверка записи ничего не
упустит. Исправление меняет устройство так, чтобы содержимое записи не могло остановить ленту, как бы ни была
написана проверка.

## 2. Решение в целом

Три общепринятых подхода вместе:

- **Transactional Inbox** — «сначала принять, потом разбирать». Шаг 1 (приём) сохраняет записи как есть и
  сдвигает закладку; от содержимого записей он не зависит. Шаг 2 (разбор) обрабатывает каждую запись отдельной
  транзакцией: ошибка затрагивает только её.
- **Повторы и «отстойник»** (dead letter, как в Kafka / SQS / RabbitMQ). Ошибка в данных — запись сразу
  `INVALID`. Временная ошибка — ограниченные повторы с паузой, затем `FAILED`. Бесконечного быстрого цикла нет.
- **Строгая проверка на границе** (anti-corruption layer). Пределы полей записаны в контракте, код и база им
  соответствуют. Проверка нужна для точной причины отказа, а не для живучести ленты.

```
лента ── шаг 1: приём (одна транзакция на пачку) ──→ inbox: RECEIVED
                проверить конверт, сохранить текст, сдвинуть закладку
inbox ── шаг 2: разбор (транзакция на запись) ──→ APPLIED / STALE / CONFLICT / INVALID / FAILED
```

Оба шага выполняются одним проходом опроса раз в 1 с: сначала приём всех доступных пачек, затем разбор всех
подошедших записей. Приём и разбор — разные части кода: будущая сверка (§6 дизайна) кладёт записи в `inbox` и
вызывает только разбор.

**Тесты не влияют на рабочий код.** В рабочем коде `dispatch` не появляется ничего ради тестов: ни флагов «сымитировать
сбой», ни методов сброса состояния, ни служебных эндпоинтов. Сбои в интеграционных тестах вызываются подменой
зависимости в тестовой конфигурации (§11), на стенде — режимом сбоя эмулятора на уровне HTTP (§9). Бизнес-логика и
схема данных эмулятора ради проверки не меняются.

## 3. Шаг 1: приём

### 3.1 Проверка конверта

Конверт — позиция записи в ленте (`feedSeq`), по ней двигается закладка. Пачка принимается, только если:

- каждый элемент — JSON-объект с целым `feedSeq` в пределах `1 … 9223372036854775807`;
- первый `feedSeq` больше закладки, дальше номера строго возрастают (пропуски допустимы, контракт их разрешает).

Иначе пачка **отвергается целиком**: ничего не сохраняется, закладка не двигается, опрос делает паузу
1 → 2 → … → 30 с (та же, что при недоступности перевозчика) и пишет `ERROR` с номером закладки и причиной.
Записи не пропускаются: без позиции неизвестно, откуда продолжать, а пропуск может потерять результаты.
Проверка конверта — часть шага приёма (`FeedPoller`, чистая функция над пачкой и закладкой): правила позиции
принадлежат закладке, а не HTTP-клиенту, и так проверка работает с любым транспортом. Нарушение — отдельный исход
«протокол нарушен», а не `CarrierUnavailableException`. В журнале «протокол нарушен» и «перевозчик недоступен»
различаются.

### 3.2 Что сохраняется

Одна транзакция на пачку: блокировка строки закладки (как сейчас, защита от второго экземпляра), затем для каждой
записи вставка в `inbox`, затем сдвиг закладки на последний `feedSeq` пачки.

| Поле `inbox` | Значение при приёме |
|---|---|
| `payload` | исходная запись текстом (Jackson экранирует управляющие символы, `text` принимает любую запись) |
| `feed_seq` | `feedSeq` из конверта |
| `message_id` | `messageId`, если он «чистый» (§3.3), иначе `NULL` |
| `source` | `FEED` |
| `processing_status` | `RECEIVED` |
| `attempts` | `0` |
| `next_attempt_at` | время приёма |
| `received_at` | время приёма |

`operation_id`, `sequence`, `result_status` и `reason` при приёме не заполняются: они появляются при разборе,
после проверки. Так приём не зависит от содержимого записи.

### 3.3 «Чистый» `messageId`

Строка длиной 1–100 символов без управляющих символов (коды 0–31 и 127). Нечистый `messageId` не сохраняется
(`NULL`): настоящий NUL база не примет ни в одной текстовой колонке. При разборе такая запись становится `INVALID`
с причиной «messageId is missing or malformed». Повторы для неё не отсеиваются, это безопасно: позиция ленты
принимается один раз (§3.4).

### 3.4 Повторы

- Повтор того же `messageId` новой строки не создаёт: `duplicate_count + 1`, `last_duplicate_at` (как сейчас,
  `INSERT … ON CONFLICT`). Режим сбоя `duplicate` попадает сюда.
- Позицию ленты гарантирует база: уникальный индекс `inbox (feed_seq) WHERE source = 'FEED'`.

## 4. Шаг 2: разбор

### 4.1 Какие записи и в каком порядке

Записи `RECEIVED` с `next_attempt_at <= now`, по `received_at`, затем `feed_seq` (записи пачки получены в один
момент и идут по номеру в ленте; у записей сверки номера нет). Каждая запись захватывается
`FOR UPDATE SKIP LOCKED`, поэтому несколько экземпляров `dispatch` не разберут её дважды. Строгого порядка внутри
одной операции нет: правила (`ResultRules`) сравнивают `sequence`, и запись, применённая позже более новой,
становится `STALE`. Запись, ждущая повтора, не задерживает остальные.

### 4.2 Одна запись — одна транзакция

В транзакции записи:
1. разобрать и строго проверить запись (§6); не прошла — итог `INVALID` с причиной;
2. дальше как сейчас: незнакомый `operationId` → `INVALID`; иначе блокировка строки операции, решение `ResultRules`
   (`APPLIED` / `STALE` / `CONFLICT`), для `APPLIED` применение к заявке и операции;
3. записать в строку `inbox` итог, причину и разобранные поля (`operation_id`, `sequence`, `result_status`).

### 4.3 Ошибки при разборе

Если транзакция записи упала, она откатывается, и в **новой** транзакции записывается исход:

| Ошибка | Исход |
|---|---|
| база отвергла данные: `DataIntegrityViolationException` (SQLSTATE класса 22 и 23; проверено тестом для `22003` и `22P05`) | сразу `INVALID`, причина — «rejected by the database: …» |
| любая другая | временная: `attempts + 1`, `last_error`, `next_attempt_at = now + пауза` (§4.4); после последней попытки — `FAILED` |
| база недоступна, исход тоже не записать | попытка не засчитывается; проход останавливается, следующий начнёт заново |

Последнее правило нужно, чтобы сбой базы не «съедал» попытки у хороших записей.

Известное следствие: ограничение базы, нарушенное из-за ошибки в нашем коде, а не в данных, тоже даст `INVALID`.
Исходный текст сохранён, такую запись можно будет разобрать заново после исправления (§5).

### 4.4 Повторы разбора

- До 5 попыток. Пауза после попытки `n`: 1 с × 2^(n−1), не больше 1 мин (1, 2, 4, 8 с — около 15 с в сумме).
- Без разброса: записи не идут к внешней системе, синхронные повторы не создают нагрузки на перевозчика.
- После 5-й неудачи — `FAILED`, причина — «processing failed 5 times: <последняя ошибка>».

### 4.5 Журнал (NF10)

- `INVALID` — `WARN`; `FAILED` — `ERROR`; каждая временная ошибка — `WARN` с номером попытки.
- В каждой строке `messageId` и `operationId`, если они известны, и `feedSeq`.
- Значения из записи в причине и журнале экранируются: управляющие символы — как `\uXXXX`, длина обрезается до
  200 символов. Причина `INVALID` сама не должна ронять запись в базу.

## 5. Статусы записи `inbox`

| Статус | Смысл | Конечный |
|---|---|---|
| `RECEIVED` | принята, ждёт разбора или повтора | нет |
| `APPLIED` | применена к заявке | да |
| `STALE` | не новее применённой | да |
| `CONFLICT` | противоречит применённой | да |
| `INVALID` | плохие данные от перевозчика | да |
| `FAILED` | данные не признаны плохими, но разобрать не удалось за 5 попыток | да |

`INVALID` и `FAILED` разделены: первое — проблема перевозчика, второе — сбой у нас. Без этого ошибка в нашем коде
выглядела бы как вина перевозчика.

**«Разобрать заново»** в эту работу не входит. В дизайне записывается: действие оператора над `INVALID` и
`FAILED` появится вместе с проблемами (§7 дизайна); данные к нему готовы — исходный текст хранится, статус
возвращается в `RECEIVED` с `attempts = 0`.

## 6. Строгая проверка записи

Пределы записываются в `contracts/carrier-api.yaml` (схема `OperationResult` / `ResultEntry`), `ResultMessage`
проверяет ровно их, база им соответствует.

| Поле | Правило |
|---|---|
| `feedSeq` | целое `1 … 9223372036854775807` (проверяется в конверте) |
| `messageId` | строка 1–100 символов |
| `operationId` | UUID |
| `sequence` | целое `1 … 2147483647` |
| `status` | `IN_PROGRESS`, `SUCCEEDED`, `REJECTED` |
| `trackingNumber` | строка 1–64 символа; обязателен для `SUCCEEDED` |
| `price` | число `0 … 9999999999.99`, не больше 2 знаков после запятой; обязательно для `SUCCEEDED` |
| `reason` | строка 1–1000 символов; обязательна для `REJECTED` |
| `occurredAt` | ISO-8601 instant |
| все строки | без управляющих символов (коды 0–31 и 127) |

- Числа проверяются на диапазон **до** преобразования (`canConvertToInt`, `canConvertToLong`, сравнение
  `BigDecimal`). `ResultMessage.parse` не бросает исключений ни на каком входе.
- Все реальные записи эмулятора укладываются с запасом: `messageId` — UUID (36), номер — `TRK-` + 8 (12),
  цена не больше 250 300.

## 7. Данные (миграции `dispatch`)

### `V7__inbox_two_step.sql`

- `payload`: `jsonb` → `text` (`USING payload::text`), существующие строки переводятся как есть.
- Новые колонки: `attempts integer NOT NULL` (существующим строкам `0`), `next_attempt_at timestamptz`,
  `last_error text`.
- `inbox_processing_status_valid` пересоздаётся: `RECEIVED`, `APPLIED`, `STALE`, `CONFLICT`, `INVALID`, `FAILED`.
- Новые ограничения:
  - `inbox_attempts_non_negative` — `attempts >= 0`;
  - `inbox_received_has_next_attempt` — `next_attempt_at` задан тогда и только тогда, когда статус `RECEIVED`;
  - `inbox_feed_has_feed_seq` — у `source = 'FEED'` задан `feed_seq`.
- Индексы:
  - `inbox_feed_seq_unique` — уникальный `inbox (feed_seq) WHERE source = 'FEED'`;
  - `inbox_due_idx` — `inbox (next_attempt_at) WHERE processing_status = 'RECEIVED'` (очередь разбора).

### `V8__result_field_lengths.sql`

- `delivery_request_tracking_number_length` — `char_length(tracking_number) <= 64`;
- `delivery_request_rejection_reason_length` — `char_length(rejection_reason) <= 1000`.

Цена уже ограничена типом `numeric(12,2)`. Каждое новое ограничение получает тест, что неверные данные отвергаются
(`SchemaMigrationTests`), список миграций в нём дополняется.

## 9. Режим сбоя эмулятора `malformed`

Дополнение к `docs/specs/carrier-faults.md` (новый §3.5 и правки §2, §6–9). Без миграций, без новых таблиц и без
изменений исполнителя, по образцу `unavailable`.

- Пятый выключатель `malformed`, в памяти, как остальные. Действует **в момент каждого чтения ленты**
  (`GET /results`), в операции не запоминается.
- Пока он включён, в ответе `GET /results` у каждой записи `SUCCEEDED` цена заменяется на `10000000000000.00`.
  Записи `IN_PROGRESS` и `REJECTED` не меняются.
- Портится только ответ. В базе эмулятора записи правильные; исполнитель, `GET /operations/{id}` и
  `GET /admin/operations` о режиме не знают и показывают настоящий итог.
- С `unavailable` побеждает `unavailable`; с `duplicate` портятся обе копии.
- Каждая испорченная запись пишется в журнал эмулятора: `Fault malformed: …` с `messageId` и `operationId` (`WARN`).
- Режим **сознательно нарушает контракт** ленты. Это записано в `carrier-faults.md` и в описании `PUT /admin/faults`.
- Схема `Faults` получает обязательное поле `malformed`; `PUT /admin/faults` принимает пять полей.
- Команда `make fault-malformed` включает только этот режим.

Ожидаемое поведение `dispatch`: испорченный итог становится `INVALID` и **не применяется** — заявка остаётся
«В работе»; записи после него применяются, лента не останавливается. У перевозчика итог есть, у `dispatch` нет —
материал для будущей сверки.

**Почему проверка детерминирована.** Запись «В работе» и итог эмулятор публикует в одной транзакции, подряд, поэтому
`dispatch` читает их одной пачкой. Если карточка показывает «В работе», испорченный итог прочитан, пока режим был
включён. Ждать по времени не нужно.

## 10. Наблюдение и ручная проверка

- `make inbox` — последние записи `inbox`: `received_at`, `feed_seq`, `processing_status`, `attempts`, `reason`,
  `last_error`, `message_id`, `operation_id`.
- `docs/manual-testing.md`: заголовок становится «Ручное тестирование обмена», во введение добавляются D04 и
  D-NF03, новые команды — в таблицу команд, новый раздел «Плохие записи от перевозчика»:
  - **А. Одна заявка.** `make fault-malformed`, создать заявку А, дождаться статуса «В работе». `make inbox`:
    итог заявки А — `INVALID` с причиной про цену. `make fault-off`, создать заявку Б — она получает итог.
    Заявка А остаётся «В работе», `make carrier-ops` показывает у неё настоящий итог.
  - **Б. Поток заявок.** `make fault-malformed`, быстро создать 5 заявок, дождаться у всех «В работе». Записей
    `INVALID` ровно 5. `make fault-off`, новая заявка получает итог.
  - **В. Перезапуск после брака.** После теста Б: `make dispatch-kill`, `make dispatch-start`. Число строк в
    `inbox` не меняется, повторного разбора нет; заявки из теста Б остаются «В работе»; новая заявка проходит.
- Падение между приёмом и разбором вручную не воспроизвести (миллисекунды в одном проходе), его проверяет
  интеграционный тест.

## 11. Тесты

Временные `ReviewFeedFindingsTests` становятся первыми красными тестами: ожидания переворачиваются, тесты
переносятся в классы ниже, временный файл удаляется. `ReviewSendFindingsTests` (лишние попытки) остаётся до своей
спеки.

**Модульные:**
- `ResultMessageTest`: каждый предел §6 на границе и за ней; большие `sequence`/`feedSeq` дают `INVALID`, а не
  исключение; управляющие символы; цена с 3 знаками; экранирование значений в причине;
- проверка конверта: нет `feedSeq`, не объект, номер не больше закладки, не возрастает, пропуски допустимы;
- политика повторов разбора: паузы 1, 2, 4, 8 с, потолок, `FAILED` после 5-й.

**Интеграционные** (`@IntegrationTest`, `FakeCarrier`):
- `FeedPollerTests`: плохая запись (цена сверх предела, `\u0000`, огромный `sequence`) не останавливает ленту —
  следующая запись применена, закладка сдвинута, плохая `INVALID`; пачка с испорченным конвертом отвергнута —
  ничего не сохранено, закладка на месте, пауза; повтор `messageId` не создаёт строку;
- приём без разбора, затем разбор следующим проходом (как после падения между шагами): результат применён один раз;
- ошибка базы, которую проверка пропустила → `INVALID`, остальные записи применены;
- временная ошибка → повторы по паузам, затем `FAILED`; если ошибка ушла до 5-й попытки — `APPLIED`;
- два параллельных разбора не разбирают одну запись дважды;
- `SchemaMigrationTests`: ограничения `V7` и `V8` отвергают неверные данные, перевод существующей строки `jsonb`
  в `text` сохраняет содержимое.

Ошибки при разборе вызываются **без изменений рабочего кода**: шпион `@MockitoSpyBean` на `InboxDao`, объявленный
один раз в общей тестовой конфигурации (`@IntegrationTest`, чтобы контекст Spring оставался общим), по умолчанию
ведёт себя как настоящий объект и сбрасывается после каждого теста. Тест задаёт ему «бросить
`RuntimeException` / `DataIntegrityViolationException` первые N раз».

Пауза при недоступности перевозчика в тестах больше не сбрасывается методом `FeedPoller.resetPause()` — метод
удаляется из рабочего кода; тесты сдвигают тестовые часы за пределы паузы.

**Эмулятор** (`@IntegrationTest`, `Contract.matchesContract()`): при `malformed` у записей `SUCCEEDED` в ответе
`GET /results` испорчена цена, и ответ нарушает контракт ровно в ней; `IN_PROGRESS` и `REJECTED` не изменены;
база, `GET /operations/{id}` и `GET /admin/operations` показывают настоящий итог; `unavailable` побеждает;
с `duplicate` испорчены обе копии; `PUT /admin/faults` требует пять полей.

**E2E** (`inbox` не виден снаружи и наружу не открывается; `INVALID` проверяют интеграционные тесты):
- `CarrierFaultsE2ETest`: при `malformed` цена итога в ленте испорчена, `GET /operations/{id}` показывает настоящую;
- `ExchangeFaultsE2ETest`: включить `malformed`, создать заявку А, дождаться «В работе»; выключить, создать заявку Б,
  дождаться её итога; заявка А осталась «В работе».

## 12. Вне объёма

- Проблемы `INVALID_MESSAGE` / `RESULT_CONFLICT`, их показ оператору и действие «разобрать заново» — §7 дизайна.
  До тех пор `INVALID` и `FAILED` видны только в журнале и в таблице `inbox`, в карточке и API ничего нового.
- Способ получить на стенде `RESULT_CONFLICT` (разные итоги по одной операции) — вместе с §7.
- Ограничение размера ответа перевозчика в байтах: огромная запись принимается целиком и при разборе становится
  `INVALID` по пределу длины. Записывается в дизайне как известное ограничение.
- Проблемы 2–5 ревью (лишние попытки при восстановлении, срок «зависания» против таймаутов, снимок реестра,
  `408`/`429`) — отдельные спеки.
- Полная проверка кода на влияние тестов (видимость методов и прочее) — отдельная работа.
