# Спека: история заявки

Статус: реализовано (18.11.2026), отличия — §6. Хранение — события, привязанные к `version` заявки (§2.1–2.2), Q1–Q6
приняты как предложено (§7); план — `docs/plans/request-history-plan.md`. Основание: ТЗ NF05, D06, D-NF03, §6; `docs/PLAN.md` этап 2, п. 5. Меняет
`docs/dispatch-design.md` §8 (вместо `audit_log` — история заявки по этой спеке) и §4 (новая таблица, колонка
`inbox`).

## 1. Зачем

ТЗ требует одну историю задания, а не журнал аудита отдельно от истории обмена:

| Где | Требование |
|---|---|
| NF05 | значимые действия имеют автора, время, объект и содержание изменения; история доступна только уполномоченным и сохраняется при смене ответственного, состояния и после перезапуска |
| D06, §6 | в UI доступна история обмена |
| D-NF03 | история связывает задание, попытки обмена, внешний результат и решение оператора |

Сейчас данные для истории лежат в разных таблицах, и интерфейс её не показывает. Часть значимых действий не
оставляет следа вовсе:

| Действие или событие | Что хранится сейчас |
|---|---|
| Создание заявки | ✅ `delivery_request`: автор, время, содержимое (неизменяемо) |
| Правка комментария, смена ответственного | ❌ меняется только заявка и `version`, прежнее значение затирается, автора нет |
| «Повторить отправку» | ❌ автор есть только в служебном `idempotency_key`; если проблемы не было, следа нет |
| Смена итога (результат из ленты, из сверки, решение оператора) | ⚠️ поля заявки перезаписываются; прежний итог восстанавливается только косвенно (`inbox`, снимок `our_*` у проблемы) |
| Попытки отправки | ✅ `exchange_attempt`: начало, конец, исход, HTTP-статус, ошибка, длительность |
| Подтверждение получения | ✅ `dispatch_operation.acknowledged_at` / `acknowledged_via` (один раз) |
| Записи перевозчика | ⚠️ `inbox`: время получения, источник, итог обработки, число повторов; **времени обработки нет** |
| Проверки сверки | ✅ `reconciliation` (неизменяемые строки, автор ручной) |
| Проблемы и решения | ✅ `problem`: открыта, закрыта, кто, решение, комментарий; обе стороны расхождения (`conflict-history.md`) |

`PATCH` и применение итога перезаписывают поля заявки на месте, и ни одна существующая таблица прежних значений не
хранит, поэтому нужна новая таблица событий.

## 2. Решение

### 2.1 Принцип

1. **Строка заявки — текущее состояние, события — его изменения.** Источник правды для «сейчас» остаётся
   `delivery_request`; события — журнал рядом с ним.
2. **Событие привязано к версии.** Каждое изменение заявки и сейчас увеличивает `version` (`PATCH` через `@Version`,
   итог через `version + 1` в `InboxDao.applyToRequest`). Событие хранит номер версии, которую создало изменение;
   пара `(request_id, version)` уникальна. Каждому увеличению `version` после создания соответствует ровно одно
   событие.
3. **Одна транзакция.** Событие пишется в той же транзакции и под той же блокировкой строки, что и `UPDATE`
   заявки. Отката одного без другого не бывает.
4. **Инвариант.** Содержимое при создании (`version = 0`) плюс события по порядку `version` дают текущие
   комментарий, ответственного и итог; номера версий без пропусков от 1 до текущей. Изменение заявки, которое забыло
   записать событие, видно как пропуск — это проверяет тест (§4).
5. **Нет изменения — нет версии и нет события.** У `PATCH` так уже сейчас (пустая правка — `200` без увеличения
   `version`). `applyToRequest` получает то же правило: если итог из записи равен итогу заявки, строка заявки не
   меняется (продвигается только `last_applied_seq` / `applied_inbox_id` операции). Иначе версия выросла бы с пустым
   событием.
6. **Повтор отправки** заявку не меняет и `version` не увеличивает; его событие без версии.
7. **Обмен** берётся из таблиц, где он уже хранится (`exchange_attempt`, `inbox`, `reconciliation`, `problem`,
   `dispatch_operation.acknowledged_*`). В `request_event` он не копируется: источник правды один.
8. **Создание** берётся из `delivery_request` (автор, время, содержимое неизменяемо).
9. Лента собирается на чтении одним запросом и отдаётся отдельным `GET`.
10. Переходы статуса доставки (`PENDING` → `SENDING` → …) отдельно не хранятся: у каждого записан повод —
    попытка с исходом, подтверждение получения, повтор оператора, проблема `DELIVERY_FAILED`/`DELIVERY_UNKNOWN`.
    Журнал статусов дал бы второй источник правды для того же самого.

### 2.2 Модель данных — миграция `V13__request_history.sql`

Номер — следующий свободный на момент реализации.

`request_event` — одна строка на действие, только `INSERT`:

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | `uuid` PK | UUIDv7 приложения |
| `request_id` | `uuid NOT NULL` FK `delivery_request` | объект |
| `version` | `bigint` | версия заявки, которую создало изменение; пусто у `DELIVERY_RETRIED` |
| `occurred_at` | `timestamptz NOT NULL` | когда (из `Clock`; у изменения заявки — тот же `now`, что в `updated_at`) |
| `actor_id` | `uuid` FK `app_user` | кто; пусто — система |
| `kind` | `text NOT NULL` | `EDITED` / `RESULT_CHANGED` / `DELIVERY_RETRIED` |
| `changes` | `jsonb NOT NULL` | массив `{field, from, to}`: изменившиеся поля (у `DELIVERY_RETRIED` — статус доставки всегда) |
| `inbox_id` | `uuid` FK `inbox` | запись перевозчика, чей итог применён (`RESULT_CHANGED`) |
| `problem_id` | `uuid` FK `problem` | проблема, по которой оператор принял итог (`RESULT_CHANGED` от оператора) |

Ограничения (каждое со своим именем):
- `request_event_kind_valid` — `kind IN ('EDITED', 'RESULT_CHANGED', 'DELIVERY_RETRIED')`;
- `request_event_version_matches_kind` — `version` есть у `EDITED` и `RESULT_CHANGED` и пуста у
  `DELIVERY_RETRIED`;
- `request_event_version_positive` — `version > 0` (версия 0 — создание, у него события нет);
- уникальный индекс `request_event_request_version_unique (request_id, version) WHERE version IS NOT NULL`;
- `request_event_changes_array` — `jsonb_typeof(changes) = 'array' AND jsonb_array_length(changes) > 0`;
- `request_event_actor_required` — у `EDITED` и `DELIVERY_RETRIED` автор обязателен;
- `request_event_result_has_record` — у `RESULT_CHANGED` есть `inbox_id` (итог всегда приходит записью: из ленты,
  из сверки или выбранной оператором); у других видов `inbox_id` и `problem_id` пусты;
- индекс `request_event_request_idx (request_id, occurred_at)` для ленты.

Поля в `changes` по видам (список полей проверяет код и тест, а не `CHECK`):

| `kind` | Поля | Значения |
|---|---|---|
| `EDITED` | `comment`, `assigneeId` | текст целиком (до 2000), `uuid` или `null` |
| `RESULT_CHANGED` | `businessStatus`, `trackingNumber`, `price`, `rejectionReason` | как в заявке, цена строкой |
| `DELIVERY_RETRIED` | `deliveryStatus` | всегда, даже без смены: `FAILED`/`ACKNOWLEDGED` → `PENDING`, `UNKNOWN` → `UNKNOWN` (`SendQueueDao.retryByOperator` оставляет его: получение по-прежнему неизвестно). Повтор — действие, а не правка поля: событие показывает, из какого состояния его сделали |

`inbox.processed_at timestamptz` — когда запись получила итог обработки (покинула `RECEIVED`). Пишется тем же
`UPDATE`, что меняет `processing_status`. Ограничение `inbox_received_not_processed`: у `RECEIVED` пусто. Старые
строки не заполняются: настоящего времени нет, а время получения выдало бы себя за время обработки (§5).

### 2.3 Где пишутся события

Писателей заявки два, и у каждого событие пишется рядом с `UPDATE`:

| Событие | Где | Версия | Когда не пишется |
|---|---|---|---|
| `EDITED` | `RequestService.update`, после успешного `save` | из сохранённого агрегата | пустая правка (значения те же), `403`, `409` |
| `RESULT_CHANGED` | `InboxDao.applyToRequest` — единственный писатель итога (его вызывают `InboxProcessor` и `OperatorResults`) | `version + 1` из того же `UPDATE … RETURNING version` | итог не изменился (§2.1 п. 5) |
| `DELIVERY_RETRIED` | `OperatorActions.retry` внутри `idempotency.execute` | — | повтор того же ключа (ответ из `idempotency_key`), недопустимое состояние |

`RESULT_CHANGED` от `OperatorResults` получает автора-оператора и `problem_id`; от ленты и сверки — без автора.
Новый код, меняющий `delivery_request`, обязан идти через одного из двух писателей; иначе его ловит тест инварианта.

### 2.4 Лента: виды записей и кто их видит

Видимость — как у заявки (`RequestPermissions.canView`), с ограничением по полям: инициатор видит деловую часть,
оператор службы — всё. Фильтрует сервер.

| Вид в API | Источник | Время | Инициатор | Оператор |
|---|---|---|---|---|
| `CREATED` | `delivery_request` | `created_at` | ✅ | ✅ |
| `EDITED` | `request_event` | `occurred_at` | ✅ | ✅ |
| `RESULT_CHANGED` | `request_event` | `occurred_at` | ✅ без ссылок на запись и проблему | ✅ |
| `DELIVERY_ACKNOWLEDGED` | `dispatch_operation` | `acknowledged_at` | ✅ «перевозчик получил заявку» | ✅ со способом |
| `DELIVERY_RETRIED` | `request_event` | `occurred_at` | — | ✅ |
| `SEND_ATTEMPT` | `exchange_attempt` | `started_at` | — | ✅ номер, исход, HTTP, ошибка, длительность |
| `RESULT_RECEIVED` | `inbox` | `processed_at`, иначе `received_at` | — | ✅ источник, статус, `sequence`, итог обработки, причина, повторы |
| `RECONCILIATION` | `reconciliation` | `checked_at` | — | ✅ запуск, автор ручной, исход |
| `PROBLEM_OPENED` | `problem` | `opened_at` | — | ✅ вид |
| `PROBLEM_RESOLVED` | `problem` | `resolved_at` | — | ✅ решение, автор, комментарий |

Порядок — новые первыми; записи одного момента (одной транзакции) идут в порядке причины: создание, повтор,
попытка, сверка, запись перевозчика, смена итога, подтверждение получения, правка, открытие проблемы, решение
(`HistoryKind`); затем по `id`. Повторы записи
перевозчика не множат строки: одна запись `RESULT_RECEIVED` с числом повторов и временем последнего (D03: повтор не
создаёт эффекта). У `EDITED` и `RESULT_CHANGED` в ответе есть `version`: по ней запись ленты сопоставляется с
версией карточки.

### 2.5 API (`dispatch-api.yaml`)

- `GET /api/requests/{id}/history?before=<cursor>&limit=<1..200, по умолчанию 50>` → `{items, nextCursor}`;
  курсор — непрозрачная строка от `(at, kind, id)` последней записи.
- `404` — заявки нет или она не видна (как карточка), `401` — без сессии.
- `HistoryEntry`: `id`, `at`, `kind`, `actor` (`PersonRef` или `null` — система) и поля своего вида (`oneOf` по
  `kind`). `EDITED` и `RESULT_CHANGED` — `version` и `changes: [{field, from, to}]`, ответственный — `PersonRef`.
- Карточка не меняется: история отдельным запросом, чтобы опрос карточки раз в 5 с не тянул её каждый раз (NF08).

### 2.6 Web

- Раздел «История» в карточке заявки (`requests/card/history/`): Mantine `Timeline`, новые сверху, «Показать
  ещё» по `nextCursor`. Пустого состояния не бывает: есть хотя бы создание.
- Каждая запись: время в бизнес-зоне, кто («Система» для `null`), что. Правка — «было → стало» (длинный комментарий
  свёрнут). Смена итога — старый и новый итог.
- Обновляется вместе с карточкой: перезапрос, когда меняется `card.version` или `deliveryStatus`, и после действий
  оператора.
- Оператору — фильтр «Все / Действия людей / Обмен»; у инициатора фильтра нет.
- 390 px: одна колонка, технические подробности раскрываются по нажатию. Обе схемы.

### 2.7 Что не входит

- Журнал безопасности системы (входы, отказы в доступе, смена прав). Входы и отказы пишет технический журнал
  (NF10, `dispatch-design.md` §8) — допущение README.
- Защита записей от подделки (цепочка хэшей, отдельная роль БД без `UPDATE`/`DELETE`): у приложения одна учётка
  владельца схемы. Неизменяемость обеспечивает код (у DAO только `insert`) и тест — ограничение README.
- История эмулятора: его состояние проверяется отдельно (`make carrier-ops`, D07).

## 3. Права и NF05

- «Уполномоченные» = те, кто видит заявку; инициатор — без технической части (§2.4).
- История не зависит от текущего ответственного и статуса: смена ответственного видна в ней же и ничего не скрывает
  («сохраняется при смене ответственного, состояния»).
- Записи не удаляются и не меняются; переживают перезапуск (БД).
- Попытка обхода: чужая заявка, заявка другой службы, инициатор, запрашивающий технические виды, — тесты прав.

## 4. Тесты (уровни; подробно — в плане)

- Модульные: сборка `changes` из старых и новых значений; видимость видов по роли; курсор.
- Интеграционные:
  - каждое событие пишется в той же транзакции (откат действия — нет события), не пишется при пустой правке,
    `409`, повторе ключа;
  - **инвариант версий**: после сценария с правками, итогом из ленты, итогом из сверки и решением оператора номера
    версий событий идут без пропусков от 1 до `delivery_request.version`, а применение `changes` по порядку к
    состоянию при создании даёт текущие комментарий, ответственного и итог;
  - `applyToRequest` с тем же итогом не меняет `version` и не пишет событие;
  - ограничения V13 (`SchemaMigrationTests`): вид, версия по виду, уникальность `(request_id, version)`, `changes`,
    автор, запись у `RESULT_CHANGED`; `processed_at` у каждого итога обработки;
  - лента в порядке; инициатор без технических видов; `404` чужой и другой службы.
- e2e `dispatch`: заявка проходит путь до итога, правка комментария и ответственного, повтор — всё в ленте у
  оператора; инициатор видит деловую часть.
- Web: Vitest для ленты и фильтра; Playwright — история в карточке у оператора и инициатора, 390 px.

## 5. Известные ограничения (в README)

- У заявок, созданных до V13, нет событий `EDITED`, `RESULT_CHANGED`, `DELIVERY_RETRIED` — восстановить автора и
  прежнее значение неоткуда; инвариант версий для них не выполняется, и тест проверяет его только на новых заявках.
  У их записей перевозчика нет времени обработки, показывается время получения. `make reset && make seed` даёт
  полную историю.
- Отдельные повторы записи перевозчика не хранятся, только их число и время последнего.

## 6. Отличия реализации

- **Порядок записей одного момента** — причинный (`HistoryKind`: создание, повтор, попытка, сверка, запись
  перевозчика, смена итога, подтверждение, правка, открытие проблемы, решение), а не по строкам таблицы §2.4: в одной
  транзакции попытка идёт раньше подтверждения, которое она принесла, а итог — раньше проблемы, которую он открыл.
- **Контракт**: варианты `HistoryEntry` описаны плоско, каждый со своим `kind: const`, без `allOf` и `discriminator`.
  Проверка ответов в тестах запрещает лишние поля в каждой части `allOf`, а `discriminator` с `oneOf` она не
  поддерживает; варианты и так различаются `kind`. Ответственный в `changes` — `AssigneeChange` (`field: assignee`,
  `PersonRef`), остальные поля — `ValueChange` (текст, цена — десятичная строка).
- **Зависимости пакетов**: запись событий (`RequestEventDao`, `Change`) ни от чего не зависит; чтение ленты
  (`HistoryService`) зависит от `request` — права (`RequestPermissions`) и `PersonRef`.
- **`inbox.processed_at`** — время нынешнего итога обработки: когда оператор применяет уже полученную запись сверки,
  время обновляется вместе с её итогом.
- **Повтор отправки** пишет статус доставки до и после всегда (`UNKNOWN → UNKNOWN`), §2.2.
- **Web**: точка на шкале окрашена в цвет того, что произошло; подробности раскрываются кнопкой-ссылкой «Подробнее» без
  анимации.

## 7. Решённые вопросы

Все приняты как предложено (18.11.2026).

**Q1. Форма `changes`: `jsonb` или колонки?** `jsonb`-массив `{field, from, to}`: видов три, полей до
четырёх, колонки «было/стало» по каждому полю дали бы ~16 колонок с перекрёстными `CHECK`. Целостность объекта,
версии, автора и повода — в БД; состав полей — код и тест.

**Q2. Писать ли смену итога в `request_event`?** Да. Без неё прежний итог восстанавливается только из
`inbox` и снимков проблем, инициатор (которому `inbox` не показывается) не увидит, что итог менялся, а инвариант
версий не выполнялся бы: итог увеличивает `version`.

**Q3. Что видит инициатор?** Создание, правки, смены итога (с автором-оператором, если итог принял он),
подтверждение получения. Попытки, записи, сверки и проблемы — нет (как сейчас в карточке: технический блок и
проблемы у инициатора скрыты).

**Q4. `inbox.processed_at` нужен?** Да: запись может обработаться много позже получения (повторы
обработки, `FAILED`), а лента должна показывать, когда итог подействовал. Без колонки `RESULT_RECEIVED` и
`RESULT_CHANGED` могут стоять в ленте не по порядку.

**Q5. Раздел «Сверки» в карточке оставить?** Оставить: там подробности проверки (обе стороны, ответ
перевозчика) и «Сверить сейчас»; в ленте — строка с исходом. Убрать можно позже, когда лента покажет всё то же.

**Q6. Отдельный `GET` или поле карточки?** Отдельный `GET` с курсором: карточку опрашивают раз в 5 с,
а попыток и записей у заявки с повторами и сбоями — десятки.
