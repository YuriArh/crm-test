# Спека: сессии входа в PostgreSQL (Spring Session JDBC)

Статус: согласовано (опрос, 18.11.2026), в работе (NF08 выполнен, `docs/load-report.md`). План —
`docs/plans/jdbc-sessions-plan.md`. Основание: ТЗ NF02 (вход под демо-пользователями), NF03 (сохранность после перезапуска),
NF08 (бюджет ресурсов и время ответа), D04 (перезапуск во время обмена). Дизайн `dispatch` — `docs/dispatch-design.md`;
эта спека меняет его §1 (коды ошибок), §2 (абзац «Сессии в памяти (сознательное упрощение)») и §4 (модель данных).
До реализации `README.md` и `docs/dispatch-design.md` описывают текущее упрощение и не меняются.

## 1. Зачем

Сессия входа сейчас — `HttpSession` встроенного Tomcat в памяти процесса `dispatch`. Spring Security кладёт в неё
контекст безопасности (`HttpSessionSecurityContextRepository` в `SecurityConfig`). Поэтому:

- после падения или перезапуска `dispatch` все сессии пропадают: cookie указывает на сессию, которой нет, следующий
  запрос получает `401 UNAUTHENTICATED`, и каждый пользователь входит заново. Сценарии падения в
  `docs/manual-testing.md` (раздел 6) и в README каждый раз требуют повторного входа;
- второй экземпляр `dispatch` не увидел бы сессии первого.

Заявки, очередь отправки и история при этом сохраняются — они в БД. Требованием ТЗ хранение сессий не является, это
сознательное упрощение (`docs/dispatch-design.md` §2). Здесь оно снимается.

Как это решают в индустрии: сессию выносят из процесса в общее хранилище, а приложение работает с ней через тот же
`HttpSession`. В экосистеме Spring для этого есть Spring Session; хранилище выбирают из тех, что уже есть в системе.
У нас есть PostgreSQL, отдельный Redis ради сессий не нужен (и не поместился бы в бюджет NF08 без ущерба остальным).

## 2. Решение

### 2.1 Хранилище

- Стартер Spring Session JDBC из BOM Spring Boot (точное имя артефакта для Boot 4.1 проверяется при составлении
  плана).
- Spring Boot сам ставит `SessionRepositoryFilter` перед цепочкой Spring Security: каждый `HttpSession` приложения —
  это строка в БД. Код входа, выхода и проверки прав не меняется (§2.7).
- Таблицы — в той же базе `dispatch` и схеме `public`, что и бизнес-данные.
- Изменения сессии записываются в конце запроса (`flush-mode: on-save`, по умолчанию): сессия, созданная при входе,
  лежит в БД к моменту, когда клиент получил ответ. Падение `dispatch` после этого её не теряет.
- Атрибуты сериализуются стандартной сериализацией Java (по умолчанию). В сессии лежит только контекст безопасности
  с `CurrentUser` без хеша пароля; `CurrentUser` — record, реализует `UserDetails` (он `Serializable`), все поля
  сериализуемы. Для record Java не требует совпадения `serialVersionUID`, поэтому добавленное поле не ломает
  сохранённые сессии. JSON не нужен: он потребовал бы настройки Jackson для классов Spring Security без выгоды.

### 2.2 Схема

Миграция `V<n>__http_sessions.sql` (следующий свободный номер на момент реализации) создаёт таблицы по эталонному
скрипту Spring Session для PostgreSQL; `spring.session.jdbc.initialize-schema: never` — схемой владеет только Flyway.

```sql
CREATE TABLE spring_session (
    primary_id            char(36)     NOT NULL,
    session_id            char(36)     NOT NULL,
    creation_time         bigint       NOT NULL,
    last_access_time      bigint       NOT NULL,
    max_inactive_interval integer      NOT NULL,
    expiry_time           bigint       NOT NULL,
    principal_name        varchar(100),
    CONSTRAINT spring_session_pk PRIMARY KEY (primary_id)
);
CREATE UNIQUE INDEX spring_session_ix1 ON spring_session (session_id);
CREATE INDEX spring_session_ix2 ON spring_session (expiry_time);
CREATE INDEX spring_session_ix3 ON spring_session (principal_name);

CREATE TABLE spring_session_attributes (
    session_primary_id char(36)     NOT NULL,
    attribute_name     varchar(200) NOT NULL,
    attribute_bytes    bytea        NOT NULL,
    CONSTRAINT spring_session_attributes_pk PRIMARY KEY (session_primary_id, attribute_name),
    CONSTRAINT spring_session_attributes_fk FOREIGN KEY (session_primary_id)
        REFERENCES spring_session (primary_id) ON DELETE CASCADE
);
```

**Сознательные отступления от правил схемы** (`CLAUDE.md`, «Schema rules»): ключ `char(36)`, а не `uuid`; время —
миллисекунды в `bigint`, а не `timestamptz`; «сейчас» Spring Session берёт из системных часов, а не из бина `Clock`.
Это таблицы фреймворка: их формат задаёт его SQL, и подгонка под наши правила потребовала бы своей реализации
хранилища. С бизнес-данными они не связаны, бизнес-код в них не пишет и из них не читает. Имена ограничений и
индексов заданы явно, как требуют правила. Исключение записывается в `docs/dispatch-design.md` §4 и в правила схемы
`CLAUDE.md`.

### 2.3 Cookie

Cookie называется `SESSION` — имя Spring Session по умолчанию: оно честно говорит, кто управляет сессией, и не
требует переопределять настройку. Меняются: контракт (`securitySchemes.session.name` и текст «Session and CSRF»),
`web/e2e/auth/session-lost.spec.ts` (удаляет cookie по имени), тестовые данные `web/src/shared/api/client.test.ts`.
Веб-клиент сам имя cookie сессии не читает (она `HttpOnly`), e2e-клиенты хранят все cookie подряд.

Остальные свойства cookie: `HttpOnly`, путь `/`, без `Secure` (стенд на http), без срока (живёт до закрытия
браузера). Spring Session по умолчанию добавляет `SameSite=Lax`; UI и API на одном адресе, поэтому это ничего не
ломает и дополнительно защищает от CSRF.

При выкатке сессии из памяти Tomcat не переносятся: все один раз входят заново. Старая cookie `JSESSIONID` больше не
нужна серверу и исчезнет при закрытии браузера.

### 2.4 Срок жизни и очистка

- Срок бездействия — 30 минут (значение Spring Boot по умолчанию, отдельно не задаётся), окно скользящее: каждый
  запрос продлевает сессию. Абсолютного предела нет (§5).
- Id сессии сам не меняется: он меняется при каждом входе (защита от фиксации, `ChangeSessionIdAuthenticationStrategy`)
  и только тогда. После истечения строка удаляется, cookie указывает в пустоту, следующий запрос — `401`, веб-клиент
  ведёт на вход и после входа возвращает на прежний адрес (`next`); вход создаёт новую сессию с новым id.
- Просроченные сессии удаляет сам Spring Session по расписанию (`cleanup-cron`, по умолчанию раз в минуту) одним
  `DELETE … WHERE expiry_time < ?` по индексу. При нескольких экземплярах удаление идемпотентно.
- Выход (`POST /api/auth/logout`) удаляет строку сессии сразу (`SecurityContextLogoutHandler` вызывает
  `invalidate()`).

### 2.5 Сессия, которую не удалось прочитать

После обновления Spring Security или изменения классов в сессии сохранённые байты могут не десериализоваться. По
умолчанию Spring Session бросает исключение, и любой запрос с такой cookie получает `500`. Пользователь сам из этого
не выйдет: веб-клиент на `500` не уводит на вход.

Решение: нечитаемая сессия считается отсутствующей. Свой `Deserializer` (обёртка над стандартным) при ошибке пишет
`WARN` «Session attribute … could not be read, treated as absent» без содержимого и возвращает `null`. Контекста
безопасности нет → `401 UNAUTHENTICATED` → веб-клиент ведёт на вход → новый вход создаёт новую сессию. Для
пользователя это то же, что истёкшая сессия.

Строка нечитаемой сессии не удаляется сразу: десериализатор превращает байты в объект и в БД не пишет. После нового
входа cookie указывает на новую сессию, старая строка безвредна и уходит с плановой очисткой не позже чем через
30 минут.

`Deserializer` ловит только ошибки десериализации байтов. Ошибки доступа к БД до него не доходят и не глотаются
(§2.6).

Отвергнуто: оставить `500` и очищать таблицу руками при каждом обновлении (ручной шаг легко забыть, цена — `500` у
всех вошедших); очищать таблицу миграцией при несовместимом обновлении (то же самое, только шаг — миграция).

### 2.6 База недоступна; ошибки вне контроллеров

ТЗ не требует, чтобы интерфейс работал без БД: NF03 — сохранность принятых изменений после перезапуска приложения и
БД, D04 — продолжение обмена после восстановления, D01 — сохранность задания при недоступности *исполнителя*
(перевозчика). Без БД и сейчас не работает почти ничего: реестр, карточка, создание, проблемы, даже
`GET /api/auth/me` (читает службу пользователя). Поэтому видимое поведение при падении БД не меняется:

- запрос с cookie сессии, пока БД лежит, — `500 INTERNAL_ERROR` (сессию не прочитать), а **не** `401`. `401` увёл
  бы пользователя на вход, хотя сессия цела; на `500` веб-клиент показывает ошибку загрузки, и после возврата БД всё
  снова работает без входа — как сейчас с сессией в памяти;
- `/actuator/health` и другие публичные адреса без cookie сессию не читают: healthcheck Docker и `make db-start`
  работают как сейчас;
- вход (`POST /api/auth/login`) без БД и сейчас невозможен (пользователь читается из БД).

Ошибку доступа к БД при чтении сессии ничто не перехватывает и не превращает в «нет сессии». Она возникает в
`SessionRepositoryFilter`, до контроллеров, поэтому `ApiExceptionHandler` её не видит: запрос уходит на `/error`, а
своего обработчика `/error` в `dispatch` нет — Spring Boot ответил бы своим JSON, а не Problem Details, как все
остальные ошибки API. Поэтому `dispatch` получает свой обработчик `/error` (`ErrorController` в `common/web/`):
статус из атрибутов запроса, тело — Problem Details через `ProblemResponseWriter`, без подробностей исключения.

| Статус | Код |
|---|---|
| `5xx` | `INTERNAL_ERROR` |
| `401` | `UNAUTHENTICATED` |
| `403` | `FORBIDDEN` |
| `404` | `NOT_FOUND` |
| прочие `4xx` | имя HTTP-статуса: `BAD_REQUEST`, `METHOD_NOT_ALLOWED`, … (`HTTP_<status>` для нестандартного) |

Для прочих `4xx` нового кода не заводится: так уже отвечает `ApiExceptionHandler` на ошибки фреймворка (404, 405,
415, …), и контракт это описывает («… or the HTTP status name for framework errors»). Обработчик `/error` берёт тот
же метод, правило остаётся в одном месте. `VALIDATION_FAILED` для них не годится: он обещает клиенту ошибки по полям,
которых нет. Веб-клиент любой незнакомый код показывает как обычную ошибку по статусу, менять его не нужно.

MockMvc не перенаправляет ошибку на `/error` (это делает контейнер сервлетов), поэтому обработчик проверяется
прямым запросом с атрибутами ошибки, а цепочка «сессию не прочитать → `/error` → Problem Details» — вручную на
стенде (§3).

Обработчик касается любой ошибки вне контроллеров, а не только сессий; ошибки в контроллерах, включая неизвестный
адрес, по-прежнему отвечает `ApiExceptionHandler`. В журнале — `ERROR` с причиной, как у любой ошибки БД.

### 2.7 Что не меняется

- `AuthController`: смена id сессии при входе (`ChangeSessionIdAuthenticationStrategy` — Spring Session её
  поддерживает), явное сохранение контекста, выход, ротация CSRF-токена.
- `SecurityConfig`: `DelegatingSecurityContextRepository` с `HttpSessionSecurityContextRepository`, обработчики
  `401`/`403`.
- CSRF: токен в cookie `XSRF-TOKEN` (`CookieCsrfTokenRepository`), в сессии его нет.
- API (кроме имени cookie и нового кода ошибки), логика веб-клиента, `make seed`, e2e.

### 2.8 Ресурсы (NF08)

Каждый запрос с сессией — чтение сессии с атрибутами (один запрос по уникальному индексу) и обновление
`last_access_time` в конце запроса. Пул соединений общий с бизнес-запросами (`DB_POOL_SIZE`, по умолчанию 10).

**Критерий приёмки:** прогон по профилю NF08 на нагрузочном стенде (`make load-up`, k6) после перехода укладывается
в требования ТЗ — 95 % запросов чтения не дольше 2 с, изменения не дольше 3 с при 20 клиентах, в бюджете 2 CPU /
4 GiB. Отдельного порога ухудшения нет: ТЗ задаёт абсолютные пороги. Цифры прогона до и после перехода
записываются в эту спеку (раздел «Отличия реализации») как факт.

### 2.9 Журнал (NF10)

- `WARN` о нечитаемой сессии (§2.5) — без id сессии и содержимого атрибутов.
- `ERROR` об ошибке вне контроллеров (§2.6) — с причиной, без тела запроса.
- Id сессии, cookie и байты атрибутов в журнал не пишутся.

## 3. Тесты

**Интеграционные (`@IntegrationTest`, реальная PostgreSQL).** С фильтром Spring Session MockMvc игнорирует
`MockHttpSession`: сессия ищется в БД по cookie. Поэтому `AuthTests` переходит с `MockHttpSession` на cookie
`SESSION` из ответа на вход.

| Тест | Проверяет |
|---|---|
| вход → `GET /api/auth/me` с cookie из ответа | `200`, текущий пользователь (как сейчас) |
| после входа в `spring_session` есть строка, `principal_name` = логин | сессия в БД, а не в памяти |
| контекст в сохранённой сессии (через `SessionRepository`) — `CurrentUser` без хеша пароля | хеш не попадает в БД (сейчас читается из `MockHttpSession`) |
| вход меняет id сессии: старая cookie после входа не действует | защита от фиксации сессии |
| выход: `204`, строки сессии нет, запрос со старой cookie — `401` | выход удаляет сессию |
| запрос с cookie несуществующей сессии — `401 UNAUTHENTICATED` | как после перезапуска |
| байты атрибута контекста испорчены `UPDATE`-ом → запрос — `401`, не `500`; в журнале `WARN`; строка сессии на месте | §2.5 |
| просроченная сессия (`last_access_time` давно, как после 30 минут без запросов) — `401` | срок жизни |
| хранилище сессий бросает ошибку доступа к БД (Mockito-spy репозитория сессий, как `InboxDao`) → запрос с cookie — `500`, Problem Details с `INTERNAL_ERROR`, не `401` (у адресов `500` в контракте не описан — тест ставит `Contract.SKIP_HEADER` с причиной) | §2.6: падение БД не выкидывает на вход |
| `/actuator/health` без cookie при той же ошибке хранилища — отвечает | healthcheck не зависит от сессий |

Остальные тесты входят через `TestSecurity.asUser` (`user()` из Spring Security Test) и сессии не используют. Если
выяснится, что они создают строки `spring_session`, `TestRows` очищает таблицу в `@AfterEach`.

**Схема (`SchemaMigrationTests`).** Новая версия в ожидаемом списке миграций; строка `spring_session_attributes` без
сессии отвергается внешним ключом; удаление сессии удаляет её атрибуты (`ON DELETE CASCADE`); повтор `session_id`
отвергается уникальным индексом.

**Unit.**
- `Deserializer` §2.5: корректные байты → объект; испорченные → `null`, без исключения.
- Отображение статуса в код обработчика `/error` §2.6: `500`, `503` → `INTERNAL_ERROR`; `401`, `403`, `404` — свои
  коды; `400` → `BAD_REQUEST`, `405` → `METHOD_NOT_ALLOWED`, `415` → `UNSUPPORTED_MEDIA_TYPE`.

**Веб.** `session-lost.spec.ts` и `client.test.ts` — на имя `SESSION`; остальные тесты Vitest и Playwright проходят
без изменений.

**e2e (`e2e/`).** Изменений нет, все существующие проходят.

**Ручная проверка** (`docs/manual-testing.md`, раздел 3). e2e не умеют ронять `dispatch`, перезапуск контейнеров из
e2e не делаем: интеграционные тесты доказывают главное — сессия читается из БД, а не из памяти. Выживание
проверяется руками: вход в обоих окнах → `make dispatch-kill` → `make dispatch-start` → обновить страницу:
пользователь на месте, повторного входа нет. При `make db-kill` / `make db-start` — как сейчас: пока базы нет,
интерфейс показывает ошибки загрузки и не уводит на вход; после возврата базы вход не нужен.

## 5. Известные ограничения

Записываются в `README.md` и `docs/dispatch-design.md` §2 вместе с реализацией.

- **Нет абсолютного предела сессии.** Сессия живёт, пока есть запросы. Веб-клиент опрашивает сервер, пока вкладка
  видна (реестр — каждые 10 с, карточка — каждые 5 с до итога), поэтому открытая видимая вкладка держит сессию
  сколько угодно, даже если человек ушёл. OWASP для таких случаев рекомендует абсолютный предел (обычно 4–8 ч с
  момента входа, затем вход заново). ТЗ его не требует; если понадобится — фильтр, который удаляет сессию старше
  предела по `creation_time` и отвечает `401` (веб-клиент уже ведёт на вход и возвращает на прежний адрес).
- **Нет обновления id сессии (renewal).** Id меняется только при входе. Периодическая смена id во время работы
  ограничивает ущерб от перехваченного id, но у SPA с параллельными запросами требует «периода милости» для старого
  id (иначе запросы, ушедшие со старым id, получают `401`). Защиту от фиксации даёт смена id при входе; от перехвата по
  сети защищает HTTPS, которого на стенде нет.
- **Нет «Запомнить меня».** После 30 минут без запросов (вкладка закрыта или скрыта) нужно войти заново. Работающего
  человека это не касается: каждый запрос продлевает сессию. Если понадобится — проще всего
  `SpringSessionRememberMeServices`: галочка при входе продлевает срок бездействия этой сессии до N дней, без новой
  таблицы.
- **Снимок пользователя в сессии может устареть.** В сессии лежит `CurrentUser` на момент входа (роль, служба,
  `enabled`). Если поменять пользователя прямо в БД, он сохранит прежние права до выхода или истечения сессии — теперь
  и через перезапуски `dispatch`. Управления пользователями в продукте нет (демо-пользователи — только миграцией).
  Когда появится, правильное решение — при изменении пользователя удалять его сессии по `principal_name` (индекс
  есть).
- **Сессии зависят от БД.** Пока БД недоступна, запросы вошедших пользователей отвечают `500` (§2.6). Видимо это
  ничего не меняет: без БД и сейчас не работает почти ничего.
- **Таблицы сессий не следуют правилам схемы проекта** (§2.2): формат задаёт фреймворк.

## 6. Вне объёма

- Список активных сеансов пользователя, «выйти на всех устройствах», ограничение числа одновременных входов —
  возможны поверх `principal_name`, но ТЗ их не требует.
- Абсолютный предел, renewal, «Запомнить меня» — §5.
- Сериализация атрибутов в JSON (§2.1), Redis и другие хранилища, отдельная схема БД для сессий.
- Перенос сессий из памяти при выкатке.
- Перезапуск контейнеров из e2e-тестов.
- `Secure`-cookie и HTTPS: стенд работает по http.

## 8. Отличия реализации

- **Код ошибки для прочих `4xx`.** Новый `BAD_REQUEST` в `ErrorCode` не заведён: ошибки фреймворка уже получают в
  `code` имя HTTP-статуса (`ApiExceptionHandler`), контракт это описывает, обработчик `/error` использует то же
  правило (§2.6, Q14).
- **Как Spring Session считает истечение.** Сессию отвергает проверка `last_access_time + max_inactive_interval`;
  колонка `expiry_time` нужна только плановой очистке. Тест состаривает сессию через `last_access_time`.
- **Журнал `/error`.** `ERROR` пишется только для ошибки, которую переслал контейнер (есть атрибут статуса):
  прямой вызов публичного адреса `/error` ничего не пишет. Ошибки, которые Tomcat отвергает до приложения (битая
  кодировка адреса, `GET /api/%zz`), отвечает сам Tomcat своей HTML-страницей; это вне Spring и вне объёма.
- **Нагрузка NF08 до перехода** (`docs/load-report.md`, два полных прогона на свежем стенде, 5000 заявок, 20 клиентов):
  p95 чтения 195,5 мс и 186,9 мс (порог 2 с); p95 изменения 188,4 мс и 102,7 мс (порог 3 с); 0 ошибок; 145 и
  174 запроса в секунду.
- **Нагрузка NF08 после перехода:** заполняется после прогона (шаг 6 плана).
