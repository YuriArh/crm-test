# Спека: сценарии перевозчика для демо — изменить итог, забыть операцию

Статус: согласовано (18.11.2026). План — `docs/plans/carrier-scenarios-plan.md`. Основание: ТЗ D05 («расхождения не затираются автоматически без
описанного правила и фиксируемого решения», «неоднозначность … видна оператору»), D06 («оператор может повторить
допустимую операцию и увидеть исход»), раздел 7 (демо-данные с разными исходами), NF01 (данные в интерфейсе — данные
работающего приложения). Пересматривает решение Q4/Q21 спеки `docs/specs/demo-seed.md` («расхождения — только
правкой базы эмулятора через `psql`, в сид не входят»; решение пользователя 17.11.2026).

Опирается на реализованные спеки: `docs/specs/reconciliation.md` (сверка, виды `RECONCILIATION_CONFLICT`,
`EXTERNAL_MISSING`, действия), `docs/specs/web-problems.md` (экраны), `docs/specs/demo-seed.md` (`make seed`),
`docs/carrier-emulator-design.md` (эмулятор).

## 1. Зачем

После `make seed` у оператора одна открытая проблема — «Некорректное сообщение перевозчика» с единственным
действием «Разобрано». Всё остальное система разбирает сама. Проверяющий не видит главного из D05/D06: как
оператор решает расхождение («Принять версию перевозчика» / «Оставить наш итог») и повторяет отправку операции,
которую потерял перевозчик. Чтобы увидеть это, сейчас нужна ручная правка базы эмулятора по
`docs/manual-testing.md` §8.

Честный эмулятор такие ситуации не создаёт: он исполняет операцию один раз и не меняет итог. В индустрии такие
ситуации в тестовых средах внешних сервисов создают **служебными эндпоинтами самого сервиса**, которые переводят
его объекты в нужное состояние через его же код (тестовые помощники песочниц платёжных API, административный API
сервисов-заглушек вроде WireMock). Правка базы чужой системы в обход её кода считается обходным путём: она
привязывает проверку к схеме и обходит правила системы.

## 2. Ограничение

**Существующий код не меняется** (решение пользователя 17.11.2026). Добавляются только новые эндпоинты эмулятора с
новыми классами. Не меняются:
- `dispatch` целиком — код, схема, контракт `dispatch-api.yaml`, web;
- существующий код эмулятора: приём, исполнитель, лента, сбои, `GET /admin/operations`;
- схема эмулятора: новых миграций нет.

Меняются: новые классы эмулятора, `contracts/carrier-api.yaml` (раздел `admin`, код ошибки), тесты,
`scripts/seed.sh`, документы. Единственная правка существующего файла эмулятора — новая константа
`OPERATION_NOT_SETTLED(HttpStatus.CONFLICT)` в перечислении `web/ErrorCode` (коды ошибок контракта собраны там, и
общий обработчик ошибок отвечает только ими); логика не меняется.

## 3. Эндпоинты эмулятора

Новый класс `admin/AdminScenariosController` и класс доступа к данным `admin/ScenarioDao` (`JdbcClient`). Оба —
только раздел `admin`: `dispatch` их не вызывает (`carrier-api.yaml`, тег `admin`).

### 3.1 `PUT /admin/operations/{operationId}/result` — перевозчик изменил итог

Тело — новый итог, по правилам `OperationResult` контракта:

```json
{"status": "SUCCEEDED", "trackingNumber": "TRK-FFFFFFFF", "price": 999.00, "reason": null}
```

- `SUCCEEDED` — обязательны `trackingNumber` (формат контракта) и `price` (диапазон контракта), `reason` — `null`;
  `REJECTED` — обязательна непустая `reason`, `trackingNumber` и `price` — `null`. Иначе `400 VALIDATION_FAILED`.
- Меняется строка операции: статус, номер, цена, причина и **новый** `result_message_id` (UUIDv7). Новый итог —
  новое сообщение: тот же `messageId` с другим содержимым нарушил бы правило «запись с полученным `messageId` —
  дубликат». `sequence` остаётся 2, `executedAt` прежний.
- Одним условным `UPDATE … WHERE operation_id = :id AND state = 'EXECUTED' AND result_publish_at IS NULL`:
  - операции нет — `404 OPERATION_NOT_FOUND`;
  - операция не исполнена или её итог ещё ждёт отложенной публикации (`delayed`) — `409 OPERATION_NOT_SETTLED`
    (иначе исполнитель опубликовал бы изменённый итог, и это был бы не «перевозчик изменил итог», а другой итог с
    самого начала).
- Лента **не меняется**: её пишет только исполнитель. `GET /operations/{operationId}` сразу отдаёт новый итог —
  это то, что видит сверка `dispatch`.
- Ответ `200` — `AdminOperation` после изменения. В лог — `WARN Scenario changeResult: operation … result changed
  (was …, now …)`.

### 3.2 `DELETE /admin/operations/{operationId}` — перевозчик потерял операцию

- В одной транзакции: блокировка строки операции (`SELECT … FOR UPDATE`), удаление её записей ленты, удаление
  строки. Блокировка первой нужна из-за исполнителя: иначе он мог бы между двумя удалениями исполнить операцию и
  вставить запись ленты, и удаление строки упало бы на внешнем ключе.
- Операции нет — `404 OPERATION_NOT_FOUND`. Ответ `204`.
- Допустимо в любом состоянии. Исполнитель с этим уже справляется: перевод `ACCEPTED → EXECUTED` и снятие
  отложенной публикации — условные `UPDATE`, по пропавшей строке они ничего не делают.
- После удаления `GET /operations/{operationId}` — `404`, в `GET /admin/operations` её нет. Повторная отправка того
  же `operationId` принимается как новая операция и исполняется (у перевозчика, потерявшего первую, это первое
  исполнение).
- В лог — `WARN Scenario forget: operation … forgotten (state …, feed entries …)`.
- `docs/carrier-emulator-design.md` §8 «Записи не удаляются» получает исключение: кроме этого сценария.

### 3.3 Контракт

`contracts/carrier-api.yaml`: два пути с тегом `admin` и описанием сценария; схема тела `AdminResultChange`;
код `OPERATION_NOT_SETTLED` в `Error.code`. Правило «Reconciliation» описания контракта получает оговорку: после
`PUT …/result` итог операции намеренно расходится с её записями ленты. `dispatch` код ошибки читает как строку,
`admin` не вызывает — его код не меняется. `make contracts-lint`.

### 3.4 Чего здесь нет: `RESULT_CONFLICT`

Второй итог **в ленте** («Расхождение итогов») по правилам — только через исполнитель, единственного писателя ленты:
запись мимо него может пропустить курсор `dispatch` (`docs/manual-testing.md` §8.2). Это изменение существующего
кода — вне ограничения §2. Остаётся ручной проверкой через `psql`. Если ограничение снимут, сюда добавится
`POST /admin/operations/{operationId}/republish` через исполнитель.

## 4. `make seed`: заявки, которые ждут оператора

Добавляются три сценария после `seed-north-8`, по тем же правилам (`docs/specs/demo-seed.md` §2.2–2.3): по одному,
пропуск уже созданных, режимы выключены при выходе. Все в «Севере». После каждого — «Сверить сейчас» сида под
`north.operator` с ключом `seed-north-N-reconcile`: фоновая сверка заявки с итогом не берёт, а без итога — только
через 2–3 минуты.

| Ключ | Сценарий | Что видит оператор |
|---|---|---|
| `seed-north-9` | итог → `PUT …/result` (другой номер и стоимость) → «Сверить сейчас» | «Расхождение при сверке»: «Версия перевозчика» и «Наш итог», «Принять версию перевозчика» / «Оставить наш итог» |
| `seed-north-10` | итог → `DELETE` → «Сверить сейчас» | «Перевозчик не знает операцию» с «Наш итог»: «Оставить наш итог» |
| `seed-north-11` | `delayed` → получение подтверждено → режим выключен → `DELETE` (до публикации итога, окно 15 с) → «Сверить сейчас» | «Перевозчик не знает операцию», итога нет: «Повторить отправку» |

После сида у оператора 4 открытые проблемы четырёх разных случаев (с `seed-north-8`), счётчик шапки 4, в реестре
значки у четырёх заявок. Итоговая таблица сида их показывает. Сид ничего не решает за оператора.

Фоновая сверка потом перепроверяет открытые `RECONCILIATION_CONFLICT` и `EXTERNAL_MISSING` с растущей паузой; ответ
перевозчика тот же, поэтому ничего не меняется — проблемы ждут оператора.

Итого 14 заявок. `executionCount = 1` у всех операций, которые эмулятор знает (у `seed-north-10` и `seed-north-11`
операций у перевозчика нет — он их «потерял»; после «Повторить отправку» у `seed-north-11` — снова одна).

## 5. Ручные проверки

`docs/manual-testing.md` §8.1, §8.3, §8.4 переходят с `psql` на эндпоинты (`curl` к `CARRIER_BASE_URL`); оговорка
«делается на простаивающем стенде» к ним больше не относится. §8.2 (`RESULT_CONFLICT`) остаётся на `psql`.
Добавляется: «после `make seed` — разберите четыре проблемы `seed-north-8…11`» с ожиданиями по каждой кнопке.

## 8. Вне объёма

- `RESULT_CONFLICT` в сиде (§3.4).
- `DELIVERY_FAILED` в сиде: попытки кончаются через ~10 минут недоступности.
- Сброс эмулятора или «вернуть операцию» — не нужны: `make reset`.
- Эндпоинты для смены содержимого операции у перевозчика (вес, адрес): `dispatch` содержимое не сверяет.

## 9. Принято самостоятельно (на согласование)

1. Пути — под существующим `/admin/operations/{operationId}`: `PUT …/result`, `DELETE`.
2. Новый `messageId` при изменении итога (§3.1).
3. `409 OPERATION_NOT_SETTLED` для неисполненной операции и для итога, ждущего отложенной публикации.
4. Три сценария сида, все с «Сверить сейчас» сида; сид не решает проблемы.
