# Спека: проблемы обмена и действия оператора

Статус: согласовано (16.11.2026), план — `docs/plans/operator-problems-plan.md`. Основание: ТЗ D04 («некорректное сообщение требует разбора»), D05 («неоднозначность
после потери ответа должна быть видна оператору», «расхождения не затираются автоматически без описанного правила и
фиксируемого решения»), D06 («оператор может повторить допустимую операцию и увидеть исход»), D-NF03, NF02, NF04;
итог проектного опроса Q1–Q23 (16.11.2026). Дизайн `dispatch` — `docs/dispatch-design.md`; эта спека меняет его §4, §5
и §7. Это первая из трёх спек пункта 3 этапа 2: дальше сверка (`docs/specs/reconciliation.md`) и демо-данные со
сбоями (`docs/specs/demo-seed.md`). Экраны — отдельная web-спека после всех трёх.

## 1. Зачем

Обмен уже переживает сбои: повторяет отправку, отсеивает дубликаты и устаревшие результаты, не даёт плохой записи ленты
остановить приём. Но всё, что требует человека, сейчас лежит в колонках, которые видит только тот, кто читает базу:

- доставка в `UNKNOWN` (ответ потерян, дошла ли заявка — неизвестно) видна только как статус;
- доставка в `FAILED` (попытки кончились, перевозчик отверг запрос) ждёт оператора, а действия у него нет;
- запись ленты `INVALID` или `FAILED` и запись `CONFLICT` видны только через `make inbox`;
- конфликтующий итог никто не может ни принять, ни отклонить — а это номер отправления и деньги клиента.

Спека делает такие ситуации **проблемами**: у каждой есть вид, заявка (если известна), причина, момент открытия и
закрытия, и кто закрыл с каким решением. Оператор видит список проблем своей службы и закрывает их действиями.

## 2. Решение

### 2.1 Виды проблем

| Вид | Когда открывается | Источник | Как закрывается |
|---|---|---|---|
| `DELIVERY_UNKNOWN` | операция перешла в `UNKNOWN` (таймаут или обрыв после отправки, прерванная отправка) | заявка | система: доставка подтверждена (ответом, результатом; в спеке (b) — сверкой) |
| `DELIVERY_FAILED` | операция перешла в `FAILED` (попытки кончились, `4xx`, `409 PAYLOAD_MISMATCH`) | заявка | система: доставка подтверждена; оператор: «Повторить отправку» |
| `INVALID_MESSAGE` | запись `inbox` стала `INVALID` (плохие данные перевозчика) | запись `inbox` | оператор: «Разобрано» |
| `MESSAGE_FAILED` | запись `inbox` стала `FAILED` (у нас не получилось её обработать) | запись `inbox` | оператор: «Разобрано» |
| `RESULT_CONFLICT` | запись `inbox` стала `CONFLICT` | запись `inbox` | оператор: решение конфликта |

Пояснения:

- **`DELIVERY_UNKNOWN` открывается сразу**, при первом `UNKNOWN` (решение Q3). Повтор при этом идёт автоматически, а
  проблема показывает оператору неоднозначность (D05). Её закрывает только подтверждение: переход
  `UNKNOWN → RETRY_WAIT` или `UNKNOWN → FAILED` неоднозначность не снимает (одна из прошлых попыток могла дойти),
  поэтому проблема остаётся открытой. Повтор оператором её тоже не закрывает.
- **`DELIVERY_UNKNOWN` и `DELIVERY_FAILED` могут быть открыты одновременно**: попытки кончились, а последняя из них
  дошла ли — неизвестно. Подтверждение закрывает обе.
- **`409 PAYLOAD_MISMATCH` — не отдельный вид** (решение Q6). Содержимое заявки неизменяемо и хэшируется, поэтому
  такой ответ означает ошибку у нас, а не бизнес-ситуацию. Это `DELIVERY_FAILED`, причина — `last_error` операции.
- **`MESSAGE_FAILED` отдельно от `INVALID_MESSAGE`**: `INVALID` — плохие данные перевозчика, `FAILED` — наш сбой
  (`docs/specs/feed-bad-records.md`). Оператор разбирает их по-разному, поэтому и вид разный.
- **Проблема без заявки.** `INVALID_MESSAGE` по записи без `operationId` или с незнакомым `operationId` не
  привязана к заявке; её видят все операторы (решение Q13).
- **«Разобрать заново» нет** (решение Q6). Итог заявки, чья запись стала `INVALID` или `FAILED`, подтянет сверка
  (спека (b)). Оператор закрывает проблему «Разобрано» с комментарием.

### 2.2 Хранение: таблица `problem` (миграция `V9__problems.sql`)

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | `uuid` | UUIDv7 из приложения |
| `kind` | `text` | вид, `CHECK` по §2.1 |
| `status` | `text` | `OPEN` / `RESOLVED` |
| `request_id` | `uuid` null, FK `delivery_request` | заявка; пусто только у проблем записи без заявки |
| `inbox_id` | `uuid` null, FK `inbox` | запись-источник у `INVALID_MESSAGE`, `MESSAGE_FAILED`, `RESULT_CONFLICT` |
| `details` | `text` | причина на момент открытия (`last_error` операции или `reason` записи), через `SafeText` |
| `opened_at` | `timestamptz` | из `Clock` |
| `resolved_at` | `timestamptz` null | |
| `resolved_by` | `uuid` null, FK `app_user` | оператор; пусто, если закрыла система |
| `decision` | `text` null | `SYSTEM` / `RETRIED` / `APPLY_CARRIER` / `KEEP_OURS` / `ACKNOWLEDGED` |
| `comment` | `varchar(2000)` null | комментарий оператора |

Ограничения (каждое со своим именем, NF03):

- `problem_kind_valid`, `problem_status_valid`, `problem_decision_valid` — списки значений;
- `problem_resolution_complete`: `status = 'OPEN'` ⇔ `resolved_at`, `decision` пусты; у `RESOLVED` оба заполнены;
- `problem_system_has_no_author`: `decision = 'SYSTEM'` ⇔ `resolved_by IS NULL`;
- `problem_decision_needs_comment`: `APPLY_CARRIER`, `KEEP_OURS`, `ACKNOWLEDGED` — с `comment`;
- `problem_comment_not_blank`: `comment IS NULL OR btrim(comment) <> ''`;
- `problem_source_matches_kind`: виды доставки — `request_id NOT NULL AND inbox_id IS NULL`; виды записи —
  `inbox_id NOT NULL`;
- `problem_decision_matches_kind`: `RETRIED` — только `DELIVERY_FAILED`; `APPLY_CARRIER` / `KEEP_OURS` — только
  `RESULT_CONFLICT`; `ACKNOWLEDGED` — только `INVALID_MESSAGE`, `MESSAGE_FAILED`; виды записи система не закрывает.

Индексы:

- `problem_open_per_request_kind` — уникальный частичный `(request_id, kind) WHERE status = 'OPEN' AND inbox_id IS
  NULL`: у заявки не больше одной открытой проблемы доставки каждого вида;
- `problem_per_inbox_record` — уникальный частичный `(inbox_id) WHERE inbox_id IS NOT NULL`: запись даёт одну
  проблему за всю жизнь;
- `problem_list_idx` — `(status, opened_at DESC)` для списка;
- `problem_request_idx` — `(request_id)` для карточки.

Служба проблемы — служба заявки (через `request_id`); отдельной колонки нет. В `SchemaMigrationTests` каждое
ограничение получает тест на отказ.

**Перенос текущего состояния.** Новая таблица сама старые строки не заполняет (шаблон expand / migrate / contract),
поэтому `V9` в конце открывает проблемы по уже существующему состоянию одним `INSERT … SELECT` на вид, id —
встроенная в PostgreSQL 18 `uuidv7()`, время — `now()` миграции:

- операции в `UNKNOWN` → `DELIVERY_UNKNOWN`; в `FAILED` → `DELIVERY_FAILED` (`details` — `last_error`);
- записи `inbox` `INVALID` → `INVALID_MESSAGE`, `FAILED` → `MESSAGE_FAILED`, `CONFLICT` → `RESULT_CONFLICT`
  (`details` — `reason`; заявка — по `operation_id`, если он известен).

Это не демо-данные, а перенос существующего состояния: без него стенд после обновления показал бы «проблем нет» при
операциях в `FAILED`. Данных мало, пачки не нужны. Тест в `SchemaMigrationTests`: строки в этих состояниях до `V9` —
после неё у каждой ровно одна открытая проблема нужного вида.

### 2.2.1 Операция: бюджет повторов и применённая запись (миграция `V10__operation_retry_budget.sql`)

Две колонки в `dispatch_operation`, обе нужны действиям оператора (§2.4):

| Колонка | Тип | Смысл |
|---|---|---|
| `retry_from` | `integer NOT NULL DEFAULT 0` | номер попытки, с которой начался текущий бюджет повторов; «Повторить» ставит его равным `attempts` |
| `applied_inbox_id` | `uuid` null, FK `inbox` | запись, чьё содержимое сейчас применено к заявке |

Ограничение `dispatch_operation_retry_from_range`: `retry_from BETWEEN 0 AND attempts`.

**Почему `attempts` не сбрасывается.** `attempts` — сквозной номер попытки: по нему нумеруются строки
`exchange_attempt` (`UNIQUE (operation_id, attempt_no)`), и он же — токен, по которому запись исхода и восстановление
проверяют, что операция всё ещё их (`WHERE attempts = :attempt`). Такой токен обязан только расти: если номер
вернётся к прежнему, опоздавший воркер запишет исход в чужую попытку, а новая попытка №1 нарушит уникальность.
Поэтому «сброс счётчика» из §7 дизайна — это новый бюджет, а не новый отсчёт: так же повтор из dead-letter queue
ставит сообщение заново со свежим счётчиком приёмов, не трогая историю. `RetryPolicy` получает номер попытки
**внутри бюджета** — `attempts − retry_from` — и в записи исхода (`SendWorker.retryOrFail`), и в восстановлении
(`SendWorker.recover`); `claimNext` и `findExpired` возвращают `retry_from` вместе с `attempts`. Пауза тоже считается
от номера внутри бюджета: первый повтор после решения оператора — через 5 с, а не через 5 мин.

**Почему нужна применённая запись.** Правила разбора сравнивают пришедшую запись с применённой при том же
`sequence` (`InboxDao.appliedContent` ищет строку `inbox` в `APPLIED`). После «применить спорную запись» (§2.4)
применена уже она, а в `APPLIED` по-прежнему старая; повтор спорной записи с новым `messageId` открыл бы конфликт
по решённому вопросу. Так же устроено разрешение конфликтов в CouchDB: все версии хранятся, одна помечена
победителем, ручное решение переносит отметку. Здесь все версии — строки `inbox`, отметка — `applied_inbox_id`; её
ставят и обработчик при `APPLIED`, и решение оператора. `appliedContent` читает содержимое записи
`applied_inbox_id`, если её `sequence` равен пришедшему; меньший `sequence` и так `STALE`. Строки `inbox` своих
статусов не меняют: исход разбора — история.

`V10` заполняет `applied_inbox_id` по существующим данным: запись `APPLIED` операции с наибольшим `sequence`.

### 2.3 Где проблемы открываются и закрываются

Проблема меняется **в той же транзакции**, что и переход, который её вызвал, и **только если условный `UPDATE`
перехода сработал** (решение Q2). Так проблема не расходится с состоянием: нельзя получить «доставка подтверждена, а
`DELIVERY_UNKNOWN` открыта» или наоборот.

Новый пакет `com.acme.dispatch.problem`:

- `ProblemDao` — SQL через `JdbcClient`: открыть (`INSERT … ON CONFLICT DO NOTHING` по частичным уникальным
  индексам — повторное открытие уже открытой проблемы ничего не делает), закрыть системой, закрыть оператором
  (условно, `WHERE status = 'OPEN'`), список, проблемы заявки;
- `ProblemService` — два входа для обмена и действия оператора (§2.4):
  - `onDeliveryStatus(requestId, operationId, newStatus, lastError, unknownOutcome, now)` — вызывается после каждого
    сработавшего перехода доставки: `UNKNOWN` → открыть `DELIVERY_UNKNOWN`; `FAILED` → открыть `DELIVERY_FAILED`, а
    если попытка, исчерпавшая бюджет, сама закончилась неизвестным исходом (таймаут, прерванная отправка;
    `unknownOutcome` — её ошибка), то и `DELIVERY_UNKNOWN`: перевозчик мог её получить; `ACKNOWLEDGED` → закрыть
    обе (`SYSTEM`); `PENDING`, `SENDING`, `RETRY_WAIT` — ничего. Причина `DELIVERY_UNKNOWN` — ошибка попытки с
    неизвестным исходом, `DELIVERY_FAILED` — новый `last_error`;
  - `onInboxOutcome(inboxId, requestId, decision, reason, now)` — после записи исхода разбора: `INVALID` →
    `INVALID_MESSAGE`, `FAILED` → `MESSAGE_FAILED`, `CONFLICT` → `RESULT_CONFLICT`; остальные — ничего.

Места вызова (каждое — после сработавшего условного обновления, внутри уже открытой транзакции):

| Где | Переход |
|---|---|
| `SendWorker.record` | `ACKNOWLEDGED`, `UNKNOWN`, `FAILED` (`RETRY_WAIT` — ничего) |
| `SendWorker.recover` | `UNKNOWN` (переназначена), `FAILED` (попытки кончились) |
| `InboxProcessor` | результат подтвердил доставку (`applyToOperation` перевёл операцию в `ACKNOWLEDGED`); исход записи `INVALID`, `FAILED`, `CONFLICT` |

**Разбор: проблемы — вне точки сохранения.** `InboxProcessor` считает любой отказ базы под точкой сохранения
(`DataIntegrityViolationException`) плохими данными перевозчика и сразу пишет запись `INVALID`. Это правило верно,
только пока под точкой сохранения пишутся данные перевозчика. Если открыть там проблему, ошибка в нашем коде
проблем станет «перевозчик прислал мусор». Поэтому область, где действует это правило, остаётся узкой (как список
типов исключений в классификаторе ошибок Spring Kafka):

- `decide` под точкой сохранения только применяет запись и возвращает, что произошло: исход и подтвердил ли
  результат доставку (`InboxDao.applyToOperation` сообщает, сработал ли перевод в `ACKNOWLEDGED`; сейчас это скрыто);
- проблемы меняются **после** точки сохранения, рядом с `recordOutcome` / `recordFailed`, в той же транзакции записи:
  закрытие проблем доставки при подтверждении, открытие `INVALID_MESSAGE`, `MESSAGE_FAILED`, `RESULT_CONFLICT`.

**Заявка у `INVALID_MESSAGE`.** Запись, не прошедшая проверку, до поиска операции не доходит, но её `operationId`
может быть корректным UUID известной заявки. Проблема ищет заявку по `operation_id` записи (если он разобрался);
не нашлась — проблема без заявки. Иначе проблема по заявке одной службы стала бы видна операторам всех служб.

**Если база отвергла саму проблему** (это возможно только из-за ошибки в нашем коде), откатывается вся транзакция
перехода, и это заметно, а не тихо:

- `SendWorker.record` — исход не записан, операция остаётся `SENDING` и через срок захвата уходит в восстановление;
- `SendWorker.recover` — откатывается всё восстановление прохода, и `runOnce` падает до отправки: **отправка
  останавливается целиком**, пока ошибку не исправят;
- разбор — как сегодня при недоступной базе: запись остаётся `RECEIVED`, проход останавливается.

Решение Q2 (одна транзакция) это не меняет: рассинхронизация проблемы и состояния хуже остановки, а остановка видна
в журнале `ERROR` и в метриках. Каждый случай покрыт тестом (§3).

**Журнал (NF10):** открытие — `WARN` `Problem <kind> opened for request <id> (operation <operationId>): <details>`;
закрытие системой — `INFO`; закрытие оператором — `INFO` с логином и решением, без текста комментария.

### 2.4 Действия оператора

Все действия:

- только оператор службы заявки (`RequestPermissions`): инициатору — `403 FORBIDDEN` на свою заявку и `404 NOT_FOUND`
  на чужую, оператору другой службы — `404`; проблему без заявки может закрыть любой оператор;
- обязательный `Idempotency-Key` (`IdempotencyService`, в транзакции действия): повтор с тем же ключом возвращает
  сохранённый ответ, а не `409` (решение Q15). В отпечаток запроса входит **цель действия** (id заявки или проблемы)
  вместе с телом: тот же ключ для другой заявки — `422 IDEMPOTENCY_KEY_REUSED`, а не чужой сохранённый ответ (так
  Stripe сравнивает параметры повтора с исходным запросом);
- действие, недопустимое в текущем состоянии, — `409 INVALID_STATE`, ничего не меняется;
- каждое действие пишет в журнал `INFO`: логин, действие, заявка, `operationId`, исход.

#### Повторить отправку — `POST /api/requests/{id}/retry`

Тела нет. Доступно, когда доставка в `FAILED` или `UNKNOWN`. Одной транзакцией:

1. условный `UPDATE dispatch_operation … WHERE request_id = :id AND delivery_status IN ('FAILED', 'UNKNOWN')`:
   `retry_from = attempts` (новый бюджет повторов, §2.2.1; `attempts` не меняется), `next_attempt_at = now`,
   `last_error = NULL`, статус: `FAILED → PENDING`, `UNKNOWN` остаётся
   `UNKNOWN` (неоднозначность не снята); `operationId` прежний — повтор безопасен, перевозчик не исполнит операцию
   дважды (D-NF02);
2. если обновление не сработало (операция уже `SENDING`, `ACKNOWLEDGED`, …) — `409 INVALID_STATE`;
3. открытая `DELIVERY_FAILED` закрывается: `RETRIED`, оператор, без комментария.

Ответ `200` — карточка заявки (`RequestCard`, как `GET /api/requests/{id}`). Исход отправки оператор видит в карточке:
она обновляется сама (D06 «увидеть исход»).

Спека (b) расширяет условие: «Повторить» доступно и для `ACKNOWLEDGED`, если открыта `EXTERNAL_MISSING`.

#### Решить конфликт — `POST /api/problems/{id}/resolve`, `RESULT_CONFLICT`

Тело `{"decision": "APPLY_CARRIER" | "KEEP_OURS", "comment": "…"}`, комментарий обязателен (1–2000 символов после
`strip`). Обе версии пришли от перевозчика: применённая раньше и спорная запись `inbox`.

- **`KEEP_OURS`** — итог заявки не меняется, проблема закрыта.
- **`APPLY_CARRIER`** — итог заявки заменяется содержимым спорной записи. Доступно, только если спорная запись —
  итог (`SUCCEEDED` или `REJECTED`): применять `IN_PROGRESS` поверх итога значило бы откатить итог; иначе
  `409 INVALID_STATE`, доступно только `KEEP_OURS`. Одной транзакцией под блокировкой строки операции (как у
  обработчика результатов): бизнес-статус и поля результата заявки из записи, `version + 1`, `updated_at`;
  `last_applied_seq = max(текущий, sequence записи)`, `applied_inbox_id` — спорная запись (§2.2.1); проблема
  закрыта. Строка `inbox` остаётся `CONFLICT`: исход разбора — история, решение — в `problem`.

**Порядок блокировок.** Решение блокирует строку операции (`FOR UPDATE`), затем условно закрывает проблему
(`WHERE status = 'OPEN'`). Разбор блокирует запись `inbox`, затем строку операции, затем вставляет проблему (новую
строку, не блокировку существующей). «Повторить» обновляет только строку операции и проблему доставки. Цикла
ожиданий нет; новый код обязан держать этот порядок: операция раньше проблемы.

Это единственный путь, которым итоговый результат меняется после того, как стал итоговым (решение Q9). Автоматически
итог по-прежнему не меняется никогда. Правка пользователя, начатая до решения, получит `409 VERSION_CONFLICT`
(`version + 1`).

Спека (b) добавляет те же решения для `RECONCILIATION_CONFLICT`.

#### Разобрано — `POST /api/problems/{id}/resolve`, `INVALID_MESSAGE` / `MESSAGE_FAILED`

Тело `{"decision": "ACKNOWLEDGED", "comment": "…"}`, комментарий обязателен. Закрывает проблему, ничего другого не
меняет.

#### Общие правила `resolve`

- Проблема уже `RESOLVED` или решение не подходит виду (например, `ACKNOWLEDGED` для `RESULT_CONFLICT`,
  `RETRIED` или `SYSTEM` через `resolve`, любое решение для `DELIVERY_*`) — `409 INVALID_STATE`.
- Закрытие условное (`WHERE status = 'OPEN'`): два оператора, решающие одновременно, — первый закрывает, второй
  получает `409 INVALID_STATE`. Версия заявки в запросе не нужна (решение Q15).
- Пустой или слишком длинный комментарий, неизвестное решение — `400 VALIDATION_FAILED` с ошибкой поля.
- Ответ `200` — проблема (`Problem`, §2.5) после закрытия.

### 2.5 Чтение

#### `GET /api/problems`

Только оператор (инициатору `403`). Параметры: `status` (`OPEN` по умолчанию, `RESOLVED`, `ALL`), `kind` (можно
несколько), `page`, `size` (до 100, по умолчанию 20). Сортировка — `opened_at DESC, id DESC`. Область: проблемы
заявок службы оператора и проблемы без заявки. Ответ — `PageResponse<Problem>`.

#### `Problem`

| Поле | Содержимое |
|---|---|
| `id`, `kind`, `status`, `details`, `openedAt`, `resolvedAt` | из строки |
| `request` | `{id, number}` или `null` |
| `operationId` | операции заявки или из записи; `null`, если неизвестен |
| `message` | для видов записи: `{messageId, feedSeq, status, sequence, trackingNumber, price, reason, occurredAt, payloadExcerpt}` — поля, что удалось разобрать (иначе `null`), и начало исходного текста (до 2000 символов, через `SafeText`); иначе `null` |
| `currentResult` | для `RESULT_CONFLICT`: текущий итог заявки (`BusinessResult` + статус), чтобы сравнить со спорной записью; иначе `null` |
| `resolvedBy` | `{id, name}` или `null` (система или ещё открыта) |
| `decision`, `comment` | |
| `actions` | доступные решения: `["APPLY_CARRIER", "KEEP_OURS"]`, `["KEEP_OURS"]`, `["ACKNOWLEDGED"]` или `[]` — сервер решает, клиент только показывает |

#### Карточка заявки

`GET /api/requests/{id}` получает поле `problems` — все проблемы заявки (открытые и закрытые), новые сверху, и
`actions` — доступные действия по заявке (`["RETRY"]` или `[]`; спека (b) добавит `RECONCILE`). Для инициатора
`problems` — `null`, `actions` — `[]` (решение Q14).

Реестр не меняется: фильтр «есть открытые проблемы» и счётчики — вместе с экранами.

### 2.6 Контракт и коды ошибок

`contracts/dispatch-api.yaml`: пути `/api/problems`, `/api/problems/{id}/resolve`, `/api/requests/{id}/retry`; схемы
`Problem`, `ProblemKind`, `ProblemStatus`, `ProblemDecision`, `ResolveProblemBody`, `ProblemMessage`, поля `problems`
и `actions` в `RequestCard`; заголовок `Idempotency-Key` у обоих действий. Новых кодов ошибок нет: `INVALID_STATE`,
`FORBIDDEN`, `NOT_FOUND`, `VALIDATION_FAILED`, `IDEMPOTENCY_KEY_*` уже есть. После изменения — `make contracts-lint`
и `make web-api-types` (web-код не меняется, только типы).
