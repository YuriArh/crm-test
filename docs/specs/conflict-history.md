# Спека: расхождение остаётся видно после решения

Статус: согласовано (17.11.2026), Q1–Q3 приняты как предложено; план — `docs/plans/conflict-history-plan.md`. Основание: ТЗ D06 («история обмена … результат сверки»), D-NF03 («история позволяет
связать задание, попытки обмена, внешний результат и решение оператора»), NF05 («содержание изменения»). Меняет
`docs/specs/reconciliation.md` (§2.9 модель, §2.10 API) и `docs/specs/web-problems.md` (§7.1 блок конфликта, §8.3
«Сверки»); дизайн `dispatch` — `docs/dispatch-design.md` §4.

## 1. Зачем

Перевозчик прислал итог, который отличается от нашего (`RESULT_CONFLICT` из ленты или `RECONCILIATION_CONFLICT` при
сверке). Оператор выбрал «Принять версию перевозчика» или «Оставить наш». После этого блок конфликта в карточке
и в панели проблемы показывает две **одинаковые** колонки. Что было разным и в чём состояла проблема, понять уже
нельзя. В «Сверках» видна только сторона перевозчика.

Причина в устройстве, а не в отображении:

| Где | Что хранится | Что показывается |
|---|---|---|
| `problem` | нашей стороны нет | правая колонка — `currentResult`, итог заявки **сейчас**, то есть уже после решения |
| `reconciliation` | наша сторона только как ключ сравнения `local_result` (`SUCCEEDED\|TRK…\|1500\|`) | API её не отдаёт, «Сверки» показывают одного перевозчика |

Сторона перевозчика уже неизменна: это запись `inbox` или строка `reconciliation`. Нашу сторону система
не сохраняет, а берёт из текущего состояния заявки. Поэтому после решения расхождение «исчезает».

Общепринятый подход в сверке (reconciliation break в платёжных и учётных системах, audit trail) такой: расхождение
сохраняется как неизменный факт с **обеими** сторонами на момент обнаружения. Решение записывается отдельно, рядом
с ним. Текущее состояние объекта не заменяет историю. Эта спека так и делает.

## 2. Решение

### 2.1 Что сохраняем

- **Строка сверки** хранит нашу сторону структурно, как и сторону перевозчика: `local_status`,
  `local_tracking_number`, `local_price`, `local_reason`. `local_result` остаётся ключом сравнения для правила
  «решено ранее» (`reconciliation.md` §2.5 п. 4).
- **Проблема** с двумя сторонами (`RESULT_CONFLICT`, `RECONCILIATION_CONFLICT`, `EXTERNAL_MISSING`) хранит наш итог
  на момент, когда её открыли: `our_recorded`, `our_status`, `our_tracking_number`, `our_price`, `our_reason`.
  - Снимок берётся из `delivery_request` в том же `INSERT` (`INSERT … SELECT`), то есть в той же транзакции
    и под той же блокировкой, что и переход, открывший проблему. Отдельного чтения и передачи значений нет.
  - `RECONCILIATION_CONFLICT`, пока открыта, переставляется на последнюю строку сверки
    (`reconciliation.md` §2.5). Тот же `UPDATE` обновляет и снимок: обе стороны всегда из одного момента.
  - После закрытия снимок и ссылки не меняются (это история).
  - Наш итог — только итоговый (`SUCCEEDED`/`REJECTED`). Если итога не было, `our_recorded = true`
    и поля `our_*` пусты.

### 2.2 Модель данных — миграция `V12__conflict_sides.sql`

`reconciliation`:

- колонки `local_status text`, `local_tracking_number`, `local_price numeric(12, 2)`, `local_reason` с теми же
  длинами, что у `carrier_*` (`V8`);
- `reconciliation_local_status_valid` — `local_status IN ('SUCCEEDED', 'REJECTED')`;
- `reconciliation_local_result_complete` — правило `carrier_result_status` для нашей стороны: нет статуса — нет
  полей; `SUCCEEDED` — номер и цена; `REJECTED` — причина;
- заполнение существующих строк из `local_result`: статус — `split_part(…, 1)`, номер — 2, цена — 3, причина —
  всё после третьего `|`. Ключ строится из этих же полей (`ResultMessage.content`), поэтому разбор однозначен:
  `|` может быть только в причине, а она последняя.

`problem`:

- колонки `our_recorded boolean NOT NULL DEFAULT false` (default нужен только для заполнения, затем снимается),
  `our_status`, `our_tracking_number`, `our_price`, `our_reason`;
- `problem_our_status_valid`, `problem_our_result_complete` — так же, как у `reconciliation`;
- `problem_our_side_needs_record` — пока `our_recorded = false`, все `our_*` пусты;
- `problem_our_side_matches_kind` — `our_recorded` только у трёх видов с двумя сторонами;
- заполнение существующих: `RECONCILIATION_CONFLICT` — из её строки сверки (точно, это тот же момент). У
  `RESULT_CONFLICT` и `EXTERNAL_MISSING` прошлых данных нет, им ставится `our_recorded = false`. Восстанавливать
  снимок из текущего итога нельзя: после «Принять версию перевозчика» это был бы уже чужой итог.

### 2.3 API (`dispatch-api.yaml`)

- Новая схема `ResultSnapshot`: `status` (`SUCCEEDED`/`REJECTED`), `trackingNumber`, `price`, `reason` (каждое
  может быть `null`).
- `Reconciliation.localResult` — `ResultSnapshot | null`: наш итог в момент проверки (`null`: итога не было).
- `ExchangeProblem.ourSide` — `{ result: ResultSnapshot | null } | null`. `null` означает, что снимка нет (другой
  вид или проблема старше этой спеки). `{ result: null }` означает, что итога у нас тогда не было.
- `currentResult` остаётся как есть: по нему считаются решения, и он показывает «итог сейчас».

### 2.4 Web

**Блок конфликта** (`problems/details/ConflictView.tsx`; одинаковый в карточке и в панели):

- Колонки: «Версия перевозчика» и «Наш итог при обнаружении» (`ourSide`). Отличия отмечаются словом «отличается»,
  как сейчас, но сравнивается со **снимком**, а не с текущим итогом.
- У закрытой проблемы под колонками добавляется строка исхода: «Принята версия перевозчика» / «Оставлен наш итог» /
  «Закрыта системой», а также «Итог сейчас» (`currentResult`). Пример: после «Принять версию перевозчика»
  видно, что номер и цена были другими и какими стали.
- Если `ourSide = null` (старая проблема), правая колонка показывает `currentResult` с пометкой «итог сейчас;
  снимок на момент проблемы не сохранён». Сравнения тогда нет, и система не выдаёт текущий итог за прошлый.
- `EXTERNAL_MISSING`: «Наш итог» берётся из `ourSide` (при обнаружении). Если `currentResult` отличается,
  он показывается ниже как «Итог сейчас».

**«Сверки»** (`requests/card/ReconciliationHistory.tsx`):

- В раскрытой строке те же две колонки: «У перевозчика» и «У нас» на момент проверки, отличия отмечены словом.
  Общая таблица сравнения выносится из `ConflictView` в один компонент (`problems/details/ResultComparison.tsx`)
  и используется в обоих местах.
- В заголовке строки `CONFLICT` под подробностями показывается список отличий: «Отличается: номер отправления,
  стоимость». Так расхождение видно без раскрытия.

## 3. Тесты

### 3.3 e2e

- `e2e/` (`*E2ETest`): расхождение при сверке (итог у перевозчика меняется через его базу, как в `make seed`) →
  `APPLY_CARRIER` → в карточке у проблемы `ourSide` ≠ `currentResult`, в строке сверки `localResult` ≠
  `carrierResult`.
- `web/e2e/problems/`: тот же сценарий в интерфейсе — после решения видны различающиеся колонки и исход.

## 5. Вне объёма

- Общая лента изменений заявки (кто и когда менял итог, комментарий, ответственного). Расхождение и решение
  по нему хранятся у проблемы, этого здесь достаточно.
- Восстановление снимков для старых `RESULT_CONFLICT`/`EXTERNAL_MISSING`: данных нет (§2.2).

## 6. Отличия реализации

- `RECONCILIATION_CONFLICT` берёт снимок не из `delivery_request`, а из `local_*` своей строки сверки (и при
  открытии, и при перестановке). Под блокировкой операции это одно и то же, но так обе стороны проблемы
  гарантированно из одной строки. `RESULT_CONFLICT` и `EXTERNAL_MISSING` берут снимок из `delivery_request`
  в том же `INSERT`.
- Добавлено ограничение `reconciliation_local_key_matches`: `local_result` и `local_status` заполнены вместе.
- Наш итог как значение — `exchange.ResultSnapshot`. Ключ `local_result` строится из него
  (`ReconciliationRules.localContent` удалён).
- Ограничения `local_*` проверяются в `ReconciliationSchemaTests`, а не в `SchemaMigrationTests`: там уже есть
  помощник строки сверки. Заполнение старых строк проверяет `ConflictSidesMigrationTests` на отдельной схеме,
  собранной до V11.
- «Итог сейчас» показывается у закрытой проблемы, а у открытой — только если итоговый результат заявки уже не
  совпадает со снимком. Строку исхода даёт существующая `ResolvedLine` («Закрыта · … · Принята версия перевозчика»).
- В «Сверках» у `CONFLICT` без итога у перевозчика вместо списка полей написано «Итог есть только у нас». Колонка
  перевозчика у `ERROR` говорит «Нет ответа», отметок «отличается» нет.
- Ручные проверки обновлены в `docs/manual-testing.md` (туда перенесён §8 `demo-seed.md`). Спека `demo-seed.md` не
  менялась.
- e2e: строка подключения к базе эмулятора передаётся из `make e2e` (`CARRIER_DB_URL` из `DB_PORT` и
  `CARRIER_DB_NAME` в `.env`).
