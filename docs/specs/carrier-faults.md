# Спека: режимы сбоев carrier-emulator

Статус: на согласовании (14.11.2026). Основание: ТЗ D07, D04, D-NF01, D-NF02; итог проектного опроса Q1–Q18.
Общий дизайн эмулятора — `docs/carrier-emulator-design.md`; эта спека заменяет его §6–7 в части сбоев.

## 1. Зачем

Эмулятор должен воспроизводимо изображать четыре сбоя внешнего перевозчика (D07): недоступность, потерю ответа после исполнения, дубликат результата и задержанный результат. По ним проверяется, что `dispatch` не теряет задания, не исполняет одну операцию дважды и не откатывает состояние устаревшими сообщениями. Фактическое исполнение проверяется отдельно от `dispatch` — через служебный API эмулятора (`executionCount`).

## 2. Общие правила

- Четыре независимых выключателя: `unavailable`, `loseResponse`, `duplicate`, `delayed`. Можно включать в любых сочетаниях.
- Выключатели живут **в памяти** эмулятора. После перезапуска эмулятора все выключены. В БД они не хранятся.
- Режимы **глобальные**: действуют на весь трафик. Адресных маркеров (по адресу, весу и т. п.) нет.
- `PUT /admin/faults` принимает объект целиком (все четыре поля обязательны) и возвращает состояние после изменения.
- Каждое изменение пишется в лог на уровне `WARN`: какие режимы были и какие стали.
- Каждое применение сбоя тоже пишется в лог (`WARN`, с `operationId`): «ответ задержан», «итог отложен до T», «запись опубликована дважды», «отказ 503» (без тела запроса). По логам эмулятора должно быть видно, что с операцией произошло (NF10).
- Служебные эндпоинты (`/admin/**`) и actuator работают при любых режимах.
- В обычном режиме и в нагрузочном прогоне NF08 все выключатели выключены, искусственных задержек нет.

### Когда режим применяется

| Режим | Момент применения |
|---|---|
| `unavailable` | в момент каждого рабочего запроса |
| `loseResponse` | в момент **первого** `POST /operations` для операции; повторы отвечают сразу |
| `duplicate` | **запоминается в операции при первом приёме** |
| `delayed` | **запоминается в операции при первом приёме** |

`duplicate` и `delayed` фиксируются в строке операции при её создании. Операция, принятая при включённом режиме, отработает со сбоем, даже если режим выключили раньше, чем её взял исполнитель. Повторный приём той же операции запомненные сбои не меняет. Так сценарий «включить → создать заявку → выключить» воспроизводим и не зависит от таймингов.

## 3. Режимы

### 3.1 `unavailable` — недоступность

- `POST /operations`, `GET /operations/{operationId}` и `GET /results` отвечают `503` с телом `{"code": "UNAVAILABLE", "message": "Carrier is temporarily unavailable"}`.
- Ответ отдаётся до чтения и проверки тела: операция не сохраняется, `receivedCount` не растёт.
- Исполнитель внутри эмулятора продолжает работать: недоступен API перевозчика, а не сам перевозчик. Уже принятые операции исполняются, их результаты попадают в ленту. `dispatch` получит их, когда режим выключат.
- Если одновременно включён `loseResponse`, побеждает `unavailable`.

### 3.2 `loseResponse` — потеря ответа после исполнения

Действует только на `POST /operations` и только на **первый приём** операции (новый `operationId` с корректным телом). Повтор с тем же `operationId`, `409` и `400` отвечают сразу, без задержки.

1. Операция сохраняется как обычно, транзакция **коммитится**.
2. Приём **ждёт, пока операция станет `EXECUTED`** (её исполняет обычный фоновый исполнитель, раз в ~1 с; приём проверяет состояние с коротким интервалом).
3. Ответ держится до истечения `lose-response-delay` (по умолчанию 10 с), считая от начала приёма. Пауза идёт **вне транзакции**, соединение с БД не удерживается.
4. После паузы отдаётся обычный `202`, который клиент к этому времени уже не ждёт.

Так ответ гарантированно теряется **после исполнения** (D07, D-NF02), а не просто после приёма. Если операция не исполнилась за время паузы (исполнитель выключен), ответ всё равно отдаётся по истечении паузы, и в лог пишется предупреждение.

Ожидаемый ход на стороне `dispatch`: обрыв по таймауту → доставка `UNKNOWN` → повтор с тем же `operationId` → сразу `202` → `ACKNOWLEDGED`. В эмуляторе одна операция, `receivedCount = 2`, `state = EXECUTED`. Выключать режим вовремя не нужно: сценарий «включить → создать заявку» детерминирован.

- Ожидание и пауза идут через внедряемый `Sleeper`, чтобы интеграционные тесты не ждали по-настоящему.
- Задержка должна быть больше таймаута ответа клиента. Эмулятор таймаут `dispatch` не знает и не проверяет (системы связаны только контрактом). Это требование записано в контракте, а в compose стоит комментарий: 10 с у эмулятора больше 5 с у `dispatch`.

### 3.3 `duplicate` — дубликат результата

- Для операции с запомненным `duplicate` каждая запись ленты (`IN_PROGRESS` и итог) пишется **двумя строками** `feed_entry` с одинаковым `messageId` и всем содержимым. Строки идут с соседними `feedSeq`, в той же транзакции.
- Работает и вместе с `delayed`: отложенная публикация тоже дублируется.
- Ожидаемая реакция `dispatch`: один эффект, второе сообщение учтено как дубль (по уникальному `messageId` в `inbox`).
- Копия намеренно идёт с тем же `messageId`: это повторная доставка того же сообщения. Случай «тот же результат под новым `messageId`» отсеивается в `dispatch` по `sequence` (`STALE`). Он покрыт интеграционным тестом `ResultInboxTests.sameSequenceWithSameContentUnderANewMessageIdIsStale`, отдельный режим для него не нужен.

### 3.4 `delayed` — задержанный результат

- Операция исполняется как обычно и сразу: `ACCEPTED → EXECUTED`, `executionCount = 1`, итог сохраняется в строке операции.
- **Публикация в ленту откладывается**: `result_publish_at = executed_at + delayed-result-delay` (по умолчанию 60 с, на Docker-стенде 15 с).
- Когда срок наступил, исполнитель публикует сначала **итог** (`sequence = 2`), затем `IN_PROGRESS` (`sequence = 1`), в одной транзакции, и обнуляет `result_publish_at`. `IN_PROGRESS` приходит после итога и должен быть отмечен в `dispatch` как `STALE`, не откатив состояние.
- Записи вставляются в момент публикации и получают новые, большие `feedSeq`. Курсор `dispatch` их не пропускает, единственный писатель ленты сохраняется.
- Срок хранится в БД, поэтому отложенная публикация переживает перезапуск эмулятора.
- `occurredAt` в записях — время исполнения, а не публикации.
- Во время задержки `GET /operations/{operationId}` **уже показывает итог** (`state = EXECUTED`, `result` заполнен). Расхождение «у перевозчика итог есть, в ленте нет» — материал для будущей сверки (`EXTERNAL_AHEAD`).

### 3.5 Идентификаторы сообщений

Чтобы итог в `GET /operations` и в ленте был одним и тем же сообщением, `messageId` обеих записей (`IN_PROGRESS` и итога) генерируются **при исполнении** и хранятся в строке операции. Публикация (сразу или отложенная) использует их. `result` в `GET /operations/{id}` и `GET /admin/operations` для исполненной операции строится из строки операции: тот же `messageId`, `sequence = 2`. Поэтому результат, применённый сверкой, и та же запись из ленты в `dispatch` дедуплицируются.

## 4. Данные (миграция эмулятора `V2__fault_modes.sql`)

Колонки `operation`:

| Колонка | Тип | Смысл |
|---|---|---|
| `fault_duplicate` | `boolean NOT NULL` | запомненный `duplicate` |
| `fault_delayed` | `boolean NOT NULL` | запомненный `delayed` |
| `in_progress_message_id` | `uuid` | `messageId` записи `IN_PROGRESS`, задаётся при исполнении |
| `result_message_id` | `uuid` | `messageId` итога, задаётся при исполнении |
| `result_publish_at` | `timestamptz` | когда опубликовать отложенный итог; `NULL` — публиковать нечего |

- Новые `NOT NULL` колонки добавляются по правилу: nullable → заполнение (`false`; `messageId` исполненных операций — из `feed_entry`) → `SET NOT NULL`.
- Ограничения с именами:
  - `operation_executed_has_message_ids` — у `EXECUTED` оба `messageId` заданы;
  - `operation_publish_at_only_delayed` — `result_publish_at` задан только при `fault_delayed` и `state = EXECUTED`.
- **Колонка `execution_count` удаляется** вместе с ограничениями, которые на неё ссылаются: `operation_execution_at_most_once`, а `operation_accepted_not_executed` и `operation_executed_has_result` пересоздаются без неё. Она всегда равна «1, если `EXECUTED`, иначе 0» и ничего не добавляет к `state`. «Не более одного исполнения» гарантируют первичный ключ `operation_id` и условный переход `ACCEPTED → EXECUTED`.
- Поле `executionCount` в API остаётся (формулировка D07 «число исполнений») и **вычисляется** из `state`.
- Индекс очереди публикации: `operation (result_publish_at) WHERE result_publish_at IS NOT NULL`.

## 5. Настройки

| Свойство | По умолчанию | env в compose | Значение на Docker-стенде |
|---|---|---|---|
| `carrier.faults.lose-response-delay` | `10s` | `CARRIER_LOSE_RESPONSE_DELAY` | `10s` |
| `carrier.faults.delayed-result-delay` | `60s` | `CARRIER_DELAYED_RESULT_DELAY` | `15s` |

Тело `PUT /admin/faults` задержек не принимает.

## 6. Контракт (`contracts/carrier-api.yaml`)

- `GET/PUT /admin/faults` и схема `Faults` остаются как есть. Описание `PUT` дополняется:
  - задержки настраиваются конфигурацией;
  - `loseResponse` действует только на первый приём операции и отвечает после её исполнения; задержка больше таймаута ответа клиента;
  - `duplicate`/`delayed` запоминаются в операции при приёме.
- Описание `executionCount`: вычисляется из состояния (0 или 1).
- `AdminOperation` получает обязательные поля:
  - `faults` — массив из `DUPLICATE`, `DELAYED` (пустой, если сбоев нет);
  - `resultPublishAt` — `date-time` или `null`.
- Описание `OperationState.result`: для `delayed` итог виден здесь раньше, чем в ленте.
- `503 Unavailable` уже описан у всех трёх рабочих эндпоинтов.
- После изменения — `make contracts-lint`.

## 7. Служебные команды

| Команда | Действие |
|---|---|
| `make faults` | показать текущие режимы |
| `make fault-unavailable` | включить только `unavailable` |
| `make fault-lose-response` | включить только `loseResponse` |
| `make fault-duplicate` | включить только `duplicate` |
| `make fault-delayed` | включить только `delayed` |
| `make fault-off` | выключить все |
| `make carrier-ops` | операции со счётчиками, `faults`, `resultPublishAt` |

Каждая команда `fault-*` выключает остальные режимы. Сочетания задаются через `curl -X PUT …/admin/faults`.

## 8. Ожидаемое поведение `dispatch` (то, что проверяет e2e)

| Режим | Что видно в `dispatch` | Что видно в эмуляторе |
|---|---|---|
| `unavailable` | доставка `RETRY_WAIT`, растущие паузы; после выключения — `ACKNOWLEDGED` и итог | операция появляется только после выключения, одна, `EXECUTED` |
| `loseResponse` | попытка с исходом `UNKNOWN`, повтор с тем же `operationId`, затем итог | одна операция, `receivedCount = 2`, `EXECUTED` |
| `duplicate` | итог применён один раз, дубль учтён в `inbox` без эффекта | в ленте по две записи с одним `messageId` |
| `delayed` | доставка `ACKNOWLEDGED`, итог появляется только через задержку; поздний `IN_PROGRESS` — `STALE`, итог не откатан | `faults = [DELAYED]`, `resultPublishAt` до публикации, затем `null` |

**Критерий «исполнено не более одного раза»** в e2e проверяется не по `executionCount` (он не может быть больше 1 по устройству), а так:
- в эмуляторе по заявке **ровно одна операция**: она находится по `operationId` из карточки `dispatch`, а общее число операций эмулятора выросло ровно на 1;
- `receivedCount` показывает, что повтор действительно был;
- `state = EXECUTED`.

Так ловится настоящая ошибка: `dispatch` при повторе прислал новый `operationId`.

Сценарии сверки и проблем (`DELIVERY_UNKNOWN`, `EXTERNAL_AHEAD`) добавляются вместе со сверкой, в эту спеку не входят.

## 9. Тесты

**Модульные:** состояние выключателей и их снимок для новой операции.

**Интеграционные** (`@IntegrationTest`, каждый ответ сверяется с контрактом через `Contract.matchesContract()`):
- `GET/PUT /admin/faults`: чтение, изменение, `400` на неполное тело;
- `unavailable`: `503` на трёх рабочих эндпоинтах, операция не сохранена; админка отвечает; исполнитель продолжает исполнять принятые;
- `loseResponse`: операция сохранена и закоммичена до паузы; ответ отдаётся только после `EXECUTED` и истечения задержки (`Sleeper` под контролем теста); повтор того же `operationId` отвечает сразу, без паузы, `receivedCount = 2`, повторного исполнения нет; `409`/`400` без паузы;
- `executionCount` в ответах вычисляется из `state` (0 для `ACCEPTED`, 1 для `EXECUTED`);
- `duplicate`: две записи с одним `messageId` и соседними `feedSeq` для `IN_PROGRESS` и итога; режим, выключенный после приёма, всё равно действует;
- `delayed`: до срока лента пуста, `GET /operations` показывает итог; после срока (сдвиг `MutableClock`) итог идёт раньше `IN_PROGRESS`; `resultPublishAt` обнуляется; `messageId` в `GET /operations` и ленте совпадают;
- `delayed` + `duplicate`: отложенная публикация дублируется;
- миграция: новые ограничения отклоняют неверные данные.

**E2E** (живой стенд; все тесты выключают режимы перед и после каждого теста; JUnit e2e идёт последовательно):
- `CarrierFaultsE2ETest` — эмулятор напрямую: каждый режим через `PUT /admin/faults` и его наблюдаемый эффект;
- `ExchangeFaultsE2ETest` — сквозной путь через `dispatch` по таблице §8; ожидание итога до ~60 с.

## 10. Вне объёма

- Адресные маркеры сбоев и счётчики «следующие K операций».
- Хранение выключателей в БД.
- Задержки в теле `PUT /admin/faults`.
- Сверка, проблемы и действия оператора (следующий шаг).
- Способ получить на живом стенде некорректную запись ленты и конфликты результатов, сценарий `EXTERNAL_AHEAD` и демо-данные через режимы сбоев — записаны в `docs/PLAN.md`, этап 2.
- `make restart-check` — отдельный коммит того же шага, описывается в README.

## 11. Ручная проверка (демо)

```bash
make fault-lose-response   # создать заявку в UI → в карточке попытка UNKNOWN, затем повтор и итог
make carrier-ops           # одна операция, receivedCount = 2, state = EXECUTED
make fault-duplicate       # создать заявку → итог один, в ленте две записи
make fault-delayed         # создать заявку → итог через ~15 с, поздний IN_PROGRESS отсеян
make fault-unavailable     # создать заявку → RETRY_WAIT; затем make fault-off → итог
make fault-off
```
