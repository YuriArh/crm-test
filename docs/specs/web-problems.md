## 1. Зачем

Сейчас оператор видит в карточке только статус доставки «Неизвестно, получена ли» или «Ошибка отправки» и
последнюю ошибку, а сделать ничего не может. Плохие записи ленты и конфликтующие итоги видны только через
`make inbox`. Сервер уже превращает такие ситуации в **проблемы** с причиной, автором и решением и даёт действия.
Экраны должны:

- показать оператору, что требует внимания: список проблем службы, счётчик в шапке, фильтр и значок в реестре;
- в карточке заявки — её проблемы, доступные действия и их исход (D06 «увидеть исход»);
- провести решение так, чтобы его нельзя было принять случайно или дважды (NF04) и чтобы любая ошибка сервера была
  понятна (NF06).

Инициатор ничего нового не видит: сервер не отдаёт ему `problems`, `actions`, `reconciliations`, `openProblems`
(NF02).

| Видеть проблемы заявки, открытые и закрытые | карточка | оператор (`card.problems`) |
| «Повторить отправку» | карточка | `card.actions` содержит `RETRY` |
| «Принять версию перевозчика» | карточка, панель | `problem.actions` содержит `APPLY_CARRIER` |

## 3. Доработка `dispatch` (часть A)

### 3.1 `GET /api/problems/{id}`

Одна проблема — `ExchangeProblem`, те же поля, что в списке (`ProblemQueryDao`: та же выборка с условием по `id`).

- Только оператор; инициатору — `403 FORBIDDEN` (как у списка).
- Область — как у списка: проблемы заявок службы оператора и проблемы без заявки. Проблема другой службы,
  несуществующий или некорректный id — `404 NOT_FOUND` (существование чужого не раскрывается, NF02).
- Транзакция только для чтения.

### 3.2 Реестр: фильтр и число открытых проблем

`GET /api/requests` получает параметр `hasOpenProblems`, разбираемый как `overdue`: `true` — только заявки с
открытой проблемой, `false` — только без открытых, без параметра — все, иное значение — `400 VALIDATION_FAILED`.
В `RequestQueryDao.where()` — `AND [NOT] EXISTS (SELECT 1 FROM problem p WHERE p.request_id = r.id AND
p.status = 'OPEN')`. Интерфейс шлёт только `true`.

- Только оператор. Инициатору с этим параметром — `403 FORBIDDEN`: иначе по выборке он узнал бы, у каких его заявок
  есть проблемы, а проблемы ему не показываются (NF02, (a) решение Q14).
- `RequestListItem` получает поле `openProblems` (`integer`, `null` у инициатора): число открытых проблем заявки,
  подзапросом в выборке страницы. Оператору — всегда число (0, если проблем нет).
- Новой миграции нет: `EXISTS` и подсчёт идут по `problem_request_idx (request_id)`, страница — 20 строк. Если
  нагрузочный прогон (п. 8 плана) покажет медленную выборку, индекс добавится тогда.

### 3.3 Контракт и документы

`contracts/dispatch-api.yaml`: путь `/api/problems/{id}` (`get`, `200`/`401`/`403`/`404`); параметр
`hasOpenProblems` и ответ `403` у `GET /api/requests`; поле `openProblems` в `RequestListItem`. Затем
`make contracts-lint`, `make web-api-types`. `docs/dispatch-design.md` §9 (реестр) — фильтр и поле.

## 4. Слова

### 4.1 Виды проблем

| `kind` | Название | Пояснение под названием | Цвет плашки |
|---|---|---|---|
| `DELIVERY_UNKNOWN` | Неизвестно, получена ли заявка | Ответ перевозчика потерян. Повтор идёт сам; закроется, когда перевозчик подтвердит получение | `orange` |
| `DELIVERY_FAILED` | Отправка не удалась | Попытки кончились или перевозчик отказал в приёме | `orange` |
| `INVALID_MESSAGE` | Некорректное сообщение перевозчика | Запись ленты нарушает контракт и не применена | `yellow` |
| `MESSAGE_FAILED` | Сообщение не обработано | У нас не получилось обработать запись ленты | `yellow` |
| `RESULT_CONFLICT` | Расхождение итогов | Перевозчик прислал итог, отличный от применённого | `red` |
| `EXTERNAL_MISSING` (B) | Перевозчик не знает операцию | Он подтверждал приём, а теперь операции у него нет | `orange` |
| `RECONCILIATION_CONFLICT` (B) | Расхождение при сверке | Итог перевозчика отличается от нашего | `red` |

Неизвестный клиенту `kind` (сервер новее клиента) показывается кодом как есть, цвет `gray`, кнопки — только
присланные сервером; экран не падает.

### 4.2 Решения и статус

| `decision` | В закрытой проблеме |
|---|---|
| `SYSTEM` | Закрыта системой |
| `RETRIED` | Отправка повторена |
| `APPLY_CARRIER` | Принята версия перевозчика |
| `KEEP_OURS` | Оставлен наш итог |
| `ACKNOWLEDGED` | Разобрано |

Статус — бейдж словом и цветом: «Открыта» (`orange`), «Закрыта» (`gray`). Строка закрытой проблемы: «Закрыта
17.11, 14:05 · Иванов · Оставлен наш итог» и комментарий оператора. Время — в бизнес-зоне (NF07).

## 5. Список проблем `/problems`

Отдельный экран, только оператор: `beforeLoad` — `requireRole(me, 'OPERATOR')`, как у формы создания; инициатор
по прямой ссылке получает страницу «Не найдено» — так же сервер отвечает на то, что вне области (NF02).

### 5.1 Данные и адрес

`GET /api/problems?status=&kind=&page=&size=20`. Состояние — в адресе, по правилам реестра (`search.ts` реестра —
образец: мусор отбрасывается, значения по умолчанию не пишутся, смена фильтра сбрасывает страницу, страница за
последней заменяется последней):

| Параметр | Значения | По умолчанию | В API |
|---|---|---|---|
| `status` | `open`, `resolved`, `all` | `open` | `OPEN` / `RESOLVED` / `ALL` |
| `kind` | значения `ProblemKind`, можно несколько | все | `kind=…&kind=…` |
| `page` | с 1 | 1 | `page − 1` |

Ключ кэша `['problems', 'list', параметры]`, `keepPreviousData`, обновление раз в 10 с при видимой вкладке — как
реестр.

### 5.2 Вид

Десктоп (≥ `md`): таблица. Колонки: «Вид» (название + бейдж статуса), «Заявка» (номер — ссылка в карточку; «—»
у проблемы без заявки), «Причина» (`details`, одна строка с многоточием), «Открыта» (бизнес-зона), «Решение» (для
закрытых: решение и автор). Строка открывает панель проблемы (§5.3) с сохранением параметров списка; ссылка на
заявку ведёт в карточку.

Над таблицей: заголовок «Проблемы» и число, переключатель статуса (`SegmentedControl`: Открытые / Закрытые / Все),
`MultiSelect` вида с русскими названиями, «Сбросить».

Телефон (< `md`): карточки по одной на проблему с теми же полями; фильтры статуса и вида — в нижней шторке, как в
реестре.

### 5.3 Панель проблемы `/problems/$id`

Вложенный маршрут под `/problems`: список остаётся под панелью со своими параметрами адреса, панель — `Drawer`
справа на десктопе, во весь экран на телефоне. «Назад» и «Закрыть» возвращают на `/problems` с теми же параметрами.

- Данные — `GET /api/problems/{id}` (§3.1), ключ `['problems', 'one', id]`; ссылка работает, даже если проблемы нет
  на текущей странице или в текущем фильтре. Обновление раз в 5 с при видимой вкладке, пока панель открыта и
  проблема открыта.
- Содержимое — общий компонент `ProblemDetails` (§7.1), тот же, что в карточке: вид, пояснение, статус, причина,
  заявка (ссылка) и `operationId` (копируется), сообщение перевозчика или блок конфликта, решение закрытой, кнопки
  решений.
- После успешного решения панель **остаётся открытой** и показывает закрытую проблему (кто, решение, комментарий),
  кнопок решений больше нет; список под ней обновляется (при фильтре «Открытые» строка уходит). Закрывает панель сам
  оператор.

| Состояние панели | Что видно |
|---|---|
| загрузка | скелет содержимого |
| `404` или `403` | «Проблема не найдена или недоступна» и «Закрыть»; список под панелью остаётся |
| нет связи / `5xx` | «Не удалось загрузить проблему» и «Повторить» |

### 5.4 Состояния списка

| Состояние | Что видно |
|---|---|
| загрузка первой страницы | скелет таблицы |
| нет проблем, фильтр по умолчанию | «Открытых проблем нет. Обмен идёт без вмешательства» |
| нет проблем под фильтром | «Ничего не найдено» и «Сбросить фильтры» |
| нет связи / `5xx` | «Не удалось загрузить проблемы. Проверьте связь» и «Повторить»; старые строки остаются, если были |
| `400` (адрес с мусором, который пропустил разбор) | адрес сбрасывается к умолчанию |
| `403` (роль сменилась) | страница «Не найдено», как у `requireRole` |

## 6. Шапка и реестр

### 6.1 Шапка

У оператора в шапке навигация: «Заявки» и «Проблемы» с бейджем числа открытых проблем
(`GET /api/problems?status=OPEN&size=1` → `totalElements`, ключ `['problems', 'openCount']`, обновление раз в 30 с
при видимой вкладке). Число — все открытые проблемы службы, включая проблемы без заявки, то есть совпадает с числом
в «Открытых» на `/problems`; сумма значков в реестре может быть меньше. 0 — бейджа нет. Ошибка запроса счётчика —
бейджа нет, без сообщений (это подсказка, а не данные экрана). Активный раздел выделен.

Ниже `xs` (телефон) навигация — две иконки-ссылки (`ActionIcon` с `aria-label` «Заявки» и «Проблемы»), бейдж —
на иконке проблем. У инициатора навигации нет (единственный экран — реестр).

### 6.2 Реестр

- Переключатель «Есть открытые проблемы» рядом с «Только просроченные», только у оператора. Параметр адреса
  `problems=1` → `hasOpenProblems=true`. У инициатора `problems` отбрасывается при разборе адреса, как `delivery`.
  «Сбросить» сбрасывает и его. В нижней шторке на телефоне — там же, где остальные фильтры.
- Значок открытых проблем: при `openProblems > 0` рядом со статусом доставки — иконка и число (цвет `orange`),
  `aria-label` «Открытых проблем: 2»; и в таблице, и в карточках на телефоне. При `0` и `null` значка нет.
- Пустое состояние под этим фильтром — «Заявок с открытыми проблемами нет».

## 7. Карточка заявки (оператор)

### 7.1 Блок «Проблемы»

Наверху основной колонки, над разделом «Содержимое» (на телефоне — сразу под шапкой карточки), если
`card.problems` не пуст:

- **открытые** — каждая отдельной плашкой (`Alert`, цвет по виду, §4.1) с `ProblemDetails` и кнопками решений;
- **закрытые** — свёрнуты под «Закрытые проблемы (3)» (`Accordion`), каждая одной строкой §4.2 с раскрытием деталей.

Если `problems` пуст — блока нет.

`ProblemDetails` по видам:

| Вид | Что показано, кроме названия, причины и времени |
|---|---|
| `DELIVERY_*` | ничего сверх; в плашке — кнопка «Повторить отправку», если в `card.actions` есть `RETRY` (в панели списка — ссылка на карточку заявки, где кнопка есть) |
| `INVALID_MESSAGE`, `MESSAGE_FAILED` | «Сообщение перевозчика»: разобранные поля `message` (что пусто — не показано), `messageId`, номер в ленте, начало исходного текста моноширинно в прокручиваемом блоке с кнопкой «Копировать» |
| `RESULT_CONFLICT`, `RECONCILIATION_CONFLICT` (B) | **блок конфликта**: две колонки «Версия перевозчика» (`message`: статус, номер отправления, стоимость, причина отказа, время) и «Наш итог» (`currentResult`); различающиеся поля выделены словом и цветом; на телефоне колонки одна под другой. У `RECONCILIATION_CONFLICT` без итога у перевозчика левая колонка — «У перевозчика итога ещё нет» |
| `EXTERNAL_MISSING` (B) | «Наш итог» из `currentResult` или «Итога нет» |

### 7.2 Действия в карточке

Кнопки действий по заявке (`card.actions`) стоят в панели «Обмен с перевозчиком» и повторяются в плашке
соответствующей проблемы доставки: «Повторить отправку», (B) «Сверить сейчас». Кнопки решений (`problem.actions`) —
в плашке проблемы.

### 7.3 Обновление

Сейчас карточка перестаёт опрашиваться, когда итог и доставка финальны. Правило меняется: у оператора карточка
опрашивается раз в 5 с и тогда, когда **есть открытая проблема** — иначе после «Повторить» по `FAILED` (доставка
«финальна») оператор не увидит исход, а закрытие `DELIVERY_UNKNOWN` системой останется незамеченным. Финальная
карточка без открытых проблем по-прежнему не опрашивается (обновится при возврате на вкладку и при заходе).

## 8. Как проходят действия

### 8.1 «Повторить отправку»

1. Кнопка открывает окно подтверждения «Повторить отправку заявки DR-000123?» с текстом по статусу доставки:
   - `FAILED`: «Начнётся новая серия попыток. Перевозчик получит ту же операцию и не исполнит её дважды»;
   - `UNKNOWN`: «Отправим сейчас, не дожидаясь паузы. Проблема „неизвестно, получена ли“ останется открытой, пока
     перевозчик не подтвердит получение»;
   - (B) `ACKNOWLEDGED` с `EXTERNAL_MISSING`: «Перевозчик потерял операцию. Отправим её заново с тем же
     идентификатором».
2. «Повторить» шлёт `POST /api/requests/{id}/retry` с `Idempotency-Key` (§8.4). Кнопка в состоянии загрузки, окно не
   закрывается до ответа.
3. `200` — ответ (карточка) кладётся в кэш вместо текущей, как у `PATCH`; списки заявок и проблем и счётчик
   помечаются устаревшими; окно закрывается, уведомление «Отправка повторена». Исход оператор видит в карточке:
   статус доставки, число попыток, плашки проблем меняются по опросу (§7.3).

### 8.2 Решение по проблеме

1. Кнопка решения открывает окно: заголовок по решению («Принять версию перевозчика», «Оставить наш итог»,
   «Разобрано»), для конфликта — блок конфликта ещё раз, и что именно изменится:
   - `APPLY_CARRIER`: «Итог заявки будет заменён версией перевозчика. Инициатор увидит новый итог»;
   - `KEEP_OURS`: «Итог заявки не изменится»;
   - `ACKNOWLEDGED`: «Проблема закроется, заявка не изменится».
2. Поле «Комментарий» обязательно (подпись, счётчик до 2000; проверка в форме своим текстом: «Опишите основание
   решения» для пустого и из одних пробелов, «Не больше 2000 символов»). `@mantine/form`.
3. `POST /api/problems/{id}/resolve` с `{decision, comment}` и `Idempotency-Key` (§8.4).
4. `200` — окно закрывается, уведомление «Решение сохранено»; ответ кладётся в кэш проблемы
   (`['problems', 'one', id]`); помечаются устаревшими: карточка заявки проблемы, списки проблем, счётчик, списки
   заявок (`APPLY_CARRIER` меняет итог, решение меняет `openProblems`).
5. `APPLY_CARRIER` поднимает `version` заявки. Если в карточке в это время есть несохранённая правка комментария или
   ответственного, она уйдёт со старой версией и получит `409 VERSION_CONFLICT`, который уже разбирает `conflict.ts`
   (другое поле — тихая переотправка). Отдельной обработки не нужно; тест это фиксирует.

### 8.3 (B) «Сверить сейчас»

Без окна подтверждения: действие ничего не меняет у перевозчика. `POST /api/requests/{id}/reconcile`, ответ —
`Reconciliation` (`200` и при `ERROR`). Под кнопкой — итог проверки: исход словом и цветом, `details`, время;
карточка перезапрашивается (сверка могла подтвердить доставку, применить итог, открыть или закрыть проблему).
Повторное нажатие — **новый** ключ (прежний вернул бы сохранённый ответ, а не новый вопрос перевозчику).

| `outcome` | Слова | Цвет |
|---|---|---|
| `MATCH` | Совпадает | `green` |
| `EXTERNAL_AHEAD` | Итог получен сверкой | `accent` |
| `EXTERNAL_MISSING` | Перевозчик не знает операцию | `orange` |
| `CONFLICT` | Расхождение | `red` |
| `ERROR` | Не удалось сверить | `yellow` |

Флаг `acknowledged` добавляет «· получение подтверждено».

**История сверок** — раздел «Сверки» в панели обмена: последние проверки (`card.reconciliations`, до 20): время,
запуск («при старте», «по расписанию», «вручную · Иванов»), исход; раскрытие — `details` и итог перевозчика.

### 8.4 `Idempotency-Key` действий (NF04)

Обобщение подхода формы создания (`create/idempotency.ts`): ключ принадлежит **одному намерению** и живёт, пока
исход намерения неизвестен.

- Ключ создаётся при первой отправке намерения и переиспользуется при повторе после неизвестного исхода (нет связи,
  `5xx`): сервер вернёт сохранённый ответ (`Idempotent-Replayed: true`), второго эффекта не будет.
- Намерение решения — `(problemId, decision, comment)`: изменили комментарий или решение — новый ключ. Намерение
  повтора — открытое окно подтверждения; новое окно — новый ключ.
- После определённого ответа (`2xx`, любой `4xx`) ключ забывается.
- `422 IDEMPOTENCY_KEY_REUSED` — ключ заменяется новым, сообщение «Повторите действие».
- «Сверить сейчас» (B) — новый ключ на каждое нажатие (§8.3), повтор после обрыва — тот же.

Реализация — общий помощник `src/shared/actions/idempotency.ts` (ключи по отпечатку намерения: `keyFor`, `forget`,
`renew`); форма создания переходит на него без изменения поведения (её тесты остаются зелёными).

### 8.5 Ошибки действий

Ошибка показывается **в открытом окне** над кнопками (`Alert`), окно не закрывается, введённый комментарий
сохраняется. Для «Сверить сейчас» — под кнопкой.

| Ответ | Повторить отправку | Решение по проблеме | Сверить сейчас (B) |
|---|---|---|---|
| нет связи, `5xx` | «Не удалось связаться с сервером. Повторите — повтор безопасен» (тот же ключ) | то же | то же |
| `409 INVALID_STATE` | «Повтор уже не нужен: состояние доставки изменилось». Карточка перезапрашивается, окно закрывается кнопкой «Понятно» | «Решение уже недоступно: проблему закрыли или её состояние изменилось». Проблема, карточка и список перезапрашиваются; окно закрывается кнопкой «Понятно», за ним видно, кем и как закрыта проблема | — (у сверки нет недопустимого состояния) |
| `400 VALIDATION_FAILED` | — | ошибка под полем «Комментарий» своим текстом (§8.2) | — |
| `400 IDEMPOTENCY_KEY_*` | «Не удалось выполнить действие. Обновите страницу» (ошибка клиента, в консоль) | то же | то же |
| `422 IDEMPOTENCY_KEY_REUSED` | новый ключ, «Повторите действие» | то же | то же |
| `404` | заявка ушла из области: страница «Заявка не найдена» (как у карточки) | «Проблема недоступна»; проблема и списки перезапрашиваются | как у повтора |
| `403` | «Действие доступно только оператору службы заявки» | то же | то же |
| `401` | общий обработчик сессии | то же | то же |

`409` и `404` — не сбой, а устаревший экран; поэтому за сообщением всегда следует перезапрос, и оператор видит
актуальное состояние, а не прежние кнопки.

### 10.4 web — Playwright (`web/e2e/problems/`)

Помощник `e2e/problems/carrier.ts` переключает сбои эмулятора (`PUT {CARRIER_BASE_URL}/admin/faults`, по умолчанию

описанием груза. Если эмулятор недоступен — сценарии со сбоями пропускаются с причиной. Режимы эмулятора глобальны
(пока включён `malformed`, итог любой новой заявки приходит испорченным), поэтому сценарии со сбоями — отдельный
проект Playwright `faults`, который идёт после остальных и последовательно.

| Сценарий | Ожидание |
|---|---|
| некорректное сообщение разбирается из списка | `malformed`, заявка под инициатором; оператор видит бейдж, открывает `/problems`, панель «Некорректное сообщение перевозчика» с началом текста; «Разобрано» с комментарием — в панели итог, в «Открытых» строки нет, в «Закрытых» — с автором |
| реестр с фильтром | та же заявка видна в реестре с «Есть открытые проблемы» и значком; после решения — нет |
| неизвестный исход в карточке закрывается системой | `loseResponse`; когда эмулятор получил первую отправку — ещё и `unavailable` (иначе повтор подтверждает получение через ~5 с, быстрее опроса карточки, и плашку можно не застать): у оператора плашка «Неизвестно, получена ли заявка»; после выключения сбоев она в «Закрытых» с «Закрыта системой» |
| права | инициатор не видит навигации и переключателя, `/problems` — «Не найдено», в карточке нет блока проблем |
| телефон 390 px | список проблем карточками, панель во весь экран, окно решения помещается, иконки навигации |
| (B) «Сверить сейчас» | обычная заявка с итогом: «Совпадает», проверка в истории сверок |

«Повторить отправку» и решения по конфликтам на стенде не воспроизводятся (как и в (a) §3) — покрыты компонентными
