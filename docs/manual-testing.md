# Ручное тестирование

Проверка основных сценариев ТЗ на живом стенде. Этапы идут по порядку: каждый следующий опирается на то, что
проверено в предыдущем. Внутри этапа — короткие шаги и ожидаемый результат.

| Этап | Что проверяем | ТЗ |
|---|---|---|
| 1 | основной сценарий: заявка доходит до итога | D01, D06, NF01, NF06, NF07 |
| 2 | права доступа | D06, NF02 |
| 3 | история и правки | NF03, NF05 |
| 4 | повторы: ни одна операция не исполняется дважды | D03, D07, NF04 |
| 5 | недоступность перевозчика и действия оператора | D01, D04, D06 |
| 6 | падения и перезапуск `dispatch`, БД, эмулятора | D04, D-NF01, NF03 |
| 7 | некорректное сообщение перевозчика | D04, D-NF03 |
| 8 | сверка и расхождения | D05, D06 |
| 9 | демо-данные `make seed` | NF09 |

Автоматические проверки (NF10) — в конце, раздел 10.

## 0. Подготовка

```bash
cp .env.example .env   # первый раз
make up                # postgres, dispatch, carrier-emulator, web на :3000
make fault-off         # все режимы сбоев выключены
```

Два окна браузера на http://localhost:3000 — обычное и приватное (сессия хранится в cookie, общем для одного
адреса). Пароль у всех `demo1234`:
- обычное окно — `north.initiator` (инициатор службы «Север»), создаёт заявки;
- приватное окно — `north.operator` (оператор «Севера»), видит заявки службы, блок «Обмен с перевозчиком» и
  «Проблемы».

Ещё есть `south.initiator` (инициатор службы «Юг») — для проверки прав.

### Команды

| Команда | Что делает |
|---|---|
| `make fault-unavailable` | перевозчик отвечает `503` |
| `make fault-lose-response` | перевозчик исполняет операцию, но ответ теряется |
| `make fault-duplicate` | перевозчик публикует каждый результат дважды |
| `make fault-delayed` | перевозчик подтверждает приём, а результат публикует через 15 с |
| `make fault-malformed` | итог «Выполнена» в ленте приходит с испорченной ценой |
| `make fault-off`, `make faults` | выключить все режимы, показать текущие |
| `make carrier-ops` | операции у перевозчика: `receivedCount` (сколько раз принята), `executionCount` (сколько раз исполнена) |
| `make inbox` | последние 30 результатов, полученных `dispatch`: статус разбора и причина |
| `make dispatch-kill` / `make dispatch-start` | уронить `dispatch` (SIGKILL) / поднять и дождаться готовности |
| `make db-kill` / `make db-start` | то же для PostgreSQL |
| `make carrier-kill` / `make carrier-start` | то же для эмулятора (режимы сбоев после старта выключены) |

`duplicate` и `delayed` запоминаются в операции при приёме: «включить → создать заявку → выключить» работает
независимо от таймингов.

### Что считается успехом

Если в сценарии не сказано иное:
1. Все созданные заявки на месте.
2. Каждая дошла до итога: «Выполнена» (номер отправления, стоимость) или «Отказ» (причина).
3. В `make carrier-ops` у каждой операции `executionCount = 1`. `receivedCount > 1` нормально: `dispatch`
   повторял отправку с тем же `operationId`.
4. Ничего не зависло в «Отправляется» или «Неизвестно, получена ли».

После каждого сценария — `make fault-off`.

## 1. Основной сценарий

1. Инициатор: «Новая заявка» → заполните груз, вес, адрес, срок → «Создать» → «Проверьте данные» → подтвердите.
2. Откроется карточка: статус «Отправляется», затем «В работе», затем «Выполнена» с номером `TRK-…` и стоимостью
   (несколько секунд, карточка обновляется сама).
3. Оператор открывает ту же заявку: в блоке «Обмен с перевозчиком» — «Попыток отправки: 1», «Получение подтверждено …
   · ответ на отправку». Получение и итог показаны отдельно: подтверждение — ещё не исполнение (D01).
4. Список заявок («Заявки» в шапке, `/requests`): заявка в нём есть; фильтры по результату и просрочке сохраняются в адресе и переживают обновление страницы.
5. Форма: пустые поля и вес вне диапазона — понятная ошибка под полем, запрос не уходит.
6. Ширина 390 px и светлая схема (переключатель в шапке): список заявок — карточками, форма и карточка в одну колонку,
   горизонтальной прокрутки нет (NF06).
7. Сроки и время показаны в бизнес-зоне (`APP_TIMEZONE`, по умолчанию Москва), а не в зоне браузера (NF07).

## 2. Права доступа

1. `south.initiator` не видит заявок «Севера» в списке заявок. Прямой адрес карточки заявки «Севера» — «Заявка не найдена».
2. Инициатор не видит «Проблемы» в шапке, блока «Обмен с перевозчиком» и кнопок оператора; `/problems` — «Страница не
   найдена».
3. Оператор не может создать заявку: кнопки нет, `/requests/new` — «Страница не найдена».
4. Прямой запрос к API (NF02): вход инициатором по `README.md` («Пример с curl»), затем
   `POST /api/requests/{id}/retry` с заголовком `Idempotency-Key` — `403` на свою заявку, `404` на чужую.

## 3. История и правки

1. В карточке инициатор меняет комментарий, оператор назначает ответственного. Обновите страницу — изменения на
   месте.
2. Оба одновременно открыли карточку и правят **одно и то же** поле: второй получает выбор «Оставить моё» / «Взять
   их», чужая правка молча не затирается (NF03).
3. Раздел «История» в карточке: создание, правки «было → стало» с автором и временем, смена итога. Оператор видит ещё
   попытки отправки, записи перевозчика и сверки (фильтр «Все / Действия людей / Обмен»); инициатор — только деловую
   часть (NF05).
4. После `make dispatch-kill` и `make dispatch-start` история та же (сессии пропадают — войдите заново).

## 4. Повторы

### 4.1. Дубликат результата

1. `make fault-duplicate`, создайте заявку, `make fault-off`.

Ожидаемо: заявка «Выполнена» один раз. В «Истории» оператора у записи перевозчика — «Повторов: 1», итог менялся один
раз. `executionCount = 1`.

### 4.2. Потеря ответа

1. `make fault-lose-response`, создайте заявку, `make fault-off`.

Ожидаемо: `dispatch` не получил ответа (таймаут 5 с) и повторил отправку с тем же `operationId`. «Попыток
отправки: 2», `receivedCount = 2`, `executionCount = 1` (D03).

### 4.3. Повторное создание

1. Заполните форму, `make db-kill`, «Создать» → подтвердите — ошибка, в списке заявок её нет.
2. `make db-start`, «Создать» ещё раз с теми же данными.

Ожидаемо: создана ровно одна заявка (форма отправляет тот же `Idempotency-Key`, NF04), она доходит до итога.

## 5. Недоступность перевозчика

### 5.1. Временная недоступность

1. `make fault-unavailable`, создайте 2 заявки.
2. Оператор: «Повтор отправки», «Попыток отправки» растёт, видны «Следующая попытка» (паузы 5, 10, 20, 40 … с) и
   «Последняя ошибка». Проблем нет: это штатный управляемый повтор.
3. Через минуту-две `make fault-off`.

Ожидаемо: заявки уходят в свою «Следующую попытку» и доходят до итога. `receivedCount = 1`: ответ `503` не приём.

### 5.2. Попытки кончились → оператор

1. `make fault-unavailable`, создайте заявку, подождите ~10 минут (8 попыток).
2. Заявка — «Ошибка отправки», у оператора открыта проблема «Отправка не удалась». Бесконечного цикла нет (D04).
3. `make fault-off`. Оператор: «Повторить отправку».

Ожидаемо: заявка уходит заново с тем же `operationId` и доходит до итога; проблема закрыта решением «Отправка
повторена»; `executionCount = 1`.

## 6. Падения и перезапуск

Правило для всех сценариев: когда бы что ни упало и сколько бы ни лежало, после старта каждая заявка доходит до
итога, ни одна не теряется и не исполняется дважды. После `make dispatch-start` войдите заново.

### 6.1. Падение `dispatch` с заявками в очереди

1. Создайте 3 заявки, сразу `make dispatch-kill`.
2. Подождите минуту, `make dispatch-start`.

Ожидаемо: все 3 дошли до итога, `executionCount = 1`.

### 6.2. Падение `dispatch` до чтения результата

1. `make fault-delayed`, создайте заявку. Оператор: «Получение подтверждено», итога нет.
2. В течение 15 с `make dispatch-kill`, подождите 20 с, `make dispatch-start`.

Ожидаемо: итог, опубликованный пока `dispatch` лежал, применён один раз сразу после старта. Запоздавшее «в работе»
итог не откатывает (D03).

### 6.3. Падение БД посреди обмена

1. `make fault-delayed`, создайте 3 заявки, сразу `make db-kill`.
2. Подождите 20 с, `make db-start` (до ~1 мин). Пока базы нет, интерфейс показывает ошибки загрузки — это нормально.

Ожидаемо: заявки на месте, все итоги применены по одному разу (NF03).

### 6.4. Падение эмулятора

1. `make carrier-kill`, создайте 2 заявки. Оператор: «Повтор отправки», «Последняя ошибка» — `ConnectException`.
2. Подождите, `make carrier-start`.

Ожидаемо: заявки дошли до итога, `receivedCount = 1`, `executionCount = 1`.

**Вариант — до публикации результата:** `make fault-delayed`, создайте заявку, в течение 15 с `make carrier-kill`,
через 20 с `make carrier-start`. Отложенная публикация пережила перезапуск эмулятора, итог применён один раз.

## 7. Некорректное сообщение перевозчика

1. `make fault-malformed`, создайте заявку А, дождитесь «В работе», `make fault-off`.
2. Создайте заявку Б.

Ожидаемо:
- Б — «Выполнена»: одна плохая запись не останавливает ленту;
- А остаётся «В работе»; `make inbox` — её итог `INVALID` с причиной про цену; у оператора проблема «Некорректное
  сообщение перевозчика»;
- в логе `dispatch` (`make logs`) одна строка `is INVALID` — запись не повторяется по кругу;
- через 2–3 минуты фоновая сверка забирает настоящий итог у перевозчика: А «Выполнена», в «Сверках» — «Итог получен
  сверкой · по расписанию». Не ждать — «Сверить сейчас»;
- проблема остаётся, пока оператор не нажмёт «Разобрано» с комментарием (без комментария — ошибка под полем).

## 8. Сверка и расхождения

Сверка — прямой вопрос перевозчику про одну заявку (`docs/specs/reconciliation.md`). Фон спрашивает сам (раз в
минуту, только «подозрительные» заявки), оператор — кнопкой «Сверить сейчас» в блоке «Обмен с перевозчиком». Исход
и история — под кнопкой и в разделе «Сверки».

Расхождения честный эмулятор не даёт; их создают служебные команды эмулятора — «перевозчик изменил или потерял данные
у себя». `operationId` копируется кнопкой в блоке «Обмен с перевозчиком»:

```bash
# перевозчик изменил итог
curl -X PUT localhost:8081/admin/operations/<operationId>/result -H 'Content-Type: application/json' \
  -d '{"status":"SUCCEEDED","trackingNumber":"TRK-FFFFFFFF","price":999.00,"reason":null}'
# перевозчик потерял операцию
curl -X DELETE localhost:8081/admin/operations/<operationId>
```

### 8.1. Всё сходится

Заявка с итогом → «Сверить сейчас». Под кнопкой «Совпадает»; в «Сверках» строка «вручную · Оператор (Север)»,
раскрывается и показывает ответ перевозчика.

### 8.2. Перевозчик недоступен

`make fault-unavailable` → «Сверить сейчас» → «Не удалось сверить» с текстом ошибки. Это записанный исход, а не сбой
экрана; заявка не меняется. `make fault-off`.

### 8.3. Перевозчик изменил итог → оператор решает

Нужны две заявки с итогом. На каждой — первая команда, затем «Сверить сейчас».

Ожидаемо: «Расхождение», итог заявки **не** изменился; плашка «Расхождение при сверке» — «Версия перевозчика» рядом с
«Наш итог при обнаружении», номер и стоимость помечены «отличается»; проблема в `/problems`.

- Первая заявка — «Принять версию перевозчика» с комментарием: итог `TRK-FFFFFFFF`, 999,00 ₽, инициатор видит новый
  итог. В закрытой проблеме обе версии остались, ниже «Итог сейчас».
- Вторая — «Оставить наш итог» с комментарием: итог прежний. Повторная «Сверить сейчас» — снова «Расхождение», но
  новой проблемы нет: решение запомнено. Ещё одна правка у перевозчика (`"price":1000.00`) — проблема открывается
  снова.

### 8.4. Перевозчик потерял операцию, итог у нас есть

Заявка с итогом → вторая команда → «Сверить сейчас».

Ожидаемо: «Перевозчик не знает операцию». «Повторить отправку» нет (повтор исполненной заявки дал бы второй эффект),
есть «Оставить наш итог»; после него проблема закрыта, итог прежний.

### 8.5. Перевозчик потерял операцию до итога

1. `make fault-delayed`, создайте заявку, дождитесь у оператора «Получена перевозчиком», `make fault-off`.
2. В течение 15 с — вторая команда (удаление), затем «Сверить сейчас».

Ожидаемо: «Перевозчик не знает операцию», в плашке «Повторить отправку». После повтора перевозчик исполняет операцию:
«Выполнена», проблема закрыта «Отправка повторена».

## 9. Демо-данные

```bash
make seed
```

Создаёт заявки через API, четыре — через режимы сбоев (`docs/specs/demo-seed.md`). У `north.operator` в шапке
«Проблемы, открытых: 4». Разберите каждую:

| Заявка (груз) | Проблема | Действие | Ожидаемо |
|---|---|---|---|
| «Электроника, 12 коробок» | «Некорректное сообщение перевозчика» | «Разобрано» | проблема закрыта |
| «Мебель для кафе, 30 мест» | «Расхождение при сверке» | «Принять версию перевозчика» или «Оставить наш итог» | итог по решению, обе версии в закрытой проблеме |
| «Запчасти для насосов» | «Перевозчик не знает операцию», итог есть | «Оставить наш итог» | итог прежний |
| «Спортивный инвентарь» | «Перевозчик не знает операцию», итога нет | «Повторить отправку» | «Выполнена» |

После всех четырёх счётчик в шапке пропадает; `executionCount = 1` у каждой операции. Повторный `make seed` безопасен.

## 10. Автоматические проверки

```bash
make build                    # unit + интеграционные на реальной PostgreSQL (Testcontainers)
make up && make e2e           # e2e по HTTP против стенда
make web-build && make web-e2e  # веб: типы, Vitest, сборка, Playwright
```

Все зелёные. Моменты падений, которые руками не поймать (между приёмом записи ленты и её разбором, гонки сверки с
лентой и воркером), покрыты интеграционными тестами (`SendWorkerTests`, `FeedPollerTests`, `InboxProcessorTests`,
`ReconcilerTests`, `ReconcileConflictTests`).

## Вне объёма

- Падение веб-клиента (nginx): он не хранит состояния.
- Два разных итога с одним номером в ленте (`RESULT_CONFLICT`): эмулятор его не выдаёт; покрыт интеграционными
  тестами.
