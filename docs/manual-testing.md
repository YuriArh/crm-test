# Ручное тестирование обмена

Проверяются требования ТЗ: система переживает падение и перезапуск во время обмена (D04), принятое задание не
теряется и продолжает обрабатываться после восстановления (D-NF01), принятые изменения сохраняются после
перезапуска приложения и БД (NF03), операция у перевозчика исполняется не больше одного раза (D-NF02, D07).
Отдельно (раздел 7): некорректное сообщение перевозчика требует разбора и не останавливает обмен, бесконечного
быстрого цикла повторов нет (D04, D-NF03).

Общее правило для тестов разделов 5–6: когда бы `dispatch` или БД ни упали и сколько бы ни лежали, после старта каждая
принятая заявка доходит до итога, ни одна не теряется и ни одна не исполняется у перевозчика дважды. Тесты ниже —
это способы уронить систему в разные моменты обмена. Те же моменты покрыты автоматическими интеграционными тестами
(`SendWorkerTests`, `FeedPollerTests`), здесь они проверяются на живом стенде.

## 1. Подготовка

```bash
make up            # собрать и поднять стенд (postgres, dispatch, carrier-emulator, web на :3000)
make fault-off     # все режимы сбоев выключены
```

Два окна браузера на http://localhost:3000, пароль у всех `demo1234`:
- обычное окно — `north.initiator`, он создаёт заявки;
- приватное окно — `north.operator`, он видит заявки службы «Север» и блок «Обмен с перевозчиком» в карточке.

Окна должны быть разными (обычное и приватное): сессия хранится в cookie, общем для одного origin.

Терминал открыт в корне репозитория. Для тестов, где важен момент падения, команду `make dispatch-kill` наберите
заранее и нажимайте Enter сразу после «Создать» в окне «Проверьте данные».

## 2. Команды

| Команда | Что делает |
|---|---|
| `make dispatch-kill` | роняет `dispatch` через SIGKILL, как настоящее падение: процесс умирает посреди работы |
| `make dispatch-start` | запускает `dispatch` и ждёт, пока он станет здоровым (на стенде ~15–20 с) |
| `make db-kill` | роняет PostgreSQL через SIGKILL; приложения продолжают работать без базы |
| `make db-start` | запускает PostgreSQL и ждёт, пока оба приложения снова станут здоровыми (до ~1 мин) |
| `make fault-*`, `make fault-off`, `make faults` | режимы сбоев эмулятора (`docs/specs/carrier-faults.md`) |
| `make fault-malformed` | эмулятор отдаёт в ленте итоги с испорченной ценой (только в ответе, в его базе цена настоящая) |
| `make carrier-ops` | операции эмулятора: `receivedCount` (сколько раз принята), `executionCount` (сколько раз исполнена) |
| `make inbox` | последние 30 результатов, полученных `dispatch`: статус разбора, причина, попытки |

## 3. Куда смотреть

- **Реестр и карточка** (оба окна): статус заявки, результат (номер отправления и стоимость или причина отказа).
- **Блок «Обмен с перевозчиком»** в карточке оператора:
  - «Попыток отправки»;
  - «Следующая попытка» (пока заявка ждёт повтора);
  - «Последняя ошибка» (пока доставка не подтверждена; после подтверждения сбрасывается);
  - «Получение подтверждено»: время и способ — «ответ на отправку» (перевозчик ответил на отправку),
    «по пришедшему результату» (подтвердил результат из ленты) или «сверка» (перевозчик знает операцию);
  - «Сверить сейчас» и раздел «Сверки» — проверки сверки с исходом и автором.
- **Проблемы** (оператор): «Проблемы» в шапке с числом открытых, `/problems`, плашки наверху карточки, значок в
  реестре.
- **`make inbox`**: записи ленты, полученные `dispatch`, со статусом разбора (`APPLIED`, `STALE`, `INVALID`,
  `CONFLICT` …), причиной и числом дублей.
- **`make carrier-ops`**: по каждой операции `executionCount` должен быть ровно `1`. `receivedCount` больше `1`
  значит, что `dispatch` отправлял повторно с тем же `operationId`, и это нормально.
- **История попыток** в интерфейсе появится на этапе 2. До тех пор её можно посмотреть в БД (идентификатор
  операции копируется из карточки оператора):

  ```bash
  docker compose exec -T postgres psql -U dispatch -d dispatch -c \
    "select attempt_no, started_at, finished_at, outcome, error from exchange_attempt
      where operation_id = '<operationId>' order by attempt_no"
  ```

## 4. Что считается успехом

В каждом тесте, кроме отдельно оговорённых ожиданий:
1. Все заявки, созданные до падения, на месте.
2. Каждая заявка дошла до итога: «Выполнена» (номер отправления, стоимость) или «Отказ» (причина).
3. У каждой операции в `make carrier-ops` `executionCount = 1`.
4. Ничего не зависло: у оператора нет заявок, навсегда оставшихся в «Отправляется», «Повтор отправки» или
   «Неизвестно, получена ли».

После каждого теста: `make fault-off`.

## 5. Падение `dispatch`

После `make dispatch-start` в обоих окнах нужно войти заново: сессии хранятся в памяти `dispatch` и при его
падении пропадают. Любое действие в окне само переведёт на страницу входа.

### 5.1. Падение без сбоев

1. Создайте 3 заявки подряд.
2. Сразу `make dispatch-kill`.
3. Подождите сколько угодно (например, минуту), затем `make dispatch-start`, войдите заново.

Ожидаемо: все 3 заявки дошли до итога. Те, что не успели уйти до падения, отправлены после старта.
`executionCount = 1` у всех.

### 5.2. Падение посреди отправки

`dispatch` отправил заявку, перевозчик её получил и исполнил, но ответ до `dispatch` не дошёл, и в этот момент
`dispatch` падает.

1. Включите потерю ответа вместе с задержанным результатом:

   ```bash
   curl -X PUT localhost:8081/admin/faults -H 'Content-Type: application/json' \
     -d '{"unavailable":false,"loseResponse":true,"duplicate":false,"delayed":true,"malformed":false}'
   ```

2. Создайте заявку и **в течение 5 секунд** `make dispatch-kill`. Окно в 5 с — это таймаут ответа `dispatch`:
   пока он ждёт, заявка находится посреди отправки.
3. `make dispatch-start`, войдите заново.

Ожидаемо:
- через ~15 с после создания (задержка `delayed`) итог появляется в карточке;
- «Попыток отправки: 1», «Получение подтверждено … · по пришедшему результату»;
- `make carrier-ops`: `receivedCount = 1`, `executionCount = 1`;
- в истории попыток (БД) через ~60 с после создания попытка 1 закрыта: `UNKNOWN`, «Send was interrupted (lease
  expired)».

Если не успели за 5 с, в карточке будет «Попыток отправки: 2» и «ответ на отправку»: `dispatch` сам получил
таймаут и повторил отправку до падения. Это тоже правильное поведение, но тест проверял не падение. Повторите.

### 5.3. Падение посреди отправки, перевозчик молчит дольше минуты

Проверяет запасной механизм: заявка, брошенная посреди отправки, через 60 с (срок захвата) считается попыткой с
неизвестным исходом и после обычной паузы (~5 с после 1-й попытки) снова уходит в отправку, если за это время ничего
не пришло. Попытки, прерванные падением, входят в общий лимит (`docs/specs/send-recovery-attempts.md`).

1. Пересоздайте эмулятор с задержкой результата 90 с (режимы сбоев после этого выключены):

   ```bash
   CARRIER_DELAYED_RESULT_DELAY=90s docker compose up -d carrier-emulator && make wait
   ```

2. Включите `loseResponse` + `delayed` той же командой `curl`, что в 5.2.
3. Создайте заявку и в течение 5 секунд `make dispatch-kill`.
4. `make dispatch-start`, войдите заново.
5. В конце верните эмулятор к обычной задержке:

   ```bash
   docker compose up -d carrier-emulator && make wait && make fault-off
   ```

Ожидаемо:
- примерно через 65 с после создания (60 с захвата + ~5 с паузы) `dispatch` повторяет отправку с тем же
  `operationId`, перевозчик сразу отвечает; в журнале `dispatch` (`make logs`) —
  «Rescheduled 1 operation(s) after an interrupted send»;
- «Попыток отправки: 2», «Получение подтверждено … · ответ на отправку»;
- итог появляется примерно через 90 с после создания;
- `make carrier-ops`: `receivedCount = 2`, `executionCount = 1`;
- в истории попыток: попытка 1 `UNKNOWN` «Send was interrupted (lease expired)», попытка 2 `ACKNOWLEDGED`.

### 5.4. Падение, когда перевозчик недоступен

1. `make fault-unavailable`.
2. Создайте 3 заявки. В карточке оператора: «Попыток отправки» растёт, есть «Следующая попытка» и «Последняя
   ошибка».
3. `make dispatch-kill`, подождите, `make dispatch-start`, войдите заново.
4. `make fault-off`.

Ожидаемо:
- после старта заявки продолжают ждать повтора, а не теряются;
- после `make fault-off` каждая уходит в своё время «Следующей попытки» (паузы 5, 10, 20, 40… с) и доходит до
  итога;
- `receivedCount = 1`, `executionCount = 1`: отказы `503` перевозчик не считает приёмом.

Держите `unavailable` не дольше нескольких минут: через ~10 минут 8 попыток кончатся и заявка честно перейдёт в
«Ошибка отправки» (`FAILED`), дальше решает оператор.

### 5.5. Падение до того, как результат прочитан

1. `make fault-delayed`: перевозчик сразу подтверждает приём, а результат публикует через 15 с.
2. Создайте заявку. В карточке оператора: «Получение подтверждено … · ответ на отправку», результата пока нет.
3. В течение 15 с `make dispatch-kill`. Пока `dispatch` лежит, результат появляется в ленте перевозчика.
4. `make dispatch-start`, войдите заново.

Ожидаемо: результат применён один раз сразу после старта, «Попыток отправки: 1», `receivedCount = 1`,
`executionCount = 1`. Запоздавшая запись «в работе» не откатывает итог.

### 5.6. Долгий простой

1. Создайте 3 заявки, сразу `make dispatch-kill`.
2. Подождите 5 минут (дольше срока захвата и пауз повторов).
3. `make dispatch-start`, войдите заново.

Ожидаемо: всё как в 5.1, длительность простоя ни на что не влияет.

### 5.7. Несколько падений подряд

1. `make fault-lose-response`, создайте 3 заявки.
2. `make dispatch-kill`, `make dispatch-start`, сразу снова `make dispatch-kill`, затем `make dispatch-start`.

Ожидаемо: все заявки дошли до итога, `executionCount = 1` у всех.

## 6. Падение БД

`dispatch` при этом не падает, поэтому сессии сохраняются, входить заново не нужно. PostgreSQL общий: эмулятор
тоже теряет свою базу и восстанавливается сам. Пока база лежит, интерфейс показывает ошибки загрузки, health
`dispatch` (`curl localhost:8080/actuator/health`) — `DOWN`.

### 6.1. Падение БД с заявками в очереди

1. `make fault-unavailable`, создайте 3 заявки (уходят в повтор).
2. `make db-kill`, подождите, `make db-start`.
3. `make fault-off`.

Ожидаемо: заявки на месте, после выключения сбоя все доходят до итога, `executionCount = 1`. Заявка, созданная
после возврата базы, тоже проходит.

### 6.2. Падение БД посреди обмена

1. `make fault-delayed`, создайте 3 заявки.
2. Сразу `make db-kill`, подождите 20 с (результаты публикуются, пока базы нет), `make db-start`.

Ожидаемо: все результаты применены, по одному разу; `executionCount = 1`.

### 6.3. Создание заявки, когда базы нет

1. Откройте форму «Новая заявка», заполните.
2. `make db-kill`, нажмите «Создать» и подтвердите.
3. `make db-start`, нажмите «Создать» ещё раз с теми же данными.

Ожидаемо:
- первое нажатие показывает ошибку, заявка не создана частично (её нет в реестре);
- второе нажатие создаёт ровно одну заявку, она доходит до итога.

## 7. Плохие записи от перевозчика

Проверяется, что одна некорректная запись ленты не останавливает получение результатов (D04, D-NF03;
`docs/specs/feed-bad-records.md`). `dispatch` сначала принимает записи ленты как есть, затем разбирает каждую
отдельно: плохая получает статус `INVALID` и остаётся для разбора, остальные применяются.

Плохие записи даёт режим `make fault-malformed`: пока он включён, итог «Выполнена» уходит из эмулятора с ценой
`10000000000000.00`, которая нарушает контракт. «В работе» и итог эмулятор публикует вместе, поэтому как только
заявка показывает «В работе», её испорченный итог уже прочитан.

Где видно: карточка заявки, `make inbox` (статус разбора и причина), `make carrier-ops` (настоящий итог у
перевозчика), лог эмулятора `make logs-carrier` (строки `Fault malformed: …`).

### 7.1. Одна заявка

1. `make fault-malformed`.
2. Создайте заявку А, дождитесь статуса «В работе».
3. `make fault-off`, создайте заявку Б.

Ожидаемо:
- заявка Б доходит до «Выполнена»: лента не встала;
- заявка А остаётся «В работе», результата нет — до фоновой сверки;
- `make inbox`: у заявки А запись «в работе» — `APPLIED`, итог — `INVALID` с причиной «price is not a number in
  0..9999999999.99 …»;
- у оператора открыта «Некорректное сообщение перевозчика» по заявке А;
- `make carrier-ops`: у операции заявки А настоящий итог (`SUCCEEDED`, цена) — у перевозчика он есть, `dispatch`
  отверг испорченную запись, итог подтянет сверка;
- через 2–3 минуты (сверка берёт доставку без итога старше 2 минут, проход раз в минуту) заявка А «Выполнена» с
  настоящим итогом, в «Сверках» — «Итог получен сверкой · по расписанию». Проблема «Некорректное сообщение
  перевозчика» остаётся открытой, пока оператор не нажмёт «Разобрано». Не ждать можно: «Сверить сейчас» (§7.5).

### 7.2. Поток заявок

1. `make fault-malformed`.
2. Быстро создайте 5 заявок, дождитесь «В работе» у всех.
3. `make fault-off`, создайте ещё одну заявку.

Ожидаемо: в `make inbox` ровно 5 новых записей `INVALID` (по одной на заявку); все 5 заявок остаются «В работе» до
фоновой сверки (через 2–3 минуты — «Выполнена», как в 7.1), у оператора 5 открытых «Некорректное сообщение
перевозчика»; последняя заявка доходит до «Выполнена». В логе `dispatch` (`make logs`) по каждой записи одна строка `is INVALID`,
без повторов: некорректная запись не повторяется.

### 7.3. Перезапуск после брака

После теста 7.2:
1. Запомните число строк в `make inbox`.
2. `make dispatch-kill`, затем `make dispatch-start`, войдите заново.
3. Создайте заявку.

Ожидаемо: старые записи не разбираются повторно (статусы и число записей прежние, новых `INVALID` нет); заявки из
7.2, ещё не взятые сверкой, остаются «В работе» до неё (после старта — проход «при старте», затем раз в минуту); новая
заявка доходит до «Выполнена».

Падение **между** приёмом записи и её разбором вручную не воспроизвести: оба шага идут в одном проходе с разницей в
миллисекунды. Этот случай проверяет интеграционный тест (`InboxProcessorTests`).

### 7.4. Разбор на экранах

Проверяются экраны проблем (`docs/specs/web-problems.md`). Войдите оператором `north.operator` на http://localhost:3000.

1. `make fault-malformed`, создайте заявку инициатором, дождитесь «В работе», `make fault-off`.
2. В шапке у «Проблемы» число открытых выросло. Откройте «Проблемы»: строка «Некорректное сообщение перевозчика»
   с номером заявки и причиной.
3. Откройте строку: панель с разобранными полями записи и началом исходного текста. Скопируйте адрес страницы и
   откройте в другой вкладке — панель та же.
4. «Разобрано» без комментария — ошибка под полем, запрос не уходит. С комментарием — «Решение сохранено», в
   панели «Закрыта · время · Оператор (Север) · Разобрано», кнопок решений нет; в «Открытых» строки нет, в
   «Закрытых» есть.
5. Реестр, «Есть открытые проблемы»: до шага 4 заявка есть со значком «1», после — нет.
6. `make fault-lose-response` и `make fault-delayed`, создайте заявку, откройте её карточку оператором: плашка
   «Неизвестно, получена ли заявка»; после `make fault-off` она уходит в «Закрытые проблемы» с «Закрыта системой».
7. Войдите инициатором: разделов в шапке и переключателя в реестре нет, `/problems` — «Страница не найдена», в
   карточке нет блока проблем.
8. Повторите 2–4 на ширине 390 px и в светлой схеме: список — карточками, фильтры — в нижней шторке, панель — во
   весь экран, горизонтальной прокрутки нет.

«Повторить отправку» (доставка `FAILED` — около 10 минут `make fault-unavailable`) и решения по расхождению итогов
честный эмулятор сам не даёт (`docs/specs/operator-problems.md` §3); поведение экранов покрыто компонентными тестами.
Расхождения для демо — `docs/specs/demo-seed.md`.

### 7.5. Сверка на экранах

Проверяется часть B `docs/specs/web-problems.md`. Оператор `north.operator`, http://localhost:3000.

1. Заявка с итогом: в карточке, панель «Обмен с перевозчиком» — «Сверить сейчас». Нажмите: окна нет, пока
   перевозчик отвечает — кнопка в загрузке; под кнопкой «Совпадает», подробности и время. В разделе «Сверки» первой
   строкой — время, «Совпадает», «вручную · Оператор (Север)»; строка раскрывается мышью и с клавиатуры (Tab,
   Enter): ответ перевозчика «Исполнена» и его итог.
2. Итог раньше ленты: `make fault-delayed`, создайте заявку инициатором, дождитесь у оператора «Получена
   перевозчиком», `make fault-off` (режим запомнен для операции). Пока итога в карточке нет (15 с), «Сверить
   сейчас» — «Итог получен сверкой · получение подтверждено» или без подтверждения, итог в карточке сразу. Через
   15–20 с, когда лента довезёт тот же итог, ничего не меняется, проблем нет; у эмулятора `executionCount = 1`
   (`make carrier-ops`).
3. Перевозчик недоступен: `make fault-unavailable`, «Сверить сейчас» — «Не удалось сверить» с текстом ошибки
   перевозчика; это исход, а не ошибка экрана. `make fault-off`.
4. Инициатор: ни кнопки, ни раздела «Сверки».
5. Повторите 1 на 390 px и в светлой схеме: раздел помещается, горизонтальной прокрутки нет.

`EXTERNAL_MISSING`, `RECONCILIATION_CONFLICT` и «оставить наш итог» по ним честный эмулятор сам не даёт — их
показывает раздел 8 правкой базы эмулятора.

## 8. Расхождения и потерянные операции

Расхождения итогов и потерянную операцию честный эмулятор не выдаёт (`docs/specs/demo-seed.md`). Здесь они
изображаются правкой базы эмулятора — «перевозчик изменил или потерял данные у себя». Эмулятор отдаёт по
`GET /operations/{id}` итог из строки операции, поэтому сверка видит правку сразу.

Подготовка — как в §1, оператор `north.operator` в приватном окне. Идентификатор операции копируется кнопкой в блоке
«Обмен с перевозчиком». Команда `psql` к базе эмулятора (пользователь и база из `.env`, по умолчанию
`carrier`/`carrier`; внутри контейнера вход без пароля):

```bash
docker compose exec -T postgres psql -U carrier -d carrier -c "<SQL>"
```

### 8.1. Перевозчик изменил итог

1. Создайте заявку, дождитесь «Выполнена». Скопируйте идентификатор операции.
2. Измените итог у перевозчика:
   ```bash
   docker compose exec -T postgres psql -U carrier -d carrier -c \
     "update operation set tracking_number = 'TRK-FFFFFFFF', price = 999.00 where operation_id = '<operationId>'"
   ```
3. `make carrier-ops`: у операции новый номер и цена.
4. В карточке оператора «Сверить сейчас».

Ожидаемо: под кнопкой «Расхождение», итог заявки не изменился; плашка «Расхождение при сверке» с колонками «Версия
перевозчика» и «Наш итог при обнаружении», номер и стоимость помечены «отличается»; проблема есть в `/problems`. В
«Сверках» строка «Расхождение» с «Отличается: номер отправления, стоимость»; раскрытая — колонки «У перевозчика» и «У
нас». Фоновая сверка сама такую заявку не взяла бы (итог уже есть), а открытое расхождение перепроверяет (пауза от 5
минут).

Дальше — на двух заявках:
- «Принять версию перевозчика» с комментарием: итог заявки — `TRK-FFFFFFFF` и 999,00 ₽, проблема в «Закрытых» с
  автором и комментарием; инициатор видит новый итог. В закрытой проблеме колонки по-прежнему разные (прежний номер —
  в «Наш итог при обнаружении»), ниже «Итог сейчас» — итог перевозчика; строка «Сверок» не изменилась;
- «Оставить наш итог» с комментарием: итог прежний, проблема закрыта, колонки разные, «Итог сейчас» — наш. Повторная
  «Сверить сейчас» — снова
  «Расхождение», но новой проблемы нет: в строке «Сверок» — «decided earlier…» (сверка запомнила решение). Ещё одна
  правка у перевозчика (`price = 1000.00`) и «Сверить сейчас» — проблема открывается снова.

Без комментария решение не уходит: ошибка под полем.

### 8.2. Два разных итога в ленте

Делается, когда других заявок в работе нет: вставка в ленту мимо исполнителя эмулятора нарушает правило
«единственного писателя ленты» (если в этот момент исполнитель держит транзакцию с меньшим номером записи, `dispatch`
может сдвинуть курсор мимо неё). Это свойство ручного вмешательства, а не продукта.

1. Создайте заявку, дождитесь «Выполнена». Скопируйте идентификатор операции.
2. Опубликуйте в ленте другой итог с тем же `sequence = 2`:
   ```bash
   docker compose exec -T postgres psql -U carrier -d carrier -c \
     "insert into feed_entry (message_id, operation_id, sequence, status, tracking_number, price, reason, occurred_at)
      values (gen_random_uuid(), '<operationId>', 2, 'SUCCEEDED', 'TRK-FFFFFFFF', 999.00, null, now())"
   ```

Ожидаемо: через несколько секунд плашка «Расхождение итогов» с двумя колонками; `make inbox` — запись `CONFLICT` с
причиной «Sequence 2 was already applied with different content»; итог заявки прежний. «Принять версию перевозчика»
применяет спорную запись, «Оставить наш итог» оставляет итог; в обоих случаях закрытая проблема показывает обе версии
с отметками «отличается» и отдельно «Итог сейчас».

**Вариант: другой итог после итога.** То же с `sequence = 3`, `status = 'REJECTED'`, `tracking_number` и `price` —
`null`, `reason = 'Адрес не обслуживается'`. Ожидаемо: `CONFLICT` с причиной «Request already has a final result
SUCCEEDED; a final result is not replaced», плашка «Расхождение итогов»; «Принять версию перевозчика» меняет итог на
«Отказ».

### 8.3. Перевозчик потерял операцию, итог у нас есть

1. Создайте заявку, дождитесь «Выполнена». Скопируйте идентификатор операции.
2. Удалите операцию у перевозчика:
   ```bash
   docker compose exec -T postgres psql -U carrier -d carrier -c \
     "delete from feed_entry where operation_id = '<operationId>';
      delete from operation where operation_id = '<operationId>'"
   ```
3. «Сверить сейчас».

Ожидаемо: под кнопкой «Перевозчик не знает операцию»; плашка «Перевозчик не знает операцию» с блоком «Наш итог при
обнаружении»;
«Повторить отправку» нет (итог есть), есть «Оставить наш итог». С комментарием — проблема закрыта, итог прежний.

### 8.4. Перевозчик потерял операцию до итога

1. `make fault-delayed`. Наберите в терминале команду удаления из 8.3 заранее, без идентификатора.
2. Создайте заявку. В карточке оператора дождитесь «Получена перевозчиком», скопируйте идентификатор операции,
   `make fault-off` (режим запомнен для операции при приёме).
3. Пока итога нет (15 с после приёма), выполните удаление из 8.3: отложенная публикация итога пропадает вместе со
   строкой операции.
4. «Сверить сейчас».

Ожидаемо: «Перевозчик не знает операцию»; в плашке «Повторить отправку» (итога нет), кнопок решений нет. Окно
повтора: «Перевозчик потерял операцию. Отправим её заново с тем же идентификатором». После повтора перевозчик
принимает операцию как новую и исполняет: заявка «Выполнена», проблема в «Закрытых» — «Отправка повторена»;
`make carrier-ops` — у операции `executionCount = 1` (прежняя строка удалена: это перевозчик, потерявший первое
исполнение, а не двойное исполнение у нас).

## 9. Вне объёма

- Падение эмулятора: он изображает внешнюю систему, его восстановление — свойство стенда, а не `dispatch`.
- Падение веб-клиента (nginx): он не хранит состояния.
