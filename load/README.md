# Нагрузочное тестирование (NF08)

k6 (`grafana/k6`, версия — `K6_IMAGE` в `Makefile`) запускается в Docker, ставить его на машину не нужно.

- Стенд — отдельный Compose-проект `exchange-load` (`make load-up`, `make load-down`, `make load-reset`): свой том
  БД, свои порты (dispatch `18080`, эмулятор `18081`, web `13000`, PostgreSQL `15432`), те же лимиты ресурсов, что
  в `docker-compose.yml`. Демонстрационный стенд во время замера должен быть остановлен: он делил бы CPU Docker.
- k6 работает вне лимитов стека, в его сети, и обращается прямо к `dispatch:8080` — ТЗ меряет время серверного API.
  Внутри контейнера каталог `load/` — это `/scripts`; адреса передаются как `__ENV.BASE_URL`
  (`http://dispatch:8080`) и `__ENV.CARRIER_URL` (`http://carrier-emulator:8081`).
- Результаты пишутся в `load/out/` (в git не входит).
- Скрипты пишутся на TypeScript: k6 исполняет `.ts` сам и просто отбрасывает типы, сборки нет. Поэтому
  разрешён только синтаксис, который можно стереть (`erasableSyntaxOnly`: без `enum`, `namespace`, свойств в
  параметрах конструктора), а локальные импорты пишутся с расширением (`./lib/session.ts`).
- Проверка типов — `make load-typecheck` (`tsc --noEmit`, `typescript` той же версии, что в `web/`, и `@types/k6`
  под версию `K6_IMAGE` — меняются вместе). Установка — `make load-install` (pnpm через corepack).
- Виртуальной машине Docker нужно не меньше 4 CPU, чтобы генератор не отнимал CPU у ограниченных контейнеров.

## Набор данных

`make load-seed` создаёт набор через API (`seed.ts`): 5000 заявок (`PROFILE=full`, по умолчанию) или 200
(`PROFILE=smoke`), поровну от `north.initiator` и `south.initiator`, ждёт итогов перевозчика и добавляет
комментарии и исполнителей. Работает только на пустом стенде; повторный запуск отказывает с подсказкой
`make load-reset && make load-up`. Содержимое заявок детерминировано (`lib/content.ts`), меняется только срок —
от даты сервера. Отправка идёт не быстрее ~20 операций в секунду, поэтому полный набор создаётся несколько минут.

## Прогон

`make load-run` (`run.ts`) — нагрузка по набору: клиенты в замкнутом цикле делают список с фильтром `businessStatus`
(страница 20) → карточку → создание → изменение комментария, поэтому все четыре операции равночастотны. Первые
30 с — прогрев (тег `phase:warmup`), затем замер (`phase:run`); пороги — p95 чтения 2 с, изменения 3 с, ошибок
меньше 1 %. Сводка и выгрузка запросов — в `load/out/` (`summary.json`, `requests.json`).

`make load-smoke` — вся цепочка в малом виде на чистом стенде: набор из 200 заявок и прогон 2 клиентов 10 с + 20 с.
Он проверяет скрипты и ничего не измеряет; он же не подходит для стенда с полным набором (набор откажет).
Повторный короткий прогон по уже созданным данным — `make load-run PROFILE=smoke`.
